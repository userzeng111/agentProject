# 一次性 UI/UX 重构设计与实施方案

## 状态

- 用户已选择路径 B：一次性页面重写。
- 本文是设计与实施方案，尚未进入业务代码修改。
- 详细方案经用户审阅并明确同意后，才可开始实施；当前 active worklog 继续保留，不归档。

## 背景与问题

前端已完成多批 UI 切片，但整体仍处于半迁移状态：项目工作台使用 `/p/{projectId}`，审核、结果和归档详情仍使用 `?id=`；`TaskRunClient`、`TaskReviewClient`、`ChatClient`、`CreateTaskClient` 仍承担过多状态、数据请求与渲染职责。

本方案按用户选择采取一次性重写：先在隔离的新页面结构中完成所有目标视图与回归验证，再在一个发布窗口内切换入口。它不改变后端任务状态机、LLM 调用、模型目录和任务数据语义，只重构前端路由、信息架构、组件边界和交互呈现。

已确认的高风险包括：

1. `output: "export"` 下未知任务 ID 的静态深链接依赖后端 SPA fallback，生产构建产物必须实测验证。
2. 当前聊天页在 `600px` 至 `959px` 可能同时保留两个固定侧栏，挤压主对话区。
3. 当前工作台将关键动作置于两张流程图之后，短视口和移动端无法快速继续任务。
4. 审核追踪和多个图标折叠控件缺少完整键盘语义及稳定可访问名称。
5. 设置页长模型 ID 表格、全局错误页暗色模式、流式聊天错误恢复和统一页面状态反馈尚未形成闭环。

## 目标

1. 以项目为唯一上下文，所有任务阶段均可在同一项目壳层内访问和刷新恢复。
2. 让用户在首屏即可识别当前任务状态、下一步动作、不可操作原因和恢复路径。
3. 在不改变后端状态和 API 合约的前提下，整体替换创建、工作台、审核、结果、归档、聊天和设置的页面结构。
4. 将桌面、平板、移动端和 `320px` 极窄屏视为同一状态机的不同布局，不以隐藏关键操作换取适配。
5. 统一暗色模式、加载/空态/错误反馈、键盘操作、焦点管理和实时状态播报。
6. 将业务控制器、领域视图和无业务共享组件分离，降低后续 UI 修改对任务执行链路的回归面。

## 非目标

- 不修改任务领域状态机、审核决策含义、SSE 协议、LLM 请求协议或模型目录来源。
- 不恢复默认模型或首项模型回退；模型必须继续来自当前 `/api/models` 目录并由用户显式选择。
- 不修改归档的业务时机：任务完成后等待用户确认，用户确认后才归档。
- 不在本批引入新的设计框架、图标库或响应式运行时依赖。
- 不做与 UI 重构无关的后端重构或数据迁移。

## 技术约束

- 前端为 Next.js `14.2.x`、React `18`、MUI `5.16.x`，生产构建启用 `output: "export"`。
- MUI 默认断点为：`xs=0`、`sm=600`、`md=900`、`lg=1200`、`xl=1536`；实现时通过 theme breakpoint API 统一控制，不新增分散的魔法数字。
- MUI 的 Accordion、Dialog、Drawer、Tabs 必须使用其原生焦点和键盘语义；折叠内容提供成对的 `id`、`aria-controls`、`aria-expanded` 与可访问名称。
- Next.js 静态导出只能在构建时生成已知动态参数页面。未知项目 ID 必须继续由静态壳加浏览器路径解析和后端 fallback 提供，不能假设静态主机会自动解析任意 `/p/{id}`。

## 目标信息架构

### 全局入口

| 页面 | 目标入口 | 目的 |
| --- | --- | --- |
| 作品库 | `/` | 项目查找、状态筛选、进入项目、新建项目 |
| 新建项目 | `/new/` | 创建任务及其前置条件说明 |
| 项目空间 | `/p/{projectId}/` | 实时状态、主动作、进度、日志与详情 |
| 项目审核 | `/p/{projectId}/?view=review` | 大纲、章节、验证审核与 Agent 追踪 |
| 项目结果 | `/p/{projectId}/?view=result` | 阅读、复制、导出、用户确认归档 |
| 项目归档 | `/p/{projectId}/?view=archive` | 已归档项目的概览、阅读、原始信息与事件尾流 |
| 归档作品库 | `/archive/` | 已确认归档作品的分页浏览和进入项目归档视图 |
| AI 对话 | `/chat/` | 会话、模型显式选择、流式消息与验证抽屉 |
| 设置 | `/settings/` | 模型协议、RAG 构建和系统级配置 |

`view` 是项目内视图状态，不是新的未知动态路由段。这样可以保持一个可导出的 `/p/[projectId]` 静态壳，同时避免把未知项目 ID 的审核、结果、归档子路由分散成多个静态导出风险点。

### URL 规范化与兼容参数

- `/p/{projectId}/` 是工作台唯一规范地址。`?view=workspace` 是兼容输入，解析后使用客户端 `replace` 规范化为无查询参数地址，避免同一工作台存在两个可分享 URL。
- `?view=review`、`?view=result`、`?view=archive` 是三个非默认项目视图的规范地址。`tab` 仅允许与 `view=archive` 联用，白名单为现有归档页的 `overview`、`outline`、`read`、`meta`；未提供时默认 `overview`。
- `task-routes.ts` 的完整导出为：`homeHref()`、`newProjectHref()`、`workspaceHref(taskId)`、`projectViewHref(taskId, view, options)`、`archiveListHref()`、`chatHref()`、`settingsHref()`、`legacyCreateHref(searchParams)`、`legacyProjectHref(pathname, searchParams)`。前七项只生成新规范 URL；后两项只供旧页面兼容壳使用，任何新入口不得调用它们。
- `legacyProjectHref(pathname, searchParams)` 先规范化来源 pathname 再映射目标视图：`/tasks/ -> workspace`、`/review/ -> review`、`/result/ -> result`、`/archive/detail/ -> archive`；它从 `id` 取任务 ID，且只有来源为归档详情时才读取 `tab`。来源不在白名单或 ID 缺失时返回 `null`，由兼容壳显示“旧链接无效”状态页，禁止猜测目标视图。
- `legacyCreateHref(searchParams)` 仅把现有 URLSearchParams 原样编码到 `/new/`，不解释、不新增也不持久化其中的业务状态；`/create/` 兼容壳必须通过该函数跳转。
- `/archive/detail/?id={id}&tab=read` 必须重定向到 `/p/{id}/?view=archive&tab=read`。合法 `tab` 原样保留，缺失或非法 `tab` 规范化为 `overview`，不得静默丢失 `read` 等用户已选择的视图。
- `next.config.mjs` 已启用 `trailingSlash: true`，因此阶段 1 将现有无尾斜杠 helper 全部改为带尾斜杠输出：`/new/`、`/p/{id}/`、`/archive/`、`/chat/`、`/settings/`。所有 `router.push`、`router.replace` 和 `Link` 只能调用 helper；外部无尾斜杠输入在客户端解析后 replace 为带尾斜杠地址。
- 非归档视图携带 `tab` 时，移除 `tab` 并 replace 为该视图的规范 URL；归档视图携带未知 `tab` 时 replace 为 `tab=overview`。非法 `view` 不自动修正，以错误页保留诊断上下文。

### 旧路由策略

- `/create/` 重定向到 `/new/`，并保留安全的查询参数。
- `/tasks/?id=`、`/review/?id=`、`/result/?id=`、`/archive/detail/?id=` 在客户端读取 ID 后重定向到对应项目视图。
- `/archive/` 保留为独立的全局归档作品库，不并入首页；它继续从归档列表 API 分页读取，卡片统一链接到 `/p/{id}/?view=archive`。顶部导航的归档入口也只指向该列表。
- 新的 `task-routes.ts` 是唯一 URL 生成入口；页面、卡片、恢复流程和 E2E fixture 禁止自行拼接项目 URL。
- 旧路由只保留兼容壳，不再渲染旧页面实现；发布后不允许新链接继续指向旧路由。

### 项目视图可达性

`ProjectPageClient` 在取得项目摘要后按以下规则呈现，所有拒绝页均使用统一 `PageState`，包含原因、关联任务 ID 和明确的主操作，不使用无法解释的自动跳转：

| 输入或任务状态 | 呈现结果 | 主操作 |
| --- | --- | --- |
| 缺失、解码失败或静态占位 project ID | “项目地址无效”错误页，不请求业务 API | 返回作品库 |
| API 返回项目不存在 | “项目不存在或已删除”错误页 | 返回作品库 |
| 非法 `view` | “项目视图不存在”错误页，保留 URL 供诊断 | 返回项目工作台 |
| 无 `view` 的工作台，包括已完成或已归档项目 | 允许只读查看工作台；动作条改为对应的“查看结果”或“查看归档” | 查看结果或归档 |
| `view=review`，任务不处于任何待审核状态 | “当前任务不需要审核”状态页 | 返回项目工作台 |
| `view=review`，状态与 `review_type` 不匹配 | “审核数据状态异常”错误页，记录任务 ID 与当前状态 | 刷新审核数据或返回工作台 |
| `view=result`，`getResult` 成功且结果有正文、正文引用或章节 | 正常结果视图；不以 `completed` 作为唯一可读条件 | 阅读、导出或确认归档 |
| `view=result`，`getResult` 返回“没有可查看结果”且工作台状态不是 `completed`、归档状态不是 `archive` | “结果尚未生成”状态页 | 返回项目工作台 |
| `view=result`，`getResult` 失败但工作台状态为 `completed` 或归档状态为 `archive`，或成功响应没有正文、正文引用和章节 | “任务结果数据不完整”错误页 | 刷新或返回项目工作台 |
| `view=archive`，`storage_state !== archive` | “任务已完成但尚未归档”或“任务尚未完成”状态页 | 已完成时查看结果，否则返回工作台 |
| `view=archive`，`storage_state === archive` 且 `getArchiveDetail` 成功 | 正常归档视图，并按合法 `tab` 恢复页签 | 继续阅读或返回作品库 |
| `view=archive`，`storage_state === archive` 但归档详情缺少正文或 API 读取失败 | “归档内容不完整”错误页，保留错误关联信息 | 返回归档作品库或刷新 |

已完成但未归档的任务始终保留工作台和结果入口，确认归档之前不得被强制跳到归档视图。

### 结果与归档数据判定顺序

前端不能读取后端内部的 `draft_result` 字段，因此 `ProjectPageClient` 必须按固定顺序判定，不能从中文错误文案猜测状态：

1. 先调用 `getWorkspace(taskId)`。失败时按 `ApiRequestError.status` 区分项目不存在、网络/服务错误和可重试读取失败；不会继续请求子视图 API。
2. 进入结果视图时调用 `getResult(taskId)`。成功且至少有 `result_markdown`、`result_md_ref` 或非空 `chapter_index` 时渲染阅读器；非终态任务返回“结果尚未生成”；`completed` 或 `archive` 状态下失败、或成功但三项内容均为空时返回“任务结果数据不完整”。
3. 进入归档视图时先检查 `workspace.meta.storage_state === "archive"`。否则不请求归档详情 API，显示尚未归档状态页；满足条件后调用 `getArchiveDetail(taskId)`，成功时渲染四个归档页签，失败或结果内容全空时显示“归档内容不完整”。
4. `request()` 改为抛出前端 `ApiRequestError`，至少包含 `status`、`path`、`requestId`、`detail` 和是否可重试；该类型只增强前端错误分类与日志关联，不改变后端 HTTP/API 合约。

## 页面与交互设计

### 项目壳层

新增 `features/project/` 作为项目级边界。`ProjectShell` 接收统一的项目元信息、当前视图、阶段导航、主动作和视图插槽，不再由工作台、审核、结果和归档各自维护阶段常量与返回路径。

项目壳层从上到下固定为：面包屑、项目标题与状态、主动作条、阶段导航、当前视图内容。主动作条必须位于首屏，包含一个主动作、必要的次级动作和不可用原因；流程图、调试信息和追踪记录不得占据主动作之前的位置。

阶段导航使用统一的“创建、规划、审核、创作、完成”模型。领域状态只映射到阶段与允许动作，不直接决定页面结构：`waiting_outline_review` 仍属于“规划”阶段但可进入审核视图；`waiting_chapter_review` 与 `waiting_verification_review` 属于“审核”阶段；`ready_for_batch` 映射到“创作”和“继续创作”。

### 审核状态矩阵

审核视图不根据文案猜测类型，只根据后端 `status`、`pending_review.review_type` 与 `outline_batch.phase` 渲染。前端保留现有审核 API 和通过、驳回、修订语义，不将不同审核的数据结构合并为同一表单。

| 后端状态 | 审核类型与子阶段 | 项目阶段 | 材料与视图 | 允许动作 |
| --- | --- | --- | --- | --- |
| `waiting_outline_review` | `outline_review`，`master` | 规划 | 总纲、故事计划、风险标记和 Agent 追踪 | 现有大纲通过、驳回、修订动作 |
| `waiting_outline_review` | `outline_review`，`chapter_batches` | 规划 | 当前章节计划批次、批次进度和 Agent 追踪 | 现有章节计划批次通过、驳回、修订动作 |
| `waiting_chapter_review` | `chapter_pair_review` | 审核 | 当前正文双章节、批次索引和审核意见 | 现有章节对通过、驳回、修订动作 |
| `waiting_verification_review` | `verification_review` | 审核 | 验证报告、待修订项和审核意见 | 现有验证通过、驳回、修订动作 |
| `waiting_manual_action`、`failed`、`cancelled` | 无待审核载荷或恢复载荷 | 按 `current_stage` 映射 | 工作台的人工处理或恢复面板 | 恢复、重新创建、返回作品库等现有动作 |
| 其他状态，或上述状态与审核类型/子阶段不匹配 | 不可用 | 按现有阶段映射 | `PageState` 错误页，显示原始状态和审核类型 | 刷新审核数据或返回工作台 |

### 项目工作台

工作台按“先行动、后观察”组织：

1. 概览区：状态说明、下一个动作、恢复/重试入口、最近错误或警告。
2. 进度区：阶段摘要、章节进度和当前 Agent 状态。
3. 工作区 Tab：概览、活动日志、章节、监督与审核、任务详情、调试诊断。
4. 流程图：移入概览 Tab 的折叠区，默认展示摘要而非两个固定高度画布。

状态与动作必须由单一 `ProjectActionAvailability` 计算：动作名称、可用性、禁用原因、确认文案、目标视图和请求状态一起返回，任何写操作在请求中只能触发一次。SSE 断开、状态刷新失败和恢复模型失效都进入同一错误/可重试呈现，不将错误混入普通日志正文。

### 审核、结果与归档

- 审核桌面使用“材料在左、决策与追踪在右”的两列布局；移动端回到单列，决策区始终紧随材料摘要并保持可见。
- Agent 追踪使用可访问 Accordion，不使用可点击 `Box`；每个展开项有标题、轮次、状态、`aria-expanded` 和内容关联。
- 结果视图以阅读器为主，复制、导出和确认归档位于阅读器上方稳定操作区。归档动作必须显示“任务已完成，等待你确认”的明确状态。
- 归档视图仅允许 `storage_state === "archive"` 的任务进入；`overview`、`outline`、`read`、`meta` 四个现有页签使用同一 Tab/查询参数模型，刷新后恢复当前 Tab。事件尾流保留在 `meta` 信息内，不额外创造未实现的页签。

### 聊天、模型和设置

- 聊天仅在 `lg` 及以上显示三栏：会话侧栏、主消息区、模型验证面板。`md` 到 `lg` 收起验证面板到 Drawer；小于 `md` 将会话和验证都置于独立 Drawer，主消息区不小于可读宽度。
- 流式回复区使用 `aria-live="polite"` 的简短状态播报；长输出提供“停止生成”、错误摘要和原消息上下文内的重试动作。
- 聊天、创建、审核使用同一模型目录与选择状态适配层。模型为空、刷新导致选择失效、模型验证失败都必须阻止提交并给出恢复入口。
- 模型协议的变更只保留设置页中的明确表单控件；首页不再以可点击 Chip 承担系统配置。
- 设置页在 `md` 以下把协议表格切换为键值卡片列表，保持“供应商、协议、保存状态、修改”完整信息和触控操作。

## 组件与状态边界

| 目录/组件 | 责任 | 禁止承担的责任 |
| --- | --- | --- |
| `features/project/ProjectPageClient` | 项目 ID、`view` 解析、工作台预读取、访问约束、项目壳层 | 具体任务动作和业务视图 JSX |
| `features/project/project-state` | 阶段映射、项目视图可达性、动作可用性 | API 请求和 React 组件状态 |
| `features/task-run/useTaskRunController` | 工作台加载、SSE、刷新、任务动作状态 | 页面布局和章节/日志具体渲染 |
| `WorkspaceActionBar` | 主动作、禁用原因、确认与提交中状态 | 直接订阅 SSE |
| `LiveEventLog` | 日志过滤、连接/断开/错误视觉状态 | 任务状态机判断 |
| `features/task-review/useReviewController` | 审核材料、提交、恢复状态 | 多栏布局和追踪项渲染 |

| `features/task-archive/ArchiveLibrary` | `/archive/` 的分页、空态、错误态和项目归档链接 | 项目归档详情与正文阅读 |
| `features/chat/useChatController` | 会话、流式请求、停止、重试、模型选择状态 | 三栏布局与消息视觉呈现 |
| `features/shared/` | `PageState`、`ConfirmActionDialog`、`CollapsibleSection`、通知 hook | 任务或模型领域规则 |

所有页面的通用异步状态统一为：`初始 -> 加载中 -> 成功 / 空态 / 失败`；写操作扩展为：`可操作 -> 提交中 -> 成功 / 失败且可重试`。每种失败必须指定错误区域、恢复动作、焦点落点和日志关联 ID。

## 响应式、主题与无障碍规则

### 布局断点

- `xl` 及以上：允许宽信息密度布局；聊天三栏、审核两列、项目元信息可同行展示。
- `lg` 至 `xl`：工作台和审核保留两列；聊天三栏可用但主消息区最小宽度不足时自动降为两列。
- `md` 至 `lg`：项目页单主列，审核决策区收为材料后的独立区块；聊天验证 Drawer 化；设置使用紧凑表格或卡片。
- `sm` 至 `md`：项目壳元信息换行，阶段导航横向滚动；Dialog 全屏化；列表卡片化。
- 小于 `sm`：导航折叠为带文字或明确 `aria-label` 的菜单入口；关键动作全宽但稳定高度；不使用悬浮卡片嵌套；允许局部内容滚动，禁止页面级横向滚动。

### 可访问性

- 所有点击目标为原生 `Button`、`IconButton`、`Tab`、`AccordionSummary` 或完整等价语义；图标按钮必须有中文 `aria-label`。
- 折叠控件使用 `aria-expanded` 与 `aria-controls`；Dialog、Drawer 需要标题关联、打开时焦点进入、关闭后焦点返回触发器。
- 加载使用 `role="status"`，错误使用可定位的 `role="alert"`，SnackBar 只用于短暂反馈，不替代持久错误与恢复入口。
- 状态、进度和审核结论同时用文字、图标和颜色表达；键盘可完成创建、审核、继续创作、归档与聊天发送。
- 全局错误页、Markdown、React Flow、表格和所有反馈组件必须使用 theme token，不再保留浅色硬编码。

## 一次性切换的实施阶段

虽然对用户采用一次发布切换，但开发必须按下列内部阶段完成，阶段间不可省略验证。

### 阶段 0：冻结接口与建立门禁

1. 记录当前各任务状态、动作、旧路由和 API 请求的契约快照。
2. 为静态构建产物建立真实服务验证：直接访问、刷新和回退 `/p/{id}` 以及四个兼容旧入口。
3. 建立核心旅程 fixture：创建、三个审核分支、继续创作、完成待归档、确认归档、恢复失败、聊天流式失败、模型为空。
4. 未通过静态深链接验证，不得开始替换线上路由入口。

### 阶段 1：项目内核和目标路由

1. 新建 `features/project/`，实现项目 ID/视图解析、工作台预读取、视图可达性、阶段映射和唯一 URL helper；同时将所有 helper 统一为带尾斜杠输出与来源路径感知的旧路由映射。
2. 用新 `ProjectPageClient` 承接 `/p/[projectId]` 静态壳；旧审核、结果、归档详情入口只做兼容跳转。
3. 在测试中证明所有新链接由同一 helper 生成，旧 URL 保留 ID 与目标视图。
4. 新旧视图同时仅存在于开发分支，发布构建中不得由用户在两套实现间切换。

### 阶段 2：重写核心任务视图

1. 重写工作台为项目壳、动作条、状态摘要、工作区 Tab 和独立控制器。
2. 重写审核为总纲、章节计划批次、正文章节对、全文验证四种材料状态下的三类审核视图、决策面板和可访问 Agent 追踪。
3. 重写结果和归档为项目内视图，保留阅读、复制、导出、确认归档和 Tab query 语义。
4. 对所有任务状态运行 E2E，确认动作、禁用原因、恢复路径与旧行为一致。

### 阶段 3：重写创建、聊天和设置

1. 创建页将 RAG、模型和上传前置条件显式纳入提交可用性，所有阻断条件可在提交前被理解和修复。
2. 聊天重构为控制器、会话侧栏、消息区、输入器和验证 Drawer，并加入停止与重试。
3. 设置页统一模型协议配置入口，替换移动端不可用的宽表格。
4. 验证模型目录刷新、用户显式选择、验证失败与空目录不会回退到写死模型。

### 阶段 4：全站视觉、移动端与无障碍收敛

1. 将全局错误页、页面状态、表单反馈、表格和图谱统一接入 theme token。
2. 逐页通过 `320x740`、`390x844`、`768x1024`、`1280x800` 布局矩阵。
3. 逐页通过键盘顺序、焦点回收、折叠语义、对比度、实时播报和 `prefers-reduced-motion` 验收。
4. 清除旧页面实现、重复 URL 拼接和已替代局部 Snackbar，保留兼容重定向壳。

### 阶段 5：一次发布切换与回滚准备

1. 完成全部构建、单元、E2E、接口 smoke、静态产物深链接和人工键盘验收。
2. 将所有新入口一次切到项目内视图，旧 URL 只重定向。
3. 回滚只反转前端入口映射并恢复上一个静态产物；不迁移或修改任务数据，因此后端任务可继续执行。
4. 观察任务创建、审核提交、恢复、归档确认和模型保存错误率；异常时按入口映射回滚而非局部混用新旧视图。

以下任一项为阻断级失败：未知项目 ID 的深链接刷新失败、主动作重复提交、任务状态没有恢复路径、页面级横向溢出、键盘无法操作审核/折叠/抽屉、无模型时发生默认回退、完成任务被自动归档。

## 风险与缓解

| 风险 | 缓解措施 |
| --- | --- |
| 一次性重写回归面过大 | 开发阶段按模块隔离，并仅在阶段 5 做用户入口切换；每阶段都使用固定状态 fixture 回归 |
| 静态导出无法处理未知项目 ID | 以真实构建产物和后端 fallback 为发布门禁；失败时停止切换，先修复托管与 fallback 契约 |
| SSE 与刷新状态竞争 | 控制器集中管理连接生命周期、最后事件版本和可重试状态；E2E 覆盖断线与刷新竞争 |
| 模型目录刷新导致选择失效 | 唯一选择适配层返回显式“需重新选择”状态，所有提交入口统一阻止并引导用户选择 |
| 视觉改造掩盖操作错误 | 主动作、错误与恢复路径优先于图谱和装饰；不使用只靠颜色的状态表达 |
| 旧实现残留造成路由分裂 | 所有新链接经唯一 helper，发布后旧页面仅保留重定向壳，并通过静态检查与 E2E 阻止回流 |

## 交付门禁与后续

1. 先由独立审查角色检查本文是否遗漏状态、路由、迁移或验收缺口。
2. 用户审阅本文并确认后，生成逐文件实施计划；此时才进入 TDD 和代码修改。
3. 实施中持续更新 `worklog/active/UI优化/20260629-02-UIUX体验重塑后续阶段.md`，在全部阶段完成且用户明确同意收口前不得归档。
4. 提交前不得混入 `.superpowers/` 目录、其他活跃任务修改或未经确认的默认模型迁移内容。
