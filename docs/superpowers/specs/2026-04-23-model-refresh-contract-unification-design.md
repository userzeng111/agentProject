# 模型刷新契约统一设计

## 背景

当前模型目录的获取与刷新策略在首页、创建页、运行页、审核页之间并不一致：

- 首页有显式“刷新模型”按钮，并展示缓存相关信息。
- 创建页、运行页、审核页大多只在首次挂载时加载模型列表。
- 模型刷新后的状态反馈、当前缓存年龄、失效提示、动作阻断规则并不统一。

从用户视角看，最直接的问题不是“模型列表有没有拿到”，而是：

1. 我在一个页面点了刷新，另一个页面为什么还是旧模型？
2. 当前已选模型如果失效了，系统会不会悄悄替我换成别的？
3. 我现在看到的模型列表，到底是不是最新的？

前一批“恢复链路显式化”已经解决了恢复动作里的模型语义问题。这一批只解决模型目录刷新的一致性，不扩展到聊天页，也不改后端 TTL 逻辑。

## 用户已确认的硬约束

本设计以以下用户确认结论为准：

1. 本批优先方向是：`模型刷新契约统一`。
2. 只覆盖任务相关页面：
   - 首页
   - 创建页
   - 运行页
   - 审核页
3. 刷新触发方式统一为：手动“刷新模型”按钮。
4. 任务相关页面都要显示刷新状态，不只给按钮或 toast。
5. 刷新后如果当前已选模型失效：
   - 直接阻断
   - 明确提示
   - 要求用户手动重选
   - 不做任何自动回退
6. 模型刷新状态展示位置放在各自模型选择器下方。

## 目标

本次设计要解决以下问题：

1. 统一首页、创建页、运行页、审核页的模型刷新入口。
2. 统一这四个页面的模型刷新反馈口径：
   - 最近拉取时间
   - 当前缓存年龄
   - 刷新成功/失败
3. 统一模型失效后的行为：
   - 禁止静默回退到任务默认模型
   - 禁止静默回退到首个可用模型
   - 明确要求用户手动重选
4. 让运行页、审核页、创建页在“模型目录已刷新但当前选择失效”时，相关动作按钮自动进入阻断态。

## 非目标

- 不改聊天页的模型刷新行为。
- 不重写后端 `ModelCatalogService` 的 TTL 与缓存策略。
- 不引入页面聚焦自动刷新。
- 不做首页/创建页首次使用引导改造。
- 不做模型推荐解释或模型能力展示重构。

## 统一准绳

### 1. 单一心智

本批之后，任务相关页面统一遵守：

> 模型目录是否最新，由用户通过“刷新模型”主动控制；当前选择是否仍有效，由页面明确告诉用户；失效后必须手动重选。

### 2. 禁止静默回退

无论在哪个任务页面，只要当前已选模型在刷新后不再有效：

- 不允许自动切换到任务默认模型
- 不允许自动切换到第一个可用模型
- 必须清空当前选择
- 必须展示失效提示
- 必须阻断相关动作按钮

### 3. 刷新反馈位置

模型刷新反馈一律放在模型选择器下方，避免用户来回扫描页面顶部或全局提示条。

每个页面的反馈结构统一为：

1. 当前刷新状态
2. 最近拉取时间
3. 当前缓存年龄
4. 如模型已失效，则展示阻断说明

## 页面设计

### 1. 首页

首页继续作为全局默认模型的刷新入口，但口径与任务页面统一。

保留：

- `刷新模型` 按钮
- 当前缓存 TTL / 缓存年龄

新增或统一：

- 最近拉取时间
- 刷新失败时的明确文案

首页不承载“当前任务模型失效”的阻断逻辑，因为首页没有具体任务动作。

### 2. 创建页

创建页的模型区域新增：

- `刷新模型` 按钮
- 最近拉取时间
- 当前缓存年龄
- 当前选择失效提示

规则：

- 刷新后如果 `payload.model_id` 已不在最新可用模型集合中，清空选择
- “创建任务”按钮进入禁用态
- 用户必须重新选择模型后才能提交

### 3. 运行页

运行页当前已经有模型刷新按钮，但行为和展示还不够统一。

统一后：

- 继续保留 `刷新模型`
- 模型选择器下方统一展示刷新状态
- 当前动作模型失效时：
  - 清空当前选择
  - 显示“任务默认模型当前不可用，请先手动选择本次动作模型”
  - `开始执行` / `继续创作` 进入禁用态

恢复弹窗沿用上一批规则：

- 恢复动作的模型过滤仍以 `allowed_model_ids` 为准
- 本批只补刷新与状态展示，不改变恢复弹窗的行为语义

### 4. 审核页

审核页的模型选择器也统一为和运行页一致的策略。

统一后：

- 增加 `刷新模型`
- 模型选择器下方展示刷新状态
- 当前执行模型失效时：
  - 清空当前选择
  - 显示失效提示
  - 所有审核提交按钮禁用

## 数据与契约

### 1. 后端

本批不新增后端刷新接口，继续复用：

- `GET /api/models?refresh=true`

后端已有返回字段：

- `meta.cache_ttl_seconds`
- `meta.cache_age_seconds`
- `meta.cached`
- `meta.fetched_at`

本批不改这些字段定义，只要求前端在任务页面统一消费它们。

### 2. 前端

建议抽一个轻量共享状态结构，供首页、创建、运行、审核页复用：

```ts
type ModelRefreshState = {
  loading: boolean;
  error: string;
  fetchedAt?: string;
  cacheAgeSeconds?: number;
  cacheTtlSeconds?: number;
  cached?: boolean;
}
```

并统一出两类辅助判断：

1. `isCurrentSelectionValid`
2. `formatModelRefreshStatus`

## 统一规则

### 1. 刷新成功

刷新成功后：

- 更新模型列表
- 更新刷新状态展示
- 如果当前已选模型仍有效，保留当前选择
- 如果当前已选模型已失效，清空选择并展示阻断提示

### 2. 刷新失败

刷新失败后：

- 保留上一版模型列表，不自动清空
- 模型选择器下方显示失败提示
- 不自动更改当前选择
- 如果当前选择本身已无效，仍保持阻断

### 3. 页面初次加载

页面初次加载时仍会主动获取模型目录，但这不视为“刷新”。

只有用户手动点击 `刷新模型` 时，才更新“最近拉取时间 / 刷新状态”反馈文案。

## 错误处理

### 1. 模型目录为空

如果任务页面拿到空模型列表：

- 选择器显示占位项
- 提示“当前没有可用模型，请先刷新或检查模型接入状态”
- 动作按钮禁用

### 2. 当前模型失效

如果当前选择的 `model_id` 不在最新可用模型集合中：

- 清空当前选择
- 不自动回退
- 选择器下方显示：
  - `当前已选模型已失效，请手动重选`

### 3. 缓存信息缺失

如果 `cache_age_seconds / fetched_at` 缺失：

- 页面仍可显示刷新按钮
- 仅隐藏对应指标，不影响刷新主流程

## 测试与验证

### 1. 前端

需要验证：

1. 首页刷新按钮可正常更新缓存展示
2. 创建页刷新后当前选择失效会被清空并阻断提交
3. 运行页刷新后当前选择失效会被清空并阻断 `开始执行 / 继续创作`
4. 审核页刷新后当前选择失效会被清空并阻断审核提交
5. 刷新失败时，旧模型列表保留，但提示更新为失败状态

### 2. 运行态

需要实测：

1. 后端 `GET /api/models?refresh=true` 可用
2. 首页、创建、运行、审核页的刷新按钮都可触发更新
3. 前端 dev 热更新后首页和任务页面仍能正常访问

## 实施边界

本批只做：

1. 首页模型刷新展示统一
2. 创建页模型刷新按钮 + 状态展示 + 失效阻断
3. 运行页模型刷新状态统一
4. 审核页模型刷新状态统一

本批不做：

1. 聊天页模型刷新统一
2. 模型推荐说明改造
3. 首页/创建页引导设计
4. 模型缓存 TTL 后端策略调整

## 推荐结论

本批推荐采用：

> 统一手动刷新、统一状态展示、失效即阻断、不做任何自动回退。

这样能在不扩大后端改动面的前提下，把任务主链路里的模型选择行为稳定到同一套用户心智里。
