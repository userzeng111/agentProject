# 恢复链路显式化设计

## 背景

当前任务工作台与审核页已经具备“失败后继续恢复”的能力，但从用户视角看，恢复链路仍有三个核心问题：

1. 页面上的“恢复任务”语义过粗，用户不知道点击后到底会发生什么。
2. 恢复动作与模型切换、状态回填、重新开跑混在一起，后果不可预测。
3. 前端主要依赖 `status + error_message + events` 猜恢复语义，缺少后端直出的结构化恢复信息。

这类不确定性会直接降低用户对系统的信任。对创作型产品来说，用户最关心的不是“系统能不能自动恢复”，而是“我的现有产物会不会丢、下一步会不会跑偏、我有没有控制权”。

因此，本次设计不追求重做整条任务状态机，而是聚焦恢复链路的“可解释性”和“可预测性”。

## 用户已确认的硬约束

本设计以以下用户确认结论为准：

1. 首批优化方向聚焦 `运行 / 恢复 / 审核` 链路。
2. 恢复主动作默认采用：`回填最近稳定阶段`。
3. 查看页遇到可修正状态时，继续允许 `静默自动修正`。
4. `按原始输入重新开始` 不作为主入口，只作为二级入口存在。
5. 主恢复动作点击后必须先弹出确认面板，再执行。
6. 恢复面板中的模型默认值采用 `任务默认模型`，用户可手动覆盖。
7. 恢复成功后默认留在当前页，并刷新当前页状态，不主动跳转。
8. `按原始输入重新开始` 作为二级入口，放在恢复确认面板内。

## 目标

本次设计要解决以下问题：

1. 让用户在点击恢复前就能知道“将恢复到哪里、会不会继续生成、会用哪个模型”。
2. 明确区分两个恢复动作：
   - `回填最近稳定阶段`
   - `按原始输入重新开始`
3. 让前端恢复入口不再依赖隐式状态猜测，而是渲染后端返回的结构化恢复信息。
4. 保持现有静默自动修正能力，但不再把真正的恢复决策藏在笼统按钮后面。
5. 统一工作台与审核页的恢复 CTA、确认面板和动作后果说明。

## 非目标

- 不重写整个任务状态机。
- 不在本次设计中取消“页面读取触发静默自动修正”的能力。
- 不重构全部查看接口为绝对只读接口。
- 不处理结果页、归档页、首页的整体信息架构重做。
- 不处理所有动作的统一下一步系统，只聚焦恢复链路。

## 用户心智与产品准绳

### 1. 恢复的主心智

恢复的第一默认语义应是：

> 尽量保住现有产物，从最近一个稳定阶段继续。

而不是：

> 出问题了就直接重跑。

因此系统的第一主动作必须是 `回填最近稳定阶段`，而 `按原始输入重新开始` 只能是低一级、风险更高的备选动作。

### 2. “查看”和“恢复”的边界

本次设计接受继续保留“静默自动修正”的产品方向，但要建立更清晰的边界：

- 轻量状态对账：允许静默自动修正
- 真正恢复执行：必须显式确认

也就是说：

- 如果系统只是把过期的待审核状态校正到最新稳定状态，允许自动进行
- 如果系统将触发真实恢复动作、可能改变任务执行位置或继续生成，则必须要求用户明确点击确认

### 3. 模型的默认值准绳

恢复面板默认采用 `任务默认模型`，不默认使用 `最近一次动作模型`。

原因：

1. 任务默认模型是任务级稳定设定，最符合用户“继续当前任务”的心智。
2. 最近一次动作模型可能正是导致失败或中断的模型，不适合作为默认恢复值。
3. 最近一次动作模型应被展示给用户作为参考，而不是静默回填为默认选择。

## 术语定义

### `回填最近稳定阶段`

含义：

- 系统尝试基于已有稳定产物或稳定状态，将任务恢复到最近一个可继续的阶段

典型结果包括：

- 恢复到 `ready_for_batch`
- 恢复到 `waiting_outline_review`
- 恢复到 `waiting_chapter_review`
- 恢复到 `waiting_verification_review`

默认行为：

- 不主动重新开始整条任务
- 恢复成功后留在当前页，刷新页面状态

### `按原始输入重新开始`

含义：

- 放弃当前不稳定执行上下文，从原始输入重新进入生成起点

典型结果包括：

- 从 `planning` 重新开始
- 重新进入大纲生成链路

展示规则：

- 不作为主按钮
- 仅作为恢复确认面板中的二级操作出现

### `静默自动修正`

含义：

- 页面读取时，后端可对轻量状态不一致做无感知修正

示例：

- 章节审核状态已过期，但小说项目已推进到全文验证审核

约束：

- 静默自动修正不等于自动触发恢复执行
- 若修正结果足以影响用户下一步判断，前端应给出轻量提示

## 交互设计

### 1. 工作台恢复入口

页面主 CTA 规则不是固定文案，而是按后端返回的恢复能力决定：

- 当 `recover_to_stable.available = true` 时：
  - 页面主按钮：`回填最近稳定阶段`
- 当 `recover_to_stable.available = false` 且存在其他恢复方案时：
  - 页面主按钮：`查看恢复方案`

展示条件：

- 仅当后端返回当前任务存在至少一个恢复方案时显示
- 页面主按钮的职责是“进入恢复确认面板”，而不是直接编码某一种动作

按钮附近补充一行短说明：

- 当前任务是否存在稳定阶段
- 当前推荐恢复动作是什么

### 2. 审核页恢复入口

审核页沿用与工作台一致的恢复主按钮与恢复面板。

审核页不应继续依赖模糊的“提交后后台会怎么处理”的心智，而是把恢复动作与审核动作分开：

- 审核动作：处理当前审核内容
- 恢复动作：处理当前任务异常或状态错位

### 3. 恢复确认面板

点击主恢复动作后，弹出统一恢复确认面板。

面板固定展示 4 类信息，但内容必须跟随“当前选中的恢复动作”动态切换。

面板内先展示恢复动作切换区：

- 主恢复动作：`回填最近稳定阶段`
- 二级动作：`按原始输入重新开始`

若 `recover_to_stable.available = false`：

- 该动作不作为可点击主选项
- 面板默认选中 `restart_from_input`
- 页面顶部明确显示：
  - `当前没有可回填的稳定阶段`

当前选中动作对应的确认区域再展示以下 4 类信息：

1. `恢复目标`
   - 将回填到哪个稳定阶段
   - 例如：`将回填到 待章节审核`

2. `恢复后果`
   - 恢复后仅更新状态，还是会继续生成
   - 首批默认设计下，以“恢复后停留在该稳定阶段”为主

3. `本次模型`
   - 默认选中任务默认模型
   - 用户可手动切换为其他可用模型

4. `失败兜底`
   - 若回填失败，系统还能做什么
   - 例如：`你仍可改为按原始输入重新开始`

面板操作：

- 主按钮：`确认执行当前动作`
- 次按钮：`取消`
- 二级动作切换：
  - `回填最近稳定阶段`
  - `按原始输入重新开始`

### 4. 恢复成功后的行为

恢复成功后：

- 不主动跳转
- 保留在当前页
- 刷新当前状态
- 必要时顶部展示一条结果横幅，例如：
  - `已回填到待章节审核，可继续处理`

### 5. “重新开始”二级入口

`按原始输入重新开始` 放在恢复确认面板内，而不是页面主按钮区。

其展示方式应明显弱于主恢复动作，并附带后果说明：

- 这会放弃当前不稳定执行上下文
- 系统将从原始输入重新进入生成起点

## 页面结果行为

### 1. 工作台页

- `recover_to_stable` 成功：
  - 留在当前工作台页
  - 刷新状态
  - 展示恢复结果横幅
- `restart_from_input` 成功：
  - 留在当前工作台页
  - 刷新为新的运行态/规划态
  - 展示“已按原始输入重新开始”的横幅

### 2. 审核页

- `recover_to_stable` 成功：
  - 留在当前审核页
  - 若恢复后的状态仍存在当前审核上下文，则刷新审核内容
  - 若恢复后审核对象变化，则进入“审核状态已更新”的当前页提示态

- `restart_from_input` 成功：
  - 不主动跳转
  - 当前 URL 保持不变
  - 但审核上下文视为失效
  - 页面进入“当前审核上下文已失效，任务已重新开始”的空态视图
  - 提供主 CTA：`打开工作台`

这样可以满足“恢复后留在当前页”的用户约束，同时避免审核页继续假装自己还在展示有效审核对象。

## 后端契约设计

### 1. 新增结构化恢复字段

在 `WorkspaceResponse` 与 `ReviewResponse` 中新增最小结构化字段。

推荐结构：

```json
{
  "allowed_actions": ["recover_to_stable", "restart_from_input"],
  "recommended_action": "recover_to_stable",
  "blocked_reason": "draft_batch_generation_failed",
  "state_reconciled": true,
  "reconciliation_kind": "stale_review_state",
  "reconciliation_summary": "已自动校正到最新稳定审核状态",
  "recovery_options": [
    {
      "action": "recover_to_stable",
      "label": "回填最近稳定阶段",
      "kind": "primary",
      "available": true,
      "reason_unavailable": "",
      "preview": {
        "target_stage": "waiting_chapter_review",
        "target_stage_label": "待章节审核",
        "will_resume_generation": false,
        "default_model_id": "gpt-5.4",
        "last_action_model_id": "glm-5.1",
        "allowed_model_ids": ["gpt-5.4", "glm-5.1"],
        "fallback_actions": ["restart_from_input"]
      }
    },
    {
      "action": "restart_from_input",
      "label": "按原始输入重新开始",
      "kind": "secondary",
      "available": true,
      "reason_unavailable": "",
      "preview": {
        "target_stage": "planning",
        "target_stage_label": "重新进入规划",
        "will_resume_generation": true,
        "default_model_id": "gpt-5.4",
        "last_action_model_id": "glm-5.1",
        "allowed_model_ids": ["gpt-5.4", "glm-5.1"],
        "fallback_actions": []
      }
    }
  ]
}
```

### 2. 字段语义

#### `allowed_actions`

- 当前任务允许的动作枚举
- 用于前端决定展示哪些按钮

#### `recommended_action`

- 后端推荐的主动作
- 首批设计下，优先推荐 `recover_to_stable`

#### `blocked_reason`

- 当前阻塞的结构化原因
- 前端用来显示更准确的恢复说明，而不是只展示原始报错

#### `recovery_options`

- 面向 UI 的动作清单
- 每一项包含：
  - `action`
  - `label`
  - `kind`
  - `available`
  - `reason_unavailable`
  - `preview`

#### `preview`

- `preview` 挂在每个 `recovery_options[n]` 下，而不是顶层单对象
- 原因：
  - 两个动作的目标阶段、生成后果、失败兜底都不同
  - 前端确认面板需要随着动作切换同步切换预览
- 每个 `preview` 至少包含：
  - 恢复目标阶段
  - 是否会继续生成
  - 默认模型
  - 最近一次动作模型
  - 允许选择的模型范围
  - 失败后的兜底动作

#### `state_reconciled / reconciliation_kind / reconciliation_summary`

- 用于表达“页面读取时，后端已经做过轻量静默修正”
- 这是对现有静默自动修正策略的结构化暴露
- 前端可据此决定是否显示轻量提示横幅

### 3. 动作接口

现有接口可以保留，但动作语义需要显式化：

- `POST /tasks/{task_id}/recover`
  - 默认模式为 `recover_to_stable`
- 新增或扩展参数：
  - `recovery_mode = recover_to_stable | restart_from_input`
  - `model_id`：本次恢复动作使用的模型，可选

请求示例：

```json
{
  "recovery_mode": "recover_to_stable",
  "model_id": "gpt-5.4"
}
```

后端校验要求：

- 若 `model_id` 不在当前恢复动作的 `allowed_model_ids` 中，直接返回 `400`
- 若 `recovery_mode` 非法或当前不可用，直接返回 `400`
- 不允许前端提交与当前选中动作不匹配的恢复参数

模型来源要求：

- 恢复确认面板的模型候选列表沿用现有模型目录接口
  - `GET /api/models?refresh=true`
- 但后端恢复预览必须给出该动作允许的 `allowed_model_ids`
- 前端只显示“模型目录 ∩ allowed_model_ids”的交集，避免出现能选但不能恢复的假选项

这样前端可以继续复用一个接口，但不再把“恢复”和“重启”混成一个语义不明的动作。

## 前端设计

### 1. 工作台页

工作台根据 `allowed_actions` 和 `recovery_options` 渲染恢复区，而不是只根据 `status === waiting_manual_action` 硬编码按钮。

展示结构建议：

1. 异常/阻塞横幅
2. 推荐下一步
3. 主恢复按钮
4. 恢复确认面板

### 2. 审核页

审核页同样引入恢复区，但不与审核主操作混排。

推荐布局：

- 审核操作卡片
- 恢复与修复卡片

这样用户能明确知道：

- 通过/驳回是在处理审核内容
- 恢复是在处理任务执行问题

### 3. 模型选择器

恢复确认面板内的模型选择器：

- 默认值：`default_model_id`
- 辅助说明：展示 `last_action_model_id` 作为参考
- 可选列表来源：`GET /api/models?refresh=true`
- 最终可选范围：`模型目录` 与 `preview.allowed_model_ids` 的交集
- 若默认模型已失效，应显式提示，而不是静默回退

## 错误处理

### 1. 无稳定阶段可回填

若当前不存在稳定阶段，则：

- 页面主按钮不再伪装成 `回填最近稳定阶段`
- 页面主按钮显示为：`查看恢复方案`
- 面板默认选中 `按原始输入重新开始`
- 面板中明确说明：
  - `当前没有可回填的稳定阶段`
  - `推荐改为按原始输入重新开始`

### 2. 默认模型失效

若任务默认模型已不在当前可用模型列表：

- 面板中不得静默切到第一个模型
- 必须显式提示：
  - `任务默认模型当前不可用，请手动选择恢复模型`
- 若当前恢复动作没有任何可用模型，则该动作标记为 `available = false`

### 3. 静默自动修正已发生

虽然本次保留静默自动修正，但其可用范围必须收敛为：

- 只允许“状态对账型修正”
- 不允许读取页面时直接恢复执行或继续生成
- 允许的典型场景：
  - 过期审核状态对齐到最新稳定审核状态
  - 缺失但可重建的只读审核载荷回填

页面顶部保留轻量提示位，并由以下字段触发：

- `已自动修正任务状态至最新稳定阶段`

前端触发条件：

- `state_reconciled = true`

这不是阻塞交互，只是降低用户困惑。

## 测试与验证

### 1. 后端

需要补充：

1. `WorkspaceResponse` 返回 `allowed_actions/recommended_action/recovery_options/state_reconciled`
2. `ReviewResponse` 返回同样结构
3. `recover_to_stable` 与 `restart_from_input` 各自的 `preview`
4. `POST /recover` 支持 `recovery_mode + model_id`
5. 无稳定阶段时 `recover_to_stable.available = false`
6. 默认模型失效时的恢复预览与模型范围
7. 轻量静默修正触发时返回 `state_reconciled/reconciliation_*`
8. 非法 `recovery_mode` / 非法 `model_id` 的错误路径

### 2. 前端

需要补充：

1. 工作台恢复按钮渲染逻辑
2. 审核页恢复区渲染逻辑
3. 恢复确认面板按动作切换内容
4. 恢复成功后停留当前页并刷新
5. 默认模型失效时不静默回退
6. 无稳定阶段时主按钮退化为“查看恢复方案”
7. 审核页执行 `restart_from_input` 后进入留页空态

### 3. 真实验收

至少验证以下场景：

1. 章节批次生成失败后，工作台显示“回填最近稳定阶段”
2. 点击恢复后弹出确认面板，并展示恢复目标阶段与默认模型
3. 点击确认恢复后留在当前页，状态刷新为稳定阶段
4. 点击“按原始输入重新开始”时，语义明确，且不会与主恢复动作混淆
5. 审核页出现恢复入口时，审核按钮与恢复按钮不会被误解为同一种动作
6. 无稳定阶段时，页面主按钮退化为“查看恢复方案”，面板默认选中“按原始输入重新开始”
7. 恢复面板里手动切换模型后，提交参数正确透传
8. 审核页执行 `restart_from_input` 后，留在当前 URL 并进入“审核上下文已失效”空态
9. 读取接口发生轻量静默修正时，前端显示轻量提示横幅

## 实施边界

第一批只做以下内容：

1. 工作台恢复入口显式化
2. 审核页恢复入口显式化
3. 后端恢复预览字段
4. 恢复确认面板
5. CTA 文案统一

本批不做：

1. 全量拆分查看接口与恢复接口
2. 结果页、归档页的信息架构重做
3. 全局状态系统重构
4. 大规模动作引擎抽象

## 推荐结论

本次推荐采用：

> 保留静默自动修正，但把真正的恢复动作显式化、可预览、可确认。

这条路线与当前产品约束一致，能在不重写状态机的前提下，最大幅度降低用户对“恢复到底会做什么”的焦虑与误判。
