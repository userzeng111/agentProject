## 本次核定后的口径修正

- `LangGraph` 节点在这个项目里应理解为“返回状态增量的工作流节点”，不应表述为严格意义上的纯函数。
- 大纲审核通过后的真实链路是 `prepare_draft_context -> draft_story`，而不是直接进入 `draft_story`。
- 审核恢复后写入状态的字段名是 `review_comment`，不是旧文档里示意用的 `comment`。
- 网关请求失败后的等待策略目前是线性递增重试：第 1 次等待 `1.5s`，第 2 次等待 `3.0s`，不属于指数退避。
- “阶段上下文包”和“章节生成中的多轮消息历史”是两套不同机制，前者来自 `ContextManager`，后者来自 `StoryEngine` 中的 `conversation_history`。
- 模型上下文窗口、能力位、缓存支持等数字，在本文中都按“当前项目本地注册值或聚合结果”表述，不写成厂商官方永久事实。

## 三篇文档各自解决什么问题

### 一、Agent 与工作流

- 什么是 Agent，为什么不能一次性生成整篇小说。
- `LangGraph` 如何把任务拆成标准化、规划、审核、起草几个阶段。
- 人工审核中断是如何暂停图执行，再由人工恢复继续。

### 二、上下文、压缩、缓存与模型能力

- 模型上下文窗口为什么是稀缺资源。
- 参考素材怎样分配预算、裁剪和组装。
- 为什么项目里既有“上下文快照”，又有“消息历史”和“响应缓存”。
- `/api/models` 背后怎样把网关模型列表和本地能力注册表聚合起来。

### 三、任务持久化与前端联动

- 后端后台线程怎样驱动任务持续执行。
- `tasklog/` 下写入了哪些文件，它们分别服务于展示、回放和归档。
- 工作台页面如何通过 `/workspace` 与 SSE 事件流实时看到任务进展。

## 建议阅读方式

- 如果你第一次接触 Agent 项目，先看第一篇。
- 如果你最关心“上下文是不是连续的”“缓存是不是真的生效”，优先看第二篇。
- 如果你想理解前端为什么能实时看到后台生成过程，优先看第三篇。
