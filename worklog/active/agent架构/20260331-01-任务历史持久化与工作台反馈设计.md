# 任务历史持久化与工作台反馈设计

## 用户原始诉求

创建的 agent 任务没有历史记录，这部分要进行输出数据持续存储，建议类似于 skills 一样保存为 md 文件，并增加对应的 id。希望这部分工作流参考 `OpenSpec`。另外当前任务工作台在等待模型返回的时候太缓慢，需要调整中间内容输出，不要让用户纯等待，例如模型传回来的思考过程等可以持续化。还需要设计首页以及各个页面的返回映射关系。

## 当前状态

已进入实现阶段，正在接通 `tasklog/` 持久化、聚合接口、SSE 工作台反馈与首页/审核/结果页映射。

- 当前先讨论三部分：任务历史持久化、任务中间过程输出、页面返回映射。

- 用户补充硬约束：`tasklog/` 的读取必须像 `skills` 一样按需、分段、最小化，避免一次性回读整份历史造成 token 膨胀。
- 用户已确认接受 `md + json` 混合方案：`md` 负责可读归档，`json` 负责程序化读取与索引。

- 已确认现有 `resume` 报错 `The read operation timed out` 的直接原因是正文生成阶段等待模型响应过久；当前方向应改为章节级持久化和章节级流式反馈，避免用户长时间无感知等待。
- 参考 `OpenSpec` 的核心不是照搬命令，而是照搬“基线规范 + 变更目录 + 完成后归档”的文件化工作流。

## 讨论中方案草案

### 任务历史持久化

- 建议新增独立目录 `tasklog/`，不要混入 `worklog/`。
- 建议参考 `OpenSpec` 分成两层：
  - `tasklog/specs/`：系统当前稳定能力的长期基线说明，例如任务状态定义、事件类型、页面映射。
  - `tasklog/runs/<task-id>/`：单个任务运行目录，保存本次任务的 `request.md`、`plan.md`、`events.md`、`result.md`、`artifacts/`。
- 每个任务 ID 建议继续使用当前 `task_<hex>` 形式，并成为文件系统主键。
- 单个任务目录中建议至少包含：
  - `meta.json`：机器可读元数据
  - `request.md`：用户输入与参考材料摘要
  - `outline.md`：大纲与审核结论
  - `events.md`：运行事件流
  - `draft.md`：最终正文或阶段正文
  - `trace.md`：模型过程输出、章节生成摘要、失败原因

### 中间过程持续输出

- 不建议直接持久化模型原始私有推理内容；更稳的是持久化“可展示的过程事件”。
- 建议将中间输出拆成三层：
  - `system event`：节点切换、状态变化、耗时、失败重试
  - `agent update`：当前在做什么，例如“正在提炼角色关系”“正在生成第 3 章”
  - `artifact preview`：阶段性产物摘要，例如当前大纲摘要、章节摘要、证据片段
- 每条事件都带：
  - `event_id`
  - `task_id`
  - `stage`
  - `event_type`
  - `message`
  - `payload_ref`
  - `created_at`
- 这些事件既写入内存/数据库，也持续追加到对应任务目录下的 `events.md`。
- 前端首选通过 `SSE` 订阅最新事件；只有重连失败或页面恢复时，才按需拉取最近片段。

### token 节省原则

- `tasklog/` 不允许“全文件无脑回读”。
- 所有读取都应先读索引和尾部摘要，再按需下钻到具体章节或具体事件。
- 类似 `skills` 的做法，应优先提供“文件头摘要 + 段落锚点 + 局部片段读取”，而不是整篇展开。
- 目录结构应采用“`md` 主体 + `json` 侧车索引”：
  - `index.json` / `meta.json` 提供快速定位
  - `*.md` 提供人类可读正文
  - 前端默认只请求 `json` 与最近片段，用户点击展开后再拉对应 `md`
- `runs/` 只保留最近和未完成任务，已完成任务自动移入 `archive/`，保证首页与工作台读取范围始终受控。
- `events.tail.json` 只保留最近 `50` 条事件，超过部分仅写入完整 `events.md`。

### 页面映射

- 首页：优先展示最近任务、运行中任务和继续任务入口，不直接展示长正文。
- 首页：不展示全局事件流，避免信息过载和无关 token 消耗。
- 创建页：提交任务后只返回 `task_id` 与初始状态。
- 任务页：主要消费事件流和当前状态，用户在这里看到“持续变化”。
- 审核页：只消费当前待审核对象，例如大纲版本、风格包版本、审核意见历史。
- 结果页：只消费最终正文、章节列表、工件索引、历史版本入口。

### OpenSpec 参考点

- 参考来源显示其基线规范放在 `openspec/specs/`，变更目录放在 `openspec/changes/`，完成后归档到 `archive/`。
- 这类结构适合迁移成“任务运行记录 + 归档”的文件式工作流。

## 僵尸任务根因说明

- 当前确认的两个僵尸任务是：
  - `task_2da277f714`
  - `task_c97310401b`
- 证据：
  - 两个任务的 `meta.json` 都停在 `status = drafting`、`current_unit = outline`。
  - 两个任务的 `events.tail.json` 最后一条都是 `review.submitted`，没有后续的 `draft.generating`、`chapter.started`、`chapter.saved`。
  - 说明它们不是“正文生成到一半卡住”，而是“审核通过后，后台恢复线程根本没有真正进入正文阶段”。
- 已定位到历史根因：
  - 当时 `resume_task()` 会先把任务状态改成 `drafting`。
  - 但后台线程 `_resume_task_sync()` 的状态门禁当时还不接受从 `drafting` 继续恢复。
  - 线程启动后立即因状态检查失败退出。
  - 同时期后台线程封装会吞掉异常，因此任务没有被写成 `failed`，而是停留在 `runs/` 目录下的 `drafting` 状态。
- 这就是“僵尸任务”的定义来源：
  - 文件态显示还在运行；
  - 实际上后台线程早已不存在；
  - 且没有新的事件继续写入。
- 当前代码已做的补救：
  - `_resume_task_sync()` 现在允许从 `drafting` 状态继续恢复。
  - dashboard 现在会把“超过阈值未更新且不在活跃线程集合中的运行中任务”判定为 stale run，不再计入 `active_runs`。
