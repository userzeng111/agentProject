# 小说 Agent 框架设计

## 用户原始诉求

采用 agent team 模式分配任务，基于 `LangChain + LangGraph` 设计一个 Agent 项目整体框架。项目目标是根据输入要求提示词自动生成对应小说，支持长篇和短篇；支持上传已有小说，生成同人内容，或在指定风格时参考原小说进行风格复刻。当前阶段不要求把需求和业务方向实现得很细，重点是输出整体设计框架，考虑如何搭建一个 Agent 框架项目。

## 讨论中方案草案

### 推荐方向

- 接入层负责任务创建、上传、参数配置、审批入口和结果查看。
- `LangGraph` 作为唯一编排中枢，管理任务状态、节点路由、断点续跑与人工介入。
- `LangChain` 负责模型抽象、结构化输出、提示编排、文档加载、切分、检索与向量库集成。
- 领域能力统一抽象为：需求建模、素材归一化、故事规划、内容生成、质量治理、产物装配。
- 通过统一状态对象兼容原创、同人和风格复刻，差异主要体现在输入素材与约束权重，而非拆成三套系统。
- 官方资料进一步确认：`LangGraph` 适合承载 `StateGraph`、`checkpointer`、`interrupt/resume`、`subgraph`、长任务恢复与人工介入；`LangChain` 适合承载结构化输出、提示模板、文档加载、文本切分、检索链路与模型适配。
- 长篇任务需要避免状态膨胀：图状态中只保留最小工作集、摘要、引用键与版本号，正文全文、原文切片和检索缓存应存放在图状态之外。

### 当前推荐的最小技术栈

- 前端：`React + MUI`
- Web 层：用户倾向 `Next.js + React + MUI`
- API / Agent Runtime：采用独立 `Python` 服务承载 `LangChain + LangGraph`
- 编排层：`LangGraph`
- 模型与组件层：`LangChain`
- 图状态持久化：`LangGraph checkpointer`，开发阶段可先 `SQLite`
- 业务元数据：关系型数据库
- 正文与原文工件：对象存储或独立正文存储
- 检索层：`text splitter + embeddings + vector store + retriever`
- 观测层：`LangSmith` 建议作为后续扩展，而不是第一阶段阻塞项

### 当前识别的风险

- 长篇任务容易出现设定漂移、角色口吻变化和时间线冲突。
- 上传原文解析不稳定会污染后续全链路。
- 风格复刻与同人任务边界容易混淆，导致产品语义和技术实现一起失控。
- 过早多 Agent 化会带来成本升高、调试困难和风格漂移。
- 如果图状态直接塞入大文本，`checkpoint` 容易膨胀，恢复与复现都会变差。

## 子代理调研结论（LangChain + LangGraph）

### 适合本项目的能力组合

- 推荐采用“`LangGraph` 负责工作流编排与状态生命周期，`LangChain` 负责模型调用与知识处理组件”的分层。
- 小说生成、同人扩写、风格复刻都属于长链路、可中断、需要阶段化产出的任务，核心流程更适合放在 `LangGraph StateGraph` 中，而不是单个大一统 agent。
- 写作过程建议拆为“任务理解 -> 规划 -> 资料检索 -> 角色/设定提炼 -> 章节生成 -> 审校/改写 -> 人工确认 -> 持久化”这类显式节点，节点之间通过状态字段传递摘要、计划和产物引用，不直接传整本长文。
- `LangChain` 侧优先承担结构化输出、提示模板、文档加载、文本切分、检索器、向量库接入、重排等能力，作为 `LangGraph` 节点内部的执行组件。

### LangGraph 更适合承载的职责

- 用 `StateGraph` 定义主写作状态机，显式描述节点、边、条件分流和失败恢复路径。
- 用 `checkpointer + thread_id` 维护单次创作会话的可恢复状态，支持长任务断点续跑。
- 用 `interrupt` + `Command(resume=...)` 处理人工确认，如大纲确认、风格对齐确认、最终章节放行。
- 用 `subgraph` 或多 agent 方式拆分“世界观提炼”“角色设定维护”“章节起草”“一致性审校”等子流程。
- 用 `Send` 处理可并行的 fan-out 任务，如多候选情节草案、多章节摘要回收、多资料源并行检索。
- 用 `store` 保存长期可复用记忆，如角色卡、世界设定、用户偏好、风格样本元数据；不要把这类长期数据混进每一步 checkpoint。

### LangChain 更适合承载的职责

- 用结构化输出约束大纲、角色卡、章节计划、审校意见等中间产物，避免自由文本污染流程状态。
- 用 `PromptTemplate` / `ChatPromptTemplate` / `MessagesPlaceholder` 管理不同阶段提示词拼装。
- 用文档加载器读取用户上传原著、设定集、角色表、参考文本。
- 用文本切分器按“卷/章/场景/段落”分层切分原文与资料，供检索与摘要使用。
- 用 retriever、vector store、embeddings、rerank 组合实现“相关片段召回”，为扩写与风格参考提供依据。
- 在图节点内部调用 `LangChain` 模型与工具，保持“图负责流程，组件负责执行”的边界清晰。

### 推荐的最小技术栈

- API 层：`FastAPI`
- 编排层：`LangGraph`
- 模型适配层：`LangChain` + 对应模型 provider 集成
- 持久化：`LangGraph checkpointer`（开发期可内存/SQLite，生产建议数据库后端）
- 长期记忆/业务存储：关系型数据库或文档库 + `LangGraph store`
- 检索层：`LangChain` retriever + embeddings + vector store
- 观测层：`LangSmith`（后续建议接入，当前可标记为扩展）

### 长篇小说场景的主要风险

- 最大风险不是模型能力不足，而是全局状态不断堆积，导致 checkpoint 变重、上下文超长、节点输入越来越脏。
- 不建议把完整章节正文、全部历史消息、全部检索片段长期放在共享 state 中。
- 推荐把 state 控制在“当前任务所需的最小工作集”：当前章节目标、已确认摘要、待审校问题、外部内容引用键。
- 长文本正文应落外部存储，只在 state 中保留引用、摘要、版本号和必要元数据。
- 每完成一个阶段，就生成阶段摘要与结构化产物，后续节点优先消费摘要而不是回灌全文。

### 设计建议

- 主流程优先做成确定性较强的图，不要一开始就把所有能力塞进自由决策型 agent。
- “创作 agent” 与 “检索/记忆 agent” 可以拆开，但建议先以单主图 + 少量子图落地，再扩展成 supervisor 模式。
- `LangSmith`、更复杂的多 agent supervisor、细粒度时间旅行、自动评价回路适合作为后续扩展，不建议进入第一版最小设计。
- 如果要支持超长篇，必须尽早引入“章节级状态隔离 + 分层摘要 + 外部正文存储”，否则后续架构会被状态膨胀反向拖垮。
