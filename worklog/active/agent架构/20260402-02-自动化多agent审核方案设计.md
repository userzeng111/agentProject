# 自动化多 Agent 审核方案设计

## 用户原始诉求
基于现在的小说流结构，当前审核部分由人工执行。需要改造成自动化多 Agent 审核模式：开启自动模式后，任务发起并完成大纲编写后，由审核 Agent 自动执行审核，分析不足，判断是否打回重做，最终完成整个自动化任务流。现阶段不需要实际代码与实现，需要先给出方案，并提供必要的文字排版图。

## 当前已知上下文
- 当前主链路为：创建 → 规划 → 人工审核 → 正文生成 → 归档
- 现有 `review_outline` 节点依赖人工审核中断与恢复
- 仓库内已有“审核流程重构：多轮审核 + 章节对锚点 + 全文验证”设计文档，可作为相关参考

## 当前实现核对结论
- 主图当前链路为 `normalize_request -> prepare_outline_context -> plan_story -> review_outline -> prepare_draft_context -> draft_story`
- `review_outline` 通过 `interrupt(...)` 触发人工审核，恢复时由 `Command(resume={approved, comment})` 接续
- 任务层已有可复用的审核语义：
  - `pending_review`
  - `review_type`
  - `review_version`
  - `summary`
  - `risk_flags`
  - `review_history`
  - `review_comment`
- 当前状态枚举里与审核最相关的是：
  - `waiting_outline_review`
  - `waiting_manual_action`
  - `drafting`
  - `cancelled`
- 现有审核页已经能承载：
  - 审核摘要
  - 风险提示
  - 大纲正文
  - 历史审核记录
  - 审核意见提交

## 本轮讨论形成的方案方向

### 推荐主方案
- 采用“固定流水线多 Agent 审核”，不采用首版就上动态 supervisor 调度
- 自动模式下，大纲生成后不直接进入人工中断，而是进入自动审核编排器
- 自动审核编排器内部并行或顺序执行多个审核 Agent，再由裁决 Agent 给出最终结论
- 当裁决结果为“通过”时，直接进入正文阶段
- 当裁决结果为“打回”时，触发大纲修订 Agent，带着审核意见重生成大纲，再回到自动审核链
- 当裁决结果为“高风险 / 低置信 / 连续失败”时，再落回人工审核口

### 建议的 Agent 角色
1. 结构审核 Agent：检查主线、冲突、节奏、章节推进是否成立
2. 设定一致性 Agent：检查世界观、角色动机、章节目标是否前后一致
3. 风格约束 Agent：检查题材、风格、受众、禁忌、参考素材边界是否偏移
4. 裁决 Agent：汇总多份审核结果，输出 `通过 / 打回 / 升级人工`
5. 大纲修订 Agent：根据裁决结果与问题清单修订大纲

### 方案理由
- 最贴合当前仓库已有 `review_history`、`risk_flags`、`pending_review` 和恢复逻辑
- 可解释性比单 Agent 直判更强
- 工程复杂度明显低于 supervisor 动态调度
- 便于后续把同一套模式扩展到章节审核与全文验证

## 关键设计约束
- 自动模式与人工模式必须共存，不能破坏现有人工审核链
- 自动打回必须设置轮次上限，避免死循环
- 自动审核必须保留人工兜底出口，避免黑盒误判把任务直接做废
- 审核历史需要可展示且可追溯，不能只留下最终 verdict

## 待用户确认
- 自动模式是否允许“升级人工”作为兜底出口
- 自动打回轮次上限采用 2 轮还是 3 轮
- 首阶段是否只接管“大纲审核”，后续再扩到章节对与全文验证

## 本轮补充结论：升级难度评估

### 总体判断
- 不是“很大困难到需要推翻重做”，但也绝对不是“只多加几个 Agent 调用”。
- 难度判断为：**中等偏高**。
- 原因不在于 LangGraph 本身做不到，而在于当前仓库大量层面都默认“审核 = 人工 interrupt + 人工 resume”。

### 有利条件
- 当前主图已经不是最初的单线流程，而是已经引入了：
  - 大纲审核循环
  - 章节对审核循环
  - 全文验证循环
- 说明图编排层本身对“多轮审核 / 多轮修订 / 条件分支”是能承载的。
- 当前已有可复用的审核承载结构：
  - `pending_review`
  - `review_type`
  - `review_version`
  - `summary`
  - `risk_flags`
  - `review_history`
  - 任务事件流与文件落盘

### 真正的难点
1. 入口层没有“自动模式 / 人工模式”字段
   - 任务创建层、共享 schema、前端创建页都还没有显式模式切换入口。
2. 审核语义现在以人工为中心
   - `waiting_outline_review`、`resume_task()`、审核页按钮文案都默认是人来做最终判断。
3. 服务层对审核类型的抽象还不够通用
   - 当前 `TaskService` 对 review 的处理和历史归纳，主要还是按大纲人工审核写死。
4. 前端展示骨架可以复用，但内容模型不够
   - 现在能展示摘要、风险、历史，但还没有“多 Agent 结论 / 裁决原因 / 轮次问题清单”的结构。
5. 状态机与事件规范需要重整
   - 自动审核过程如果不补一套新的 stage/event 语义，后续会很难追踪和排错。

### 结论
- **图层改造难度：中等**
- **服务层与状态层改造难度：中等偏高**
- **前端与可视化改造难度：中等**
- **整体联调难度：中等偏高**

### 推荐实施策略
- 不建议一步到位把所有审核都改成多 Agent
- 推荐分三段：
  1. 先只接管“大纲审核”
  2. 稳定后再接“章节对审核”
  3. 最后再接“全文验证”

## 方案候选

### 方案 A：单审核 Agent 直判
- 大纲生成后直接交给单个审核 Agent
- 输出不足分析、通过/打回结论
- 打回时由改稿 Agent 重写，再次审核
- 优点：结构最简单，改动面最小
- 风险：单模型偏差大，误判率高，鲁棒性不足

### 方案 B：并行审核 Agent + 裁决 Agent + 改稿 Agent（推荐）
- 大纲生成后进入自动审核编排层
- 多个审核 Agent 并行从不同维度审查
- 裁决 Agent 汇总各自意见，给出 `通过 / 打回重做 / 升级人工`
- 打回时由改稿 Agent 根据结构化缺陷清单修订大纲，再回到自动审核
- 通过后进入正文阶段；升级人工时才进入现有 `waiting_outline_review`
- 优点：兼顾质量、可解释性、与现有人工恢复链兼容
- 风险：时延和调用成本高于方案 A，需要明确轮次上限

### 方案 C：主创 Agent 自检 + 审核议会 + 人工兜底
- 大纲编写 Agent 先做一次自检
- 再交给多个审核 Agent 会审
- 最后由裁决 Agent 输出结论
- 优点：质量上限更高
- 风险：链路更长，更适合后续增强，不适合作为第一阶段最小落地

## 当前推荐
- 推荐采用方案 B
- 核心原因：
  - 不破坏现有 `interrupt/resume` 设计，只把人工审核前移为“自动审核优先，必要时人工接管”
  - `waiting_outline_review` 继续只表示“真的在等人”，避免状态语义污染
  - 多审核 Agent 并行后再裁决，比单 Agent 直判更稳定，也比完整议会模型更容易第一阶段落地

## 推荐流程草图
```text
创建任务
  -> 生成大纲
  -> 自动审核编排器
       -> 审核Agent-结构
       -> 审核Agent-设定/人物一致性
       -> 审核Agent-风格/禁忌/目标约束
       -> 裁决Agent汇总
            -> 通过: 进入正文生成
            -> 打回: 改稿Agent重写大纲 -> 再次自动审核
            -> 升级人工: 进入 waiting_outline_review -> 人工 resume
  -> 正文生成
  -> 完成/归档
```

## 初步规则建议
- 自动审核最多重试 `2~3` 轮，超过即升级人工
- 裁决结论固定三态：`approved / revise / escalate`
- 只有升级人工时才写入 `pending_review`
- 自动审核过程优先保持 `status = planning`，通过 `current_stage` 区分 `auto_outline_review`、`auto_outline_revision`
- `waiting_manual_action` 继续保留给“自动链跑不下去，需要用户明确处理”的场景

## 当前仓库现状核对
- 当前主图为 `normalize_request -> prepare_outline_context -> plan_story -> review_outline -> prepare_draft_context -> draft_story`
- `review_outline` 当前通过 `interrupt()` 触发人工审核暂停，恢复时使用 `Command(resume={"approved": ..., "comment": ...})`
- 当前任务状态只有一个审核等待态：`waiting_outline_review`
- 当前前端审核页已具备以下展示槽位：`review_type`、`review_version`、`summary`、`risk_flags`、`review_history`、`outline_markdown`
- 当前审核历史主要基于事件流派生：`review.waiting`、`review.submitted`、`task.cancelled`、`task.completed`

## 初步方案方向
- 不建议直接删除人工审核能力，推荐改为“人工模式 / 自动模式”双轨共存
- 自动模式下，将原本单点人工审核改为图内多 Agent 审核闭环：`大纲生成 -> 多 Agent 评审 -> 汇总裁决 -> 通过 / 打回修订 / 升级人工`
- 人工 `interrupt()` 更适合作为兜底出口，而不是自动模式主路径；这样既贴合 LangGraph 能力边界，也能保留高风险任务的人类接管点
- 推荐先做“大纲阶段自动审核 MVP”，暂不一次性扩大到章节对审核与全文验证自动化

## 当前识别的关键风险
- 若没有明确“通过阈值 / 打回阈值 / 人工升级阈值”，自动审核容易出现反复打回或误放行
- 若复用现有 `waiting_outline_review` 语义但不增加自动审核过程可视化，用户会感觉任务黑盒运行
- 若把所有 Agent 结论都直接暴露给用户，信息会过载；若完全不展示，又缺乏可解释性
- 若缺少最大重试轮数与人工兜底，任务可能卡在自动循环中

## 本轮讨论结论

### 目标拆分
自动模式下，不是简单把“人工点击通过/驳回”换成“一个模型判断”，而是要拆成三层职责：
1. 审核分析：指出大纲缺陷、风险、不足
2. 审核裁决：判断通过、打回重做、升级人工
3. 流程推进：根据裁决决定继续生成、进入重写循环或挂起

### 候选方案

#### 方案 A：单审核 Agent 直判
- 大纲生成后，由一个审核 Agent 输出分析与结论
- 若通过则继续，若不通过则打回大纲重写
- 优点：最简单，改动面最小
- 缺点：单点偏差大，可解释性弱，不适合作为长期主方案

#### 方案 B：固定流水线多 Agent 审核
- 大纲生成后，按固定顺序运行多个审核 Agent：
  - 结构审核 Agent：看故事骨架、节奏、章节设计
  - 设定审核 Agent：看世界观、人物动机、一致性
  - 风格与约束审核 Agent：看题材、风格、禁忌、目标受众
  - 裁决 Agent：汇总前述结论，给出通过 / 打回 / 升级人工
- 若打回，则进入 `revise_outline`，再回到自动审核链
- 优点：可解释性强，适合映射到现有 review history / risk flags
- 缺点：链路更长，成本高于单 Agent

#### 方案 C：Supervisor 动态调度多 Agent
- 由一个总控 Agent 先看大纲，再决定是否调用不同审核子 Agent
- 子 Agent 数量和顺序按任务复杂度动态变化
- 优点：理论上最灵活
- 缺点：对当前仓库来说过重，不利于和现有固定状态机对齐

### 当前推荐
- 推荐 **方案 B：固定流水线多 Agent 审核**
- 原因：
  - 最贴合当前仓库现有 `StateGraph + 条件分支 + review_history` 结构
  - 能保留自动模式和人工模式共存
  - 比 supervisor 式动态路由更容易做状态落盘、问题追踪和前端展示

## 推荐架构草图

```text
手动模式
创建任务
  -> 生成大纲
  -> 人工审核中断
  -> 通过: 生成正文
  -> 驳回: 结束 / 等人工处理

自动模式
创建任务
  -> 生成大纲
  -> 自动审核编排器
       -> 结构审核 Agent
       -> 设定审核 Agent
       -> 风格约束审核 Agent
       -> 裁决 Agent
  -> 裁决结果
       -> 通过: 生成正文
       -> 打回: revise_outline -> 回到自动审核编排器
       -> 升级人工: waiting_outline_review
```

## 推荐状态流转
- 不建议一上来推翻现有 `waiting_outline_review`
- 推荐先保留两套入口：
  - `manual`：继续走 `interrupt + resume`
  - `auto`：走自动审核链，只有遇到低置信度、冲突裁决、超过重试上限时才落到 `waiting_outline_review`
- 推荐新增的是“阶段/节点语义”，而不是先大改全部任务状态枚举

## 自动审核的决策规则建议
- `通过`
  - 所有审核 Agent 都未命中硬性风险
  - 关键评分达到阈值
  - 裁决 Agent 置信度达标
- `打回`
  - 存在可修复问题，如人物动机弱、章节目标模糊、风格偏移
  - 但问题不需要人工重新定义需求
- `升级人工`
  - 审核结论冲突明显
  - 多轮重写仍未达标
  - 大纲与原始用户诉求存在方向级冲突
  - 命中高风险约束，如禁忌、题材边界、参考素材侵权风险

## 风险与边界
- 若自动审核直接拥有最终裁决权，必须给用户暴露完整审核理由，避免“黑盒通过/黑盒驳回”
- 自动打回必须设置上限，建议 `2~3` 轮；超过上限直接升级人工
- 自动模式应默认保留人工接管按钮，否则故障时会卡死在后台链路
- 现有 `review_history` 目前语义较粗，后续若实施，建议扩展为“分析结果 + 裁决结果 + 重写轮次”
