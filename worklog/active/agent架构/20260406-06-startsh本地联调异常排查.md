# start.sh 本地联调异常排查

## 用户原始诉求
- 本地执行 `start.sh` 测试时，为什么 `localhost:3000` 会有问题

## 当前已知上下文
- 根目录存在 `start.sh`，用于并行启动前后端
- 后端本地端口口径为 `8000`
- 前端本地端口口径为 `3000`
- `start-backend-tunnel.sh` 刚刚已经确认存在“优先使用系统 Python 而非项目 `.venv`”的问题，并已修复

## 当前状态
- 已创建问题记录
- 正在复现 `start.sh` 的实际启动表现并核对根因

## 本轮排查记录
- `start.sh` 当前实现特征：
  - `detect_python()` 优先返回系统 `python3`
  - 后端启动命令为 `python3 -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload`
  - 脚本没有等待后端健康检查成功，就直接打印“后端已启动”
- 实际复现 `timeout 12s ./start.sh` 输出：
  - 检测到 Python 为 `/usr/bin/python3`（`Python 3.10.12`）
  - 后端立即报错：`/usr/bin/python3: No module named uvicorn`
  - 但脚本仍打印：
    - `后端已启动 (PID: ..., http://localhost:8000)`
    - `前端已启动 (PID: ..., http://localhost:3000)`
  - 前端 `npx next dev` 实际可以进入 `Ready in 4.2s`
- 由此确认：
  - `localhost:3000` 的“有问题”不是前端完全起不来
  - 而是 `start.sh` 启动的后端根本没起来，导致前端页面加载后访问 API 会异常
- 额外发现：
  - `apps/web` 目录只有 `package-lock.json`，当前项目实际包管理器口径为 `npm`
  - `start.sh` 这轮运行也确实检测到了 `npm`

## 当前结论
- 根因与刚修复的 `start-backend-tunnel.sh` 属于同一类：
  - `start.sh` 没有优先使用 `apps/agent-runtime/.venv/bin/python`
- 其次还有一个脚本层面的误导问题：
  - 即便后端启动失败，脚本仍然提示“后端已启动”，没有做健康检查门禁

## 本轮实现进展
- 已修复 `start.sh`：
  - 优先使用 `apps/agent-runtime/.venv/bin/python`
  - 按锁文件优先选择前端包管理器，当前仓库优先 `npm`
  - 后端改为等待 `/api/health` 成功后再宣告启动完成
  - 前端改为等待 `http://127.0.0.1:3000` 返回成功后再宣告启动完成
  - 清理逻辑改为带引号的 PID 关闭，避免空值或特殊字符问题

## 本轮验证记录
- `bash -n start.sh`
  - 通过
- `timeout 20s ./start.sh`
  - 后端成功启动并通过 `/api/health`
  - 前端成功启动并返回 `GET / 200`
  - 超时退出后 `3000` 与 `8000` 均无残留监听
