# 多agent任务流与架构合理性评审

## 用户原始诉求

- 执行 code review
- 分析系统中存在的问题
- 评估“复杂任务可自增分配 agent”的系统流是否合理
- 对整体架构进行合理性设计分析
- 本轮限定只读范围为 `apps/agent-runtime/app/context/manager.py`、`apps/agent-runtime/app/context/assembler.py`、`apps/agent-runtime/app/context/models.py`、`apps/agent-runtime/app/llm/auto_reviewer.py`、`apps/agent-runtime/app/llm/story_engine.py`、`apps/agent-runtime/app/storage/task_store.py`

## 本轮计划
- 梳理主任务流、审核流、上下文流与状态持久化结构
- 识别当前系统是否具备“任务拆分 -> 子 agent 派发 -> 汇总收口”的明确边界

- 输出问题分级、架构判断与设计建议

## 本轮审查结论（2026-04-05）
- 当前运行时主编排本质上是“单任务 + 单状态机 + 单后台线程”的串行工作流，不存在显式 `subtask` / `child task` / `child agent` 的领域对象与生命周期管理。
- `WorkflowState` 仅维护单个 `task_id` 下的大纲、章节对、验证三段循环；所谓“多 Agent”主要体现在自动审核返回的 `agent_trace`，更像审核内部实现细节，而不是运行时主编排层的任务分派能力。
- 已发现“审核循环重试/修订次数上限”和上下文预算、缓存状态展示，但未发现通用调度器、任务拆分器、结果汇总器、资源预算控制、失败重试队列或并发执行编排。
- API 层只暴露 `create/run/resume` 与查询接口，没有面向子任务、子 Agent、编排 DAG、依赖关系或汇总结果的外部操作面。

## 本轮范围内补充结论（限定 6 个文件）
- 上下文与存储建模明显以 `task_id` 为主轴：`ContextPacket` / `ContextSnapshot` 只有任务维度，没有 `agent_id`、`agent_session_id`、`subtask_id` 等隔离字段。
- `ContextManager` 与 `StoryEngine` 的缓存键都未纳入 `task_id` 或 `agent_id`，说明缓存设计默认允许跨任务复用相同输入的结果，这与多 Agent 自治协作所需的强隔离存在冲突。
- `AutoReviewManager` 确实实现了“角色化并行审核子 Agent + 综合 Agent”的模式，但仍属于单个编排器在一次审核请求内发起的并行 LLM 调用，并未形成可独立持久化、可恢复、可继续对话的自治 Agent。
- `StoryEngine` 属于单 Agent 多阶段生成链路：大纲、章节、修订、验证、修复均复用同一引擎与同一响应缓存体系，没有按角色拆分的子 Agent 状态面。
- `TaskLogStore` 可按任务写入上下文快照、消息历史、事件流与当前阶段，但存储路径只区分 `task_id/stage/name`，没有 agent 级命名空间；并且 `trace/current.json` 只保留当前阶段摘要，不足以支撑多 Agent 的精细恢复。

## 问题分级汇总

### P0 / 严重
- 当前系统不是“复杂任务可自增派发的多 Agent 主编排系统”，而是“单任务状态机 + 自动审核并行调用”。
- 缺少显式 `subtask / agent_run / supervisor_decision / dependency` 等领域模型，无法表达：
  - 顶层任务拆分为哪些子任务
  - 哪些 Agent 正在执行
  - 谁依赖谁
  - 哪个单元失败后应局部重试还是整体回滚

### P1 / 高
- 缺少顶层 supervisor / router / aggregator：
  - 当前 `TaskService` 只负责起线程和调用 `graph.invoke()`
  - `main_graph` 只负责阶段推进，不负责动态派发与资源仲裁
- 上下文、缓存、持久化均为任务级，不是 agent 级：
  - 难以保证独立记忆空间
  - 难以解释多 Agent 之间的上下文边界
  - 难以做 agent 级恢复与可观测
- 自动审核中的“多 Agent”没有自治生命周期：
  - 只是一轮审核内部的并行角色调用
  - 不是可单独恢复/继续/观察的子 Agent

### P2 / 中
- 失败治理仍偏流程兜底：
  - 修订次数到上限后存在直接放行语义
  - 更像为了不阻塞流程，而不是严格的质量与失败治理
- 前端和文档对外口径目前仍更接近“单任务工作流系统”：
  - 如果要宣称多 Agent 编排平台，当前证据不足

## 架构判断
- 如果你的目标只是：
  - 单任务写作流程
  - 中间插人工审核
  - 审核里让多个角色并行给意见
  - 最终生成结果并归档
- 那么当前架构是基本合理的，且已有一定工程基础。

- 如果你的目标是：
  - 复杂任务进入后可自动拆解
  - 按复杂度递增派发更多 Agent
  - 子 Agent 可独立上下文、独立运行、独立恢复
  - 顶层统一汇总、裁决、重试与回滚
- 那么当前架构不够合理，主要问题不是“少几个节点”，而是“缺一层顶层编排模型”。

## 建议方向
- 不建议继续在现有单状态机里无限堆节点来模拟多 Agent。
- 更合理的方向是两层结构：
  - 顶层：`SupervisorGraph`
    - 负责任务分类、拆分、派发、预算、汇总、失败治理
  - 下层：`Worker Subgraph / Specialized Agent`
    - 负责单一职责执行，例如规划、资料分析、章节写作、验证、修复
- 并补齐四类基础设施：
  - 子任务与 agent run 领域模型
  - agent 级上下文与缓存命名空间
  - agent 级事件、trace、恢复点
  - 汇总与收口策略

## 对照官方模式的结论
- 结合官方 `LangGraph` 与 `LangGraph Supervisor` 文档，复杂多 Agent 系统更适合采用：
  - supervisor 路由多个 specialized agents
  - 支持 nested supervisors 的层级结构
  - 依赖 durable execution 与 human-in-the-loop 做恢复与接管
- 当前仓库已经具备：
  - `LangGraph` 状态编排
  - checkpoint
  - interrupt / resume
  - 任务级持久化与 SSE
- 但尚未进入 supervisor / hierarchical multi-agent 的架构阶段。
