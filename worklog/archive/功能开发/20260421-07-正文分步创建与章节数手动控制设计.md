# 问题标题
正文分步创建与章节数手动控制设计

# 用户原始诉求
- 进入创建正文后，不要一次性把全部章节都创建完。
- 需要改为分步创建，用户可以输入“本次创建章节数”，后续继续时从后续章节接着创作。
- 已经创作完成的章节需要在数据库中记录。
- 总章节数不要只靠分级选择，用户需要可手输，例如输入 `100` 章，并允许根据剧情上下浮动 `10` 章。
- 用户补充：
  - 数据库存储用于任务恢复与进度追踪，至少要存：小说名、大纲章节列表、进度状态等结构化信息。
  - 正文章节内容仍然保存在本地 `md` 文件中。
  - 需要继续脑暴“任务恢复追踪”的持久化方案，必要时为数据库增加索引。

# 当前状态
已归档：本轮目标已完成，包含目标总章节数、分步继续创作、SQLite 结构化进度、章节本地 `md+json` 落盘、恢复校验与人工修复回迁首版能力，并已完成后端全集、API 冒烟、前端冒烟与生产构建验证。

# 当前结论
- 当前正文生成链路仍以 `chapter_plan` 全量推进，批次大小主要由系统内部决定，用户没有“本次生成几章”的控制入口。
- 当前总章节规划来源于 `planned_chapter_count / chapter_plan`，但创建页前端仍以分级为主，没有用户手填总章节数入口。
- 该需求至少会涉及：
  - 创建页输入模型
  - 审核页/继续创作页交互
  - 后端 `resume` / 章节批次推进逻辑
  - 任务状态中已完成章节与下一批计划的持久化
- 当前实现中，章节正文已经按 `artifacts/chapter-xx.md` 落盘，本地 `md` 路径可以复用。
- 当前数据库只有任务索引表，不足以承载“章节计划 / 已完成章节 / 下一批次 / 进度恢复”这类结构化状态，需要新增持久化表或扩展索引模型。
- 用户已确认：
  - 持久化方案选择 `A`：SQLite 仅存结构化状态，正文继续存本地 `md`
  - “本次创建章节数”输入位置选择 `2`：放在工作台单独的“继续创作”面板
  - 默认批次大小选择 `3`
- 已生成正式设计文档：`docs/superpowers/specs/2026-04-21-batched-chapter-generation-and-persistence-design.md`
- 已生成实现计划：`docs/superpowers/plans/2026-04-21-batched-chapter-generation-and-persistence-implementation.md`
- 现版设计已明确：
  - `target_chapter_count` 为用户主控目标
  - `chapter_count_min/max` 为创建时固化范围
  - `planned_chapter_count` 为正文阶段最终执行准绳，且必须满足范围校验与 `chapter_plan` 数量一致
  - “继续创作”接口采用 `continue_request_id` 作为批次幂等键
  - 正文批次持久化采用“先建批次、再落文件、再回写章节状态”的顺序
  - 恢复逻辑按稳定状态机与文件一致性校验执行

# 交互草案
- 创建任务时：
  - 用户输入目标总章节数，例如 `100`
  - 系统生成章节规划约束，例如 `90-110`
  - 前端直接展示该浮动范围，并允许主 agent 最终将 `planned_chapter_count` 落在该区间内
- 大纲审核通过后：
  - 不直接无条件启动正文全量创作
  - 进入“继续创作”控制面板
  - 默认带出“本次创建章节数 = 3”
  - 用户可改成其他值后再启动本批次创作
- 后续续写时：
  - 从 `next_chapter_number` 继续往后写
  - 已完成章节的结构化信息写入 SQLite
  - 章节正文继续写入本地 `artifacts/chapter-xx.md`
