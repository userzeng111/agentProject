# 问题标题
评审回归修复

# 用户原始诉求
- 修复评审指出的三个回归：
  - `planned_chapter_count` 未校验导致章节生成可能空循环卡死。
  - 章节范围硬约束错误覆盖用户填写的目标章节数，并把 `long` 默认 400 章误改成 `401+`。
  - 聊天页在没有可用 gateway 模型时错误预选本地画像模型，导致聊天请求显式带入不可用模型。

# 当前状态
已完成修复与验证，待用户确认是否收口归档。

# 初步关注点
- `planned_chapter_count` 与 `chapter_plan` 长度不一致时，工作流是否会在 `generate_chapter_pair -> accumulate_chapters -> route_after_accumulate` 间空循环。
- 章节范围文案是否应优先使用任务里的 `target_chapter_count/chapter_count_min/chapter_count_max`，仅在缺省时回退到篇幅分档。
- 聊天模型选择是否应只在存在 gateway-backed 模型时预选，否则保持 `null` 以回退后端默认模型。

# 本轮结论
- 后端 `build_normalized_spec()` 已改为优先使用任务输入中的：
  - `target_chapter_count`
  - `chapter_count_min`
  - `chapter_count_max`
  仅在缺省时才回退到篇幅默认值，不再把 `long` 固定写成 `401 章及以上`。
- 后端章节循环已改为以 `chapter_plan` 的实际长度作为有效总章节数来源，并在 `plan_story/revise_outline/prepare_chapter_pair_context` 统一规范化 `story_plan.planned_chapter_count`，避免因 LLM 返回更大的计划值而进入空批次循环。
- 前端聊天模型默认预选已收紧到仅允许 gateway-backed 模型：
  - 没有可用 gateway 模型时不再回退到 `registry` 本地画像模型
  - 会话里保存的 `registry` 模型也不会再覆盖聊天默认模型
  - 这样聊天请求会继续走后端默认模型兜底
- 为前端模型选择新增了独立纯函数与 Node 内置测试，避免后续再把 `registry` 模型预选回去。
