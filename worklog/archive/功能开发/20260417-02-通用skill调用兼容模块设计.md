# 问题标题
通用 skill 调用兼容模块设计

# 用户原始诉求
全程采用agent team：还有一个问题，这个skill是我的codex和cluade code的通用skill调用规则，所以你要参考这个进行优化，他的加载调用实际路线应该和这个是一样的，你考虑一下增加一个skill调用兼容模块，我不只是有这个skill，头脑风暴一下。

# 当前状态
已完成：已实现小说专用 `skill` 通用层，统一 workflow 与 style 两类小说包的运行时上下文装配，并完成后端验证。

# 2026-04-17 当前讨论结论
- 主项目现有两套相邻但不同的机制：
  - `app/agents/loader.py` + `BaseAgent._load_skills()`：面向 Agent prompt YAML 的 SkillLoader，目标是加载可执行 prompt 配置。
  - `app/style_profiles/service.py`：面向小说风格实例目录的 Profile Loader，目标是把实例规则压缩成 `compiled_summary` 供写作链路注入。
- 当前仓库并没有实际被 `SkillLoader` 读取到的 `story_engine` / `auto_reviewer` 外部 YAML skill 文件，因此这套 Skill 机制目前是“接口和 fallback 已就位、外部实例未落地”。
- 因此通用兼容模块更适合承担：
  - 统一目录扫描；
  - `manifest` / 元数据读取；
  - 规则文件聚合与摘要编译；
  - 输出标准化运行时对象。
- 不适合把以下内容耦合进通用兼容模块：
  - 小说专用字段名（如 `source_novel`、`source_author`、`fidelity_score`）；
  - `style_remix` 模式判断；
  - `StoryEngine` 的 prompt 变量与章节生成语义；
  - “风格实例一定来自 bisheng-style” 这种固定来源假设。

# 2026-04-17 范围收敛
- 用户已确认：不做“所有 skill 的通用框架”，当前只做“小说特定 skill”的通用层。
- 目标对象收敛为两类：
  - 现有小说方法论 skill：`apps/agent-runtime/app/methodology/novel-writer-workflow/SKILL.md`
  - 小说风格实例 skill：`NoteStyle/bisheng-style/SKILL.md` + `instances/*`
- 设计目标调整为：把“小说方法论层 + 小说风格层”统一到同一条发现、解析、触发和运行时注入路线；暂不考虑其他风格、其他领域 skill。

# 2026-04-17 当前进一步结论
- 当前“原来的小说特定 skill”的事实入口，不在 `.agents/skills`，而在 `NoteStyle -> style_profile_service -> style_remix -> StoryEngine prompt` 这条链上。
- `bisheng-style` 与现有小说任务流的同构部分，不是“同一个 skill 执行器”，而是：
  - 实例注册发现；
  - `manifest` / `rules` 读取；
  - 规则分维聚合；
  - 规则摘要编译；
  - 运行时注入。
- 只做小说通用层时，最小公共抽象应收敛为：
  - 小说方法论包（workflow skill）
  - 小说风格包（style skill）
  - 统一的小说 skill 解析器/选择器
  - 统一的小说运行时上下文对象
- 不应泛化的部分包括：
  - `style_remix` 的小说任务语义；
  - 小说九类规则维度；
  - 小说创作协议本身（故事骨架、卷纲/章纲、场景卡、章节自检、失真审校）。

# 2026-04-17 当前推荐设计
- 推荐目标：只做“小说 skill 通用层”，统一两类包：
  - `workflow`：小说方法论包（现有 `novel-writer-workflow`）
  - `style`：小说风格包（现有 `bisheng-style`）
- 推荐核心对象：
  - `NovelSkillPackage`
  - `NovelSkillManifest`
  - `NovelSkillInstance`（仅 `style` 包需要）
  - `NovelSkillResolver`
  - `NovelRuntimeContext`
- 推荐统一原则：
  - `workflow` 是底座，常驻加载；
  - `style` 是叠加层，按实例选择加载；
  - 两者统一发现和解析路线，但不强行合并为单一 skill。
