# 问题标题
旧异常任务恢复与清理机制设计

# 用户原始诉求
开始做旧异常任务的恢复/清理机制。

# 当前状态
已完成：双轨恢复机制已落地，后端与前端提示层均已验证通过，历史旧任务已可自动或手动恢复。

# 当前已知现象
- `task_af31e4c58f`：停留在 `planning / outline-revision`，`pending_review=null`，`story_plan=false`，属于修复前遗留的不可恢复中间态。
- `task_044fcbd442`：停留在 `waiting_chapter_review / chapter-pair-0`，`pending_review_type=chapter_pair_review`，但 `story_plan=false`，属于待审核态与业务快照不一致的脏状态。
- 新链路创建的正式任务已可正常完成，说明当前主流程已恢复，剩余问题集中在历史遗留脏任务的“恢复或清理”策略。

# 当前讨论结论
- 机制目标采用 `双轨`：
  - 自动恢复：服务启动后或任务读取时，对可恢复的历史异常任务自动补齐最近稳定阶段。
  - 手动恢复：保留用户可见的“恢复任务”入口，允许对自动判定失败或用户明确指定的任务手动触发恢复。
- 长篇创作场景下，纯清理方案不满足需求；恢复必须作为主路径，清理仅作为不可恢复任务的兜底。
- 对不可恢复任务，用户选择的落点状态为 `waiting_manual_action`，而不是 `failed`。
- 对手动恢复入口，用户选择 `原任务原地修复并继续`，不创建恢复副本。

# 已实现内容
- 后端新增恢复入口：`POST /api/tasks/{task_id}/recover`
- `TaskService` 已接入按需自动恢复触发点：
  - `get_task`
  - `get_workspace`
  - `get_review`
  - `resume_task`（仅在原任务本身不满足恢复前置时触发）
- 已实现最近稳定阶段恢复：
  - 从 `outline-history / outline-revision-history` 恢复到 `waiting_outline_review`
  - 从大纲历史 + 章节历史恢复到 `waiting_chapter_review`
  - 从历史快照恢复到 `waiting_verification_review`
- 不可恢复任务会转入 `waiting_manual_action`
- 前端工作台页已新增最小手动恢复入口：`恢复任务` 按钮
- 前端 `waiting_manual_action` 已补充展示：
  - 人工处理提示
  - 自然语言恢复原因（`error_message`）
  - 结构化恢复阻塞原因（如 `missing_stable_state`）
