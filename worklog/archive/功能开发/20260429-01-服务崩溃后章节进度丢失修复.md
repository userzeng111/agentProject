# 服务崩溃后章节进度丢失修复

## 问题标题
服务崩溃后，已完成 5 章的任务在恢复后从第 1 章开始重写。

## 用户原始诉求
> 服务掉了，而且有一个问题，我掉了之后再继续任务，他没有回到我已经完成的位置，明明我已经完成了 5 章了，但是竟然从第一章开始重写了。

## 根因分析

### 1. `_mark_failed_unless_stable` 未同步更新 `blocked_from_status`
`core.py:487` 的 `_mark_failed_unless_stable` 在将任务设为 `WAITING_MANUAL_ACTION` 时，只更新了 task JSON，未调用 `update_project_status` 同步设置数据库 `novel_project.blocked_from_status`。导致数据库中该字段为空字符串。

### 2. `_recover_novel_project_state` 对空 `blocked_from_status` 处理不足
`recovery.py:500` 的逻辑：
```python
if task.status is TaskStatus.WAITING_MANUAL_ACTION and project.blocked_from_status:
```
当 `blocked_from_status` 为空时，条件为 False，直接 `return None`。此时 fallback 链会继续往下走。

### 3. fallback 链错误地恢复到待大纲审核
`_recover_task_from_stable_state` 在 `_recover_novel_project_state` 返回 None 后，依次尝试：
1. `_can_recover_outline_review` — 只要 `story_plan` 存在就返回 True
2. `_recover_outline_review` — 将任务恢复到 `WAITING_OUTLINE_REVIEW`

用户重新通过大纲审核后，任务进入 `READY_FOR_BATCH`，但此时 `completed_chapter_count` 可能因项目重建或流程重置而丢失，导致 `continue_task` 中 `completed_count = 0`，`batch_index = 0`，从第 1 章开始生成。

## 修复方案

### Agent A：修复 `_mark_failed_unless_stable` 的 DB 同步
- 在 `set_waiting_manual_action` 后，读取当前 DB project 状态，调用 `update_project_status` 设置 `blocked_from_status=project.status`
- 若 project 不存在，则跳过

### Agent B：增强恢复链路对章节进度的保护
- `_recover_novel_project_state`：增加兜底逻辑，对于 `WAITING_MANUAL_ACTION` 且存在 novel project、有已完成章节（`completed_chapter_count > 0`）且 `story_plan` 存在的任务，即使 `blocked_from_status` 为空也应恢复到 `READY_FOR_BATCH`
- `_preview_recover_to_stable`：同步增加预览逻辑
- `_can_recover_outline_review`：增加判断，如果任务存在 novel project 且有已完成章节，则不应恢复到待大纲审核

### Agent C：补充恢复链路单元测试
- 测试 `_mark_failed_unless_stable` 是否正确设置 `blocked_from_status`
- 测试 `blocked_from_status` 为空但项目有已完成章节时的恢复行为
- 测试 recovery 不应 fallback 到 outline review 当任务已有 approved chapters
