# 当前状态
只读分析完成，未修改业务代码；已确认运行页、审核页与恢复弹窗在“模型失效”和“契约缺失”场景下的剩余风险点，并整理最小补强建议与待验证场景。

# 观察记录
- 运行页和审核页都通过 `/api/models` 拉取模型目录，并仅允许 `gateway + verified` 模型进入任务动作选择列表。
- 恢复弹窗会基于 `recovery_options[].preview.allowed_model_ids` 进一步过滤恢复模型，并在未选中有效模型时禁用确认按钮。
- 运行页与审核页对“当前选中模型已失效”的处理仍包含自动退回到列表首项的逻辑，需继续确认是否形成静默回退风险。

# 当前结论
- 运行页与审核页仍存在静默回退：当任务默认模型或用户先前选择的动作模型不在最新可选列表中时，前端会自动切到列表第一个模型，并直接用于 `run / continue / resume`，没有显式警告或二次确认。
- 恢复链路当前没有同类静默回退：恢复弹窗若默认模型不在允许列表里，会清空选择并禁用确认按钮，这部分防线基本成立。
- 恢复模型过滤仍是 fail-open：`filterRecoveryModels()` 在 `allowed_model_ids` 缺失时直接放行全部候选模型。当前后端通常会返回 allowlist，所以这更像契约破损时的防线缺口，而不是已知必现 bug。
- 运行页与审核页的模型目录只在组件挂载时刷新一次，长开页面期间如果模型下线或兼容性变化，前端不会主动重新校验，最终只能依赖后端在提交时报错。

# 最小修复建议
- 取消运行页和审核页对失效动作模型的“自动选第一个”逻辑；一旦当前任务模型失效，应显式进入“未选择模型 / 当前模型已失效”状态，并阻止提交，要求用户手动确认。
- 恢复模型过滤改为 fail-close：`allowed_model_ids` 缺失、不是数组或对应 preview 缺失时，直接视为“当前动作没有可用模型”，而不是回退成全量可选。
- 在 `run / continue / resume / recover` 提交前补一次轻量目录刷新或本地再校验，至少覆盖长开页面后的模型下线场景。

# 需要验证的场景
- 任务默认模型已失效，但模型目录里仍有其他可用模型时，运行页和审核页不能自动跳到第一个模型。
- 用户手动选择过动作模型后，该模型从目录中消失时，页面应提示“已失效，需要重新选择”，而不是悄悄替换。
- 恢复动作 preview 正常返回 allowlist 时，只能看到 allowlist 内模型；默认模型不在 allowlist 时必须手选。
- 恢复动作 preview 缺少 `allowed_model_ids`、preview 缺失或 action 找不到时，恢复弹窗应 fail-close，不能放出全部模型。
- 页面长时间停留后模型下线，再执行 run / continue / resume / recover 时，前端应在提交前重新校验并给出明确提示。
