## 只读排查结论

- 自动审核模型根因：
  - `AutoReviewPolicy` 语义上支持空字符串表示“跟随任务创作模型”。
  - 当前启动配置把 `auditor_model` 与 `synthesis_model` 默认写成 `MiniMax-M2.7-highspeed`，导致后续 `setdefault()` 不会用动作模型覆盖。
  - 因此用户选择 K2.6 时，创作链路走 K2.6，自动审核链路仍走 MiniMax。
- 前端展示问题：
  - 创建页当前文案是“生成模型”，工作台和审核页展示“任务默认模型/最近一次动作模型”，没有明确展示“创作模型/审核模型”。
  - 创建任务 payload 只有 `model_id` 与 `auto_review`，没有审核模型字段。
- 性能耗时问题：
  - 主要耗时不在普通 API，而在后台大纲生成、章节生成、JSON 解析/重试、自动审核动态 Agent 编排。
  - 自动审核一次通常会放大为 `Master + Planner + 多个分析 Agent + 综合 Agent` 多次 LLM 请求，并发层会增加 CPU/网络压力。
  - 流式接口会及时返回 SSE，但后台需要等上游完整 body 后才能解析 JSON、写历史、保存章节并推进状态，前端因此长时间停留在生成中。
- 缓存命中率问题：
  - 响应缓存 key 是 `model + 完整 request_messages` 的精确哈希。
  - 小说任务每章的章节号、目标、上一章全文、已完成摘要、审核反馈、修订内容都不同，所以 exact-match 响应缓存很难命中。
  - 当前三类任务日志中可见的创作缓存事件均为 `cache_hit=false`。
  - 与 Claude Code 的差异在于 Claude Code 常依赖稳定前缀或 provider prompt cache；当前系统没有对 Anthropic/K2.6 注入 provider prompt cache 控制，只做本地完整响应缓存。
- RAG/Milvus：
  - 当前项目运行态不是 Milvus，而是 FAISS + SQLite。
  - 当前 RAG 状态接口只检查 `index.faiss` 与 `metadata.sqlite3` 是否存在，没有校验 FAISS 与 SQLite doc_id 一致性、维度、源文件 mtime/hash。
  - 因此存在索引陈旧或局部失配但状态仍显示可用的风险。

## 建议实施方案

- 第一阶段：修复模型语义与展示。
  - 后端保留固定审核模型能力，但新增/启用“跟随创作模型”语义。
  - 前端把“生成模型”改成“创作模型”，并在创建页、工作台、审核页展示“审核模型：跟随创作模型/固定模型名”。
- 第二阶段：降低耗时和误判。
  - 给动态审核增加限流/轻量模式配置，避免每次自动审核都扩成过多 Agent 请求。
  - 增加阶段耗时指标，记录 task_id、stage、node、model、首 token、完成、JSON 解析、缓存段 hash。
- 第三阶段：缓存与索引诊断。
  - 增加 cache diff 诊断，拆分稳定段与动态段 hash。
  - 对 Anthropic/K2.6 协议层调研并接入 provider prompt cache 控制。
  - 给 RAG 状态接口增加 FAISS/SQLite 一致性、源文件更新时间与状态文件时间对比。

## 外部瓶颈图谱评估

- 用户提供 Claude Code 侧分析，列出 10 个瓶颈：缓存键逐章变化、全量 checkpoint、任务锁、HTTP Client 新建、全量写盘、状态膨胀、RAG 同步阻塞、恢复重复加载历史、取消阻塞 10 秒、同步端点。
- 本轮定点核对结果：
  - 已证实：响应缓存 key 为 `model + 完整 request_messages`，小说任务几乎必然 miss。
  - 已证实：`gateway_client.py` 每次请求新建 `httpx.Client/AsyncClient`，连接不能复用。
  - 已证实：`WorkflowState.completed_chapters` 保存章节 dict，`accumulate_chapters` 会持续追加，存在 checkpoint 状态膨胀风险。
  - 已证实：`SqliteSaver` 被用于 LangGraph checkpoint，会随节点持久化状态。
  - 已证实：`TaskStore.save()` 会写任务文件、同步 SQLite、写索引；`append_event()` 会重写事件与 trace。
  - 已证实：取消任务请求会 `thread.join(timeout=10)`，请求可阻塞 10 秒。
  - 部分成立：`routes.py` 多数端点为同步 `def`，但这不是当前长耗时主因；重型 LLM 工作已转后台线程，普通 API 目前多为几十毫秒。
  - 需要谨慎：解除任务级锁和章节并发可能破坏章节连续性、审核顺序、恢复一致性，不宜作为早期优化。
  - 需要谨慎：简单排除 `completed_summaries/previous_chapter_full_text` 生成响应缓存 key 会产生错误复用风险，不能直接用于最终 LLM 响应缓存。
- 安全采纳顺序：
  - 先做 HTTP 连接复用、审核模型跟随创作模型、阶段耗时诊断、RAG 状态校验、取消接口非阻塞化。
  - 再做状态瘦身与增量持久化，必须保留人工审核中断、恢复、全文验证和归档完整性。
  - 最后评估章节级并发，仅允许在上下文独立的预计算、RAG 检索或审核分析 Agent 层面并发，正文章节生成仍应默认串行。

## 综合优化方案

- 总原则：
  - 先观测、再优化，避免在没有阶段耗时数据的情况下大改架构。
  - 创作语义优先，章节正文生成默认串行，不能为了吞吐破坏章节连续性。
  - 保留人工审核中断、恢复、取消、归档、全文验证能力。
  - 所有高风险优化都要先有回滚点和测试覆盖。
- Phase 0：安全基线。
  - 已完成数据库与索引备份。
  - 后续改动前补充最小回归用例：任务创建、运行、大纲审核、章节审核、继续生成、取消、恢复、归档。
- Phase 1：低风险高收益修复。
  - 修复自动审核模型语义：默认跟随当前创作模型；固定审核模型作为显式配置保留。
  - 前端展示区分“创作模型”和“审核模型”，避免 K2.6/MiniMax 误判。
  - `gateway_client` 增加可复用 HTTP Client/连接池，减少重复建连。
  - 取消任务不再同步等待 10 秒，改为快速标记取消并异步清理。
  - 增加阶段耗时日志：task_id、stage、node、model、首 token、完成、JSON 解析、持久化耗时。
- Phase 2：缓存与上下文优化。
  - 不直接放宽最终响应缓存 key，避免错误复用章节内容。
  - 增加 cache diff 诊断：system/style/outline/history/current_chapter/reference 分段 hash。
  - 将稳定 prompt 段前置并保持顺序稳定，为 provider prompt cache 做准备。
  - 调研并接入 K2.6/Anthropic 协议的 prompt cache 控制，优先缓存系统提示、风格样例、世界观、大纲等稳定前缀。
  - 减少动态上下文体积：上一章全文改为“摘要优先 + 必要片段”，但需保留质量回退开关。
- Phase 3：状态瘦身与持久化优化。
  - `completed_chapters` 从全文 dict 改为轻量元数据与 artifact ref；全文只存章节文件。
  - checkpoint state 保留恢复必需字段，不再携带整本正文。
  - `TaskStore.save()` 拆分为元数据保存、事件追加、索引刷新，降低每次进度更新的全量写盘。
  - RAG 状态接口增加 FAISS/SQLite doc_id 一致性、索引维度、源文件 mtime/hash 校验。
- Phase 4：受控并发。
  - 不默认并发生成正文章节。
  - 可并发的范围：RAG 检索、上下文预构建、审核分析 Agent、无依赖的诊断任务。
  - 动态审核增加轻量模式与 max_workers 配置，减少一次审核放大为过多 LLM 请求。
- 验收指标：
  - 模型展示：前端明确显示创作模型与审核模型，K2.6 任务不再误显示 MiniMax 为创作调用。
  - 性能：单次非 LLM API 保持毫秒级；取消接口不再固定阻塞 10 秒；日志能拆出每个阶段耗时。
  - 缓存：能看到稳定段 hash 跨章节复用率；最终响应缓存不得错误复用。
  - 状态：长篇任务 checkpoint 体积不随正文全文线性膨胀。
  - 功能：创建、运行、审核、继续、恢复、取消、归档全链路通过。

## 可选实施路线

- 方向 A：稳态修复优先。
  - 范围：修复创作/审核模型语义与展示、HTTP 连接复用、取消非阻塞、阶段耗时日志、RAG 状态校验。

  - 代价：缓存命中和 checkpoint 膨胀只能先观测，无法立刻根治。

  - 特点：直接针对“Claude Code 快、本项目慢”的差异；减少重复 prompt 成本和审核放大。
  - 代价：需要验证 K2.6/网关对 provider prompt cache 的实际支持，且必须避免错误复用内容。
- 方向 C：状态与持久化架构优先。
  - 范围：瘦身 `WorkflowState.completed_chapters`，正文全文改为 artifact ref，checkpoint 不再携带整本正文，`TaskStore.save()` 增量化。
  - 特点：解决长篇任务越跑越慢、SQLite checkpoint 膨胀、恢复变慢等根因。
  - 代价：风险最高，需要完整回归创建、审核、继续、恢复、归档、全文验证。
- 方向 D：吞吐与并发治理优先。
  - 范围：动态审核 max_workers/轻量模式、RAG/上下文预构建并发、后台任务调度队列；正文生成保持默认串行。
  - 特点：适合多任务同时跑时降低 CPU 峰值和请求放大。
  - 代价：对单个章节生成的速度提升有限，更多是稳定性和资源治理。
