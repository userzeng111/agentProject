# 问题标题
前端静态资源 404 排查与修复

# 用户原始诉求
用户在手动测试前端时，浏览器控制台出现大量静态资源 404：
- `main-app.js`
- `webpack.js`
- `app-pages-internals.js`
- `page.js`
- `layout.js`
- `not-found.js`
- `error.js`
- `global-error.js`
- `layout.css`

要求修复。

# 当前状态
已修复并验证：
- 根因已确认：`next dev` 运行中叠加 `npm run build`，污染同一份 `apps/web/.next`。
- 已实施“开发态与构建态产物目录隔离”。
- 已重启前端热更新服务，当前 `http://127.0.0.1:3000` 正常返回。

# 当前已知信息
- 本地当前运行入口：
  - 前端：`http://127.0.0.1:3000`
  - 后端：`http://127.0.0.1:8000`
- 浏览器报错形态更接近“HTML 正常返回，但页面依赖的静态 chunk/css 路径不正确或被错误路由吞掉”。
- 当前 [next.config.mjs](/home/user01/WorkSpace/AgentProject/apps/web/next.config.mjs) 固定配置了 `output: "export"`。
- 通过服务日志确认：`GET /` 返回 `200`，但紧接着对 `/_next/static/css/app/layout.css`、`/_next/static/chunks/app/page.js`、`main-app.js` 等请求持续 `404`。
- `apps/web/.next/static` 目录内确实已有静态产物，说明不是“完全未构建”，而是 dev 服务器对运行态 chunk 路由解析异常。
- 当前最强修复方向：开发态禁用 `output: "export"`，仅在生产导出时启用；随后清空 `apps/web/.next` 并重启前端验证。

## 2026-04-23 增量排查结论
- 当前 [next.config.mjs](/home/user01/WorkSpace/AgentProject/apps/web/next.config.mjs) 已经改成仅在 `NODE_ENV=production` 时启用 `output: "export"`，所以本轮 404 不是由该配置直接触发。
- 当前前端进程实际是 `next dev --hostname 127.0.0.1 --port 3000`，不是 `next start`。
- 当前首页 HTML 引用的是开发态虚拟资源路径：
  - `/_next/static/chunks/main-app.js`
  - `/_next/static/chunks/app/error.js`
  - `/_next/static/chunks/app/global-error.js`
  - `/_next/static/css/app/layout.css`
- 但当前磁盘上的 [`.next`](../../../../apps/web/.next) 里实际存在的是生产构建产物：
  - `static/chunks/main-app-25ff4945274d2d44.js`
  - `static/chunks/app/error-80e26e6faf8e406a.js`
  - `static/chunks/app/global-error-cc93fbcbb096681c.js`
  - `static/css/5d2bdd4f93c229c9.css`
- 同时 [`.next/build-manifest.json`](../../../../apps/web/.next/build-manifest.json) 和 [`.next/app-build-manifest.json`](../../../../apps/web/.next/app-build-manifest.json) 仍保留开发态未哈希路径清单，说明当前 `.next` 已被“开发态 manifest + 生产态静态文件”混写污染。
- 直接结论：
  - 在 `next dev` 运行期间执行 `npm run build`，两者共用 `apps/web/.next`，会把 dev 进程需要的未哈希虚拟资源映射破坏掉，触发这组 `404`。

## 当前推荐处置
- 最小处置：
  - 停掉当前 `next dev`
  - 删除 `apps/web/.next`
  - 重新启动 `next dev`
- 稳定性方向：
  - 开发态与生产构建态不要共用同一个 `.next`
  - 如果后续还需要频繁边跑 dev 边做 `next build` 验证，应拆分 `distDir` 或固定为“先停 dev，再 build，再恢复 dev”的运维流程

## 2026-04-23 已确认实施方向
- 采用“目录隔离 + 立即恢复”：
  - `next dev` 独立使用 `apps/web/.next-dev`
  - `next build` / `next start` 继续使用 `apps/web/.next`
- 这样即使开发态运行中执行构建，也不会再把 dev 服务器的 `_next/static/*` 虚拟资源映射打坏。
