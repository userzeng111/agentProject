# 问题标题
任务动作级模型切换与恢复策略改造

# 用户原始诉求
- 任务在模型切换或生成失败后不能“一次判死刑”，需要更强的恢复与重试能力。
- 每次触发 AI 生成时都应允许切换模型，而不是被创建任务时的单个模型绑定住。
- 首页模型列表需要真正反映后端可用模型，并且刷新页面或显式刷新时应重新获取，而不是长时间停留在旧缓存。

# 当前状态
已完成：
- 后端响应已显式区分 `default_model_id` 与 `last_action_model_id` / `last_action_kind`，不再要求前端通过单一 `model_id` 猜语义。
- `TaskRecord`、`TaskSummary`、`WorkspaceResponse.request_preview` 以及 tasklog 的 `index/meta/request` 投影均已补齐上述字段。
- 前端运行页、审核页、归档列表/详情页已明确展示“任务默认模型”和“最近一次动作模型”；动作选择器初始化只绑定默认模型，不再使用最近动作模型回填。
- 创建页“从旧任务重试创建”已改为优先继承任务默认模型，不再误继承最近一次动作模型。
- 已完成定向验证：`apps/agent-runtime` 下 61 个相关单测通过，`apps/web` 的 `npm run build` 通过。

# 当前遗留
- 无。此前衍生出的 `start.sh` 启动问题已拆分到独立问题单并完成修复。

# 初步关注点
- `run/resume/continue/recover` 是否都应支持动作级 `model_id` 覆盖。
- 小说任务模型兼容性校验是否在每次动作前都执行。
- 首页模型列表是否需要区分“实时网关模型”和“聚合模型目录”，以及前端刷新触发时机。
