# 问题标题
镜中人固定章节锚点恢复设计

## 用户原始诉求
用户要求“镜中人恢复”不要按原始输入重新开始，而是基于数据库中的大纲、已写章节和失败位置，恢复到之前的固定节点继续执行。

用户举例说明：如果小说在编写第四章时出问题，后续再次进入恢复时，应恢复到第四章对应节点，而不是重新创建整本小说。

## 当前状态
已完成一轮实现与定向验证，尚未归档。

## 当前讨论要点
- 现有“恢复”语义是否混入了“按原始输入重新开始”。
- 当前数据库与任务快照是否足以识别“已完成到第几章、卡在第几章/哪一批”。
- 恢复锚点应绑定章节节点、章节批次，还是审核阶段节点。
- 需要输出一版可落地的恢复流程与最小持久化约束。

## 当前只读结论
- 现有恢复动作已明确分成两条：
  - `recover_to_stable`：回填最近稳定阶段；
  - `restart_from_input`：按原始输入重新开始。
- 当前后端恢复合同构建入口位于 `apps/agent-runtime/app/application/task_service.py`：
  - `_preview_recover_to_stable()`
  - `_preview_restart_from_input()`
  - `_build_recovery_contract()`
- 当前“稳定态恢复”更偏向恢复到审核/批次状态，而不是直接表达“从第 N 章继续写”：
  - `_recover_outline_review()`
  - `_recover_chapter_review()`
  - `_recover_verification_review()`
  - `_recover_novel_project_state()`
- 当前数据库其实已经具备章节锚点基础信息：
  - `NovelProject`：`completed_chapter_count`、`next_chapter_number`、`active_batch_no`、`blocked_from_status`
  - `NovelGenerationBatch`：`actual_start_chapter`、`expected_end_chapter`、`persisted_count`、`actual_end_chapter`、`status`
  - `NovelOutlineChapter`：`chapter_number`、`status`、`batch_no`、`md_ref/json_ref`、`content_hash`、`file_size`
- 当前章节正文还会落盘到 `tasklog/runs/<task_id>/chapters/<NN>.json`，并由 `get_current_chapters()` 读取，因此“已写到第几章”原则上可以通过 DB + 章节文件双重回探。
- 当前缺的不是底层持久化，而是“恢复目标语义”和“恢复决策规则”：
  - 现在系统更容易说“恢复到待章节审核”或“恢复到待验证审核”；
  - 但用户要的是“如果第 4 章出问题，就回到第 4 章对应固定节点继续”，这需要把章节号映射成明确恢复节点。

## 新增讨论结论
- 用户选择恢复口径为：
  - 若目标章节正文已稳定落盘，则恢复到“该章节/该批次待审核”；
  - 若未稳定落盘，则恢复到“该章节待生成”，而不是整本重开。
- 当前实现里，继续创作和章节审核恢复都会把 `completed_chapters` 重新灌回生成链路。
- 这意味着：如果已经完成前三章，那么生成第四章时，当前实现原则上会把前三章正文一起作为 `completed_chapters` 传入。
- 该设计在前几章问题不大，但对长篇场景存在明显 token 增长风险；章节越多，恢复和续写越重。
- 后续方案设计需要单独回答：
  - 哪些历史章节必须全文带入；
  - 哪些只能以摘要/结构化记忆带入；
  - 在“上下文连续性”和“token 成本”之间如何设定默认策略。

## 用户新增口径
- 用户补充约束：
  - 更早章节不要默认带摘要；
  - 摘要仅用于“近 20 章”范围；
  - 需要兼容短篇小说场景，不能按长篇方案硬套。
- 用户进一步确认：
  - 恢复第 4 章时，可以带第 3 章全文；
  - 该口径优先保障相邻章节衔接质量。
- 新的讨论重点变为：
  - 主流 Agent 工具如何做上下文压缩；
  - `Codex` / `Claude Code` 是否会自动压缩传给 LLM 的上下文；
  - 这些机制对当前小说恢复方案有什么可借鉴之处。

## 本轮已实现
- 后端恢复预览已支持章节级语义：
  - `target_chapter_number`
  - `target_chapter_numbers`
  - `target_batch_no`
  - `reuse_existing_draft`
- `recover_to_stable` 预览在“继续创作失败、应恢复到固定章节继续”场景下，已可明确展示：
  - `恢复到第 N 章待生成`
  - `恢复到第 X-Y 章批次待生成`
  - `恢复到第 N 章待审核`
- 小说项目表已新增并接入 `current_generating_chapter_number`，用于记录当前实际生成到哪一章。
- 继续创作链路已在失败回退时保留目标章节锚点，不再只能表达抽象的“稳定态恢复”。
- 章节生成上下文已调整为：
  - 带上一章全文；
  - 已完成章节摘要只保留最近 20 章；
  - 若存在目标章节历史草稿，则带入 prompt。
- 前端恢复弹窗已支持展示：
  - 目标章节/章节范围；
  - 目标批次号；
  - 是否复用已有历史草稿。

## 当前已知边界
- 本轮重点落地的是“固定章节锚点恢复语义”和“恢复时上下文装配规则”，没有引入新的独立恢复模式枚举。
- 当前“恢复到第 N 章待生成”在内部仍通过 `READY_FOR_BATCH -> continue_task()` 落地，而不是新增一个独立任务状态。
- 更细粒度的“第 4 章生成到一半、精确恢复到半章游标”本轮仍未实现；当前粒度稳定到“章节级/批次级”。

## 只读分析结论（2026-04-23）
- 当前仓库已经有“固定章节节点恢复”的基础，但粒度主要是“稳定阶段 + 批次边界”，还不是“失败到第 N 章”的强约束恢复。
- SQLite 中的 `novel_project`、`novel_generation_batch`、`novel_outline_chapter` 已经能判断：
  - 已审核通过多少章；
  - 下一章应从哪一章开始；
  - 当前活动批次原计划覆盖哪些章节；
  - 哪些章节文件已经落盘且是否通过哈希校验。
- `TaskRecord.pending_review` 与 `context/drafting/chapter-xx-history.json` 能补足审核态和图恢复所需的章节内容，但仍偏运行态补水，不是单独的数据库单点真相。
- 当前“恢复到稳定阶段”主要会回到：
  - `waiting_outline_review`
  - `waiting_chapter_review`
  - `waiting_verification_review`
  - `ready_for_batch`
- 如果要严格实现“第四章出问题，下次恢复直接回到第四章对应节点，而不是整本重开”，最小约束应至少保证：
  - 大纲章节计划已入库，且每章有稳定 `chapter_number`；
  - 每次继续创作先落批次边界：起始章、预期结束章、有效章数、已持久化章数；
  - 每章落盘后立即写入章节表，记录批次号、文件引用、内容哈希、产物状态；
  - 小说项目表持续维护 `completed_chapter_count`、`next_chapter_number`、`active_batch_no`、`blocked_from_status`；
  - 恢复入口禁止重新推导批次范围，只能恢复已持久化的活动批次。
