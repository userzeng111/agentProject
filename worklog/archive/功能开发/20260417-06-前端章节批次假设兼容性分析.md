# 问题标题
前端章节批次假设兼容性分析

# 用户原始诉求
只读分析前端和任务展示层面对章节批次的假设。重点看 workspace/review/result/archive 页面、types、SSE 事件里是否默认两章一批。输出：哪些 UI/类型必须一起改，哪些可以保持兼容。不要改代码。

# 当前状态
进行中：已完成只读排查，确认 `review` 页与章节审核类型命名存在显式“双章一批”假设；`workspace/result/archive` 页大多可继续兼容任意批次大小，但会透传后端事件文案与 `current_unit` 中的 `chapter-pair-*` 表达。

# 当前结论
- `apps/web/src/features/task-review/task-review-client.tsx` 明确以 `chapter_pair_review`、`chapter_pair`、`pairNumber = Math.floor(batchIndex / 2) + 1`、`batchIndex + 2` 计算与文案展示为核心，是前端最需要联动修改的区域。
- `apps/web/src/lib/types.ts` 中 `ReviewResponse` 与后端 `ReviewPayload` 使用 `chapter_pair*` 命名，属于接口语义层面的双章假设；若要从“章节对”升级为“任意章节批次”，前后端类型最好一起调整。
- `workspace` 页本身没有按 2 章分组计算进度，它主要依据 `chapter.*` 事件逐章展示；但会直接显示后端生成的 `current_unit=chapter-pair-*` 与 `review.waiting`/`trace.summary` 文案，因此展示语义会继续暴露“双章一批”。
- `result` 与 `archive` 页按单章索引渲染，不依赖批次大小；只要后端继续输出章节列表，这两页可以基本保持兼容。
