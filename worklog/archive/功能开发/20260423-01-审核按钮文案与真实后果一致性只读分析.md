# 问题标题
审核按钮文案与真实后果一致性只读分析

# 用户原始诉求
- 只读检查 `apps/web/src/features/task-review/task-review-client.tsx` 与相关后端返回路径，分析“审核按钮文案与真实后果一致性”当前还差什么，不改代码。
- 输出：
  - 按钮文案与真实后果不一致的点
  - 最小修复建议
  - 需要验证的场景

# 当前状态
已完成只读核查，确认当前仍有 3 处按钮文案与真实后果存在不一致或条件性不一致；尚未修改代码。

# 初步关注点
- 前端审核页按钮文案是否准确反映点击后的状态推进、接口副作用与跳转落点。
- 后端审核提交接口返回的 `next_action`、`redirect_path`、状态字段与前端提示文案是否一致。
- 不同审核结论（通过、驳回、进入修复、进入下一阶段、完成）是否存在同文案多后果或同后果多文案。

# 只读结论
- `POST /api/tasks/{id}/resume` 当前不返回显式 `redirect_path` 或 `next_action`；前端完全依据返回的 `status` 跳转：
  - `completed` -> 结果页
  - `approved && ready_for_batch` -> 工作台
  - `waiting_*_review` -> 留在审核页刷新
  - 其他状态（如 `planning` / `drafting`）-> 工作台
- `大纲审核` 的通过按钮当前文案是“通过并进入继续创作”。实际后果不是立即继续生成正文，而是把任务置为 `ready_for_batch` 并跳回工作台，等待用户再次点击“继续创作”。该文案轻度超前，容易让人误解为点击后会直接开写。
- `章节批次审核` 的通过按钮当前文案是“通过并返回继续创作”。实际后果分两种：非最后一批时返回工作台等待继续创作；最后一批时直接进入 `waiting_verification_review` 并停留在审核流中。因此该文案存在条件性失真。
- `章节批次审核` 的拒绝按钮当前文案是“拒绝并修订”。实际后果是把任务置回 `ready_for_batch` 并返回工作台等待用户再次发起继续创作，不会在本次点击后立即进入自动修订。
- `验证审核` 的通过按钮当前文案是“通过并生成正文”。实际后果是先把任务置为 `drafting/verification` 并跳回工作台，由后台线程继续收尾，最终才进入 `completed`；正文在此前已经生成完成，该按钮不会再触发“生成正文”。

# 最小替换建议
- `大纲审核` 通过：建议改为“通过并返回工作台”或“通过并进入可继续创作”。
- `章节批次审核` 通过：
  - 若坚持最小改动面，只改成“通过并进入下一步”即可。
  - 若允许加一条条件判断，更推荐按是否最后一批动态显示：
    - 非最后一批：`通过并返回工作台`
    - 最后一批：`通过并进入全文验证`
- `章节批次审核` 拒绝：建议改为“拒绝并返回工作台重写本批”或同等不暗示“立即自动修订”的文案。
- `验证审核` 通过：建议改为“通过并完成任务”或“通过并提交完成”，避免“生成正文”。

# 建议验证场景
- 大纲审核通过：确认点击后状态变为 `ready_for_batch`，页面跳到工作台，且未自动发起章节生成。
- 章节批次审核通过（非最后一批）：确认点击后状态变为 `ready_for_batch`，页面跳到工作台。
- 章节批次审核通过（最后一批）：确认点击后状态变为 `waiting_verification_review`，页面刷新为验证审核，而不是回工作台。
- 章节批次审核拒绝：确认点击后状态变为 `ready_for_batch`，页面跳到工作台，且未自动进入章节修订执行态。
- 验证审核通过：确认点击后先进入 `drafting/verification` 并跳到工作台，后台收尾完成后再进入 `completed`；全程不应重新生成正文。
