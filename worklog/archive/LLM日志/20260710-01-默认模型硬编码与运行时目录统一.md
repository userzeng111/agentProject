# 默认模型硬编码与运行时模型目录统一

## 用户原始诉求

用户要求盘点并统一系统中写死的默认模型与默认调用：相关默认值应留空，模型可用性以供应商 API `/models` 返回的模型为准；并基于已成功解析白鹿 usage 的链路修复相应功能。

## 当前状态

已完成修复与验证，等待用户进行界面测试并确认是否收口；在确认前保持 active，不归档、不提交。

## 已确认事实

- 当前 `.env` 的 `DEFAULT_CHAT_MODEL=mimo-v2.5-pro` 不在白鹿 `/models` 实测返回的 34 个模型中，真实调用返回 HTTP 400 `invalid_model`。
- 白鹿 `bailu-2.7-free` 已实测可调用，并返回可被系统解析、落盘和聚合的 usage；它仅作为验证样本，不应被替换为新的写死默认值。
- 后端设置、动态 Agent、自动审核、任务恢复、聊天服务和前端模型选择中均存在模型字符串默认值或“可用列表第一项”回退。
- `ModelCatalogService` 当前会把本地 registry 中未由网关返回的模型补入 API 结果；这与“以供应商 API 模型为准”不一致。
- 前端创作页与聊天页当前会在无选择时自动选择首个可选模型；这与“默认模型留空”不一致。
- 白鹿 `/models` 的真实模型项含有 `context_length` 和 `max_tokens`，可直接作为模型上下文窗口与最大输出的运行时来源。
- 当前 `ModelCatalogService` 实测聚合为 34 个 `gateway` 模型和 14 个 `registry` 模型；小说任务已验证标记仅落在本地 registry 模型，导致供应商当前返回的模型不能自然进入创作任务选择。
- `tasklog/settings.json` 还持久化了 `bailu-2.7-free` 作为运行时默认模型，说明除了环境变量外，还存在跨重启的默认模型来源。

## 待确认设计决策

- 用户已选择 A：不允许用户持久化默认模型；配置、运行时设置和前端初始选择均保持为空。
- 在没有用户显式选择时，创作任务、聊天和动态审核均必须拒绝调用，而不是自动选择 API 返回列表的第一项。

## 预期验收

- 配置文件、后端和前端不再以固定厂商模型 ID 作为运行时默认调用值。
- `/api/models` 的可选模型集合仅来自当前供应商接口；本地 capability registry 只做已返回模型的补充元数据。
- 新任务使用白鹿 API 已返回模型执行后，LLM 摘要显示真实输入、输出和总 token。

## A 方案设计

- API 目录为模型 ID 的唯一来源：`ModelCatalogService` 只保留当前配置网关 `/models` 返回的条目；本地 registry 和能力配置只能为同 ID 的 API 条目补充显示、协议或兼容性元数据，不能新增可选模型。
- 供应商无关的能力解析：统一识别常见的 `context_length`、`context_window`、`max_context_length`、`max_input_tokens`、`max_output_tokens`、`max_tokens` 及其嵌套字段，并记录实际字段路径。接口返回的上下文窗口和输出上限优先于本地通用降级值，不能覆盖 API 值。
- 不保留全局或运行时默认模型：清空 `DEFAULT_CHAT_MODEL`、自动审核默认模型和 `tasklog/settings.json` 的历史默认值；移除默认模型设置接口与首页默认模型选择卡片。
- 调用前必须有显式模型：创建任务、聊天、动态 Agent、审核、恢复和继续任务均只使用用户选择或任务已保存的模型。模型缺失或不再出现在当前 API 目录时返回明确错误，并要求用户手动选择当前在线模型。
- 保留小说任务兼容性验证：因为供应商目录包含图像、视频等非文本模型，API 返回仅代表可见/可调用，不自动代表可用于小说工作流。验证状态只能作用于当前 API 目录中的模型，不能让 registry 独立模型进入选择列表。
- 前端不再自动选择第一个模型：创作、聊天和恢复选择器初始为空；刷新后仅保留仍在 API 目录中的用户选择，失效即清空并禁用提交。
- 回归与验收：新增 API-only 目录、无默认调用、上下文 API 优先、旧任务模型失效、前端无首项回退、真实 usage 聚合的测试；最后使用当前配置供应商 API 返回且通过兼容性验证的模型跑一个新任务，确认 LLM 摘要 token 为非零。

## 用户补充边界（2026-07-10）

- 白鹿 API 与 `bailu-2.7-free` 只用于本次真实接口验证，不得成为运行时默认值、内置模型列表、供应商专用分支或测试中的固定生产依赖。
- 后续用户可能切换其他供应商 API；模型目录、模型能力、上下文窗口、最大输出与可用性必须随当前配置的接口动态刷新。
- 真实集成验收模型由显式测试参数或当前用户选择提供，代码不能自动选择白鹿或任何其他供应商的固定模型。

## 执行计划（已获用户“执行”确认）

1. 先补后端失败测试：API-only 模型目录、通用 provider limit 映射、空模型拒绝、旧任务模型失效时不回退默认模型。
2. 再补前端失败测试：创建任务、聊天和模型刷新均保持空选择，不得自动取目录第一项；首页不再写入全局默认模型。
3. 实施后端：移除配置/持久化/运行时默认模型，目录只保留 API 返回条目，通用解析接口能力字段，并让任务、聊天、动态审核使用显式模型。
4. 实施前端：删除全局默认模型切换，保留按任务、聊天和恢复动作的显式选择与失效提示。
5. 执行定向、全量、静态检查与接口冒烟；使用显式集成测试模型对当前供应商做真实 token 摘要验证。集成模型不得写入代码或配置默认值。

- 任务、聊天、动态编排与自动审核均已改为显式模型；聊天和动态编排在动作入口强制刷新目录校验。

## 补充收敛设计（执行中）

- 规格审查确认 `default_model_id` 仍作为任务 API 与前端调试数据的兼容别名，会掩盖错误的默认模型回退。该字段不再作为运行时输出或前端读取来源。
- 任务创作模型统一使用 `model_id` 与 `creative_model_id`；恢复预览改为 `creative_model_id`。历史 tasklog 中的旧字段只按旧数据容忍读取，不再重新写出。
- 先以 API/前端回归测试约束“响应不含 default_model_id、展示仅取任务创作模型”，再迁移后端序列化、前端类型与调用方，并复跑接口和 E2E 测试。

## 审查发现与修复边界（2026-07-10）

- 历史 tasklog 的 `task.json`、`state/task.json`、`meta.json`、`request.json` 可能仍包含 `default_model_id`；当前加载逻辑只把旧字段映射到内存中的 `model_id`，不会回写规范化文件，导致调试文件接口仍可展示旧字段。
- 任务摘要、工作台和恢复预览属于读取路径，却通过 `_resolve_task_model_id()` 和自动审核策略走了当前模型目录的严格校验。历史任务保存的模型下线或为空时，页面会在读取阶段失败，用户无法进入工作台重新选择在线模型。
- 执行路径保持严格校验：创建、运行、续写、恢复等操作仍必须由当前供应商目录中已兼容验证的显式模型执行。读取路径只展示任务中保存的模型 ID，不触发目录验证。
- `RecoveryPreview.creative_model_id` 与 `TaskSummary.creative_model_id` 将兼容读取旧响应中的 `default_model_id`，但序列化只输出新字段。
- 审查还发现旧的固定自动审核策略若仅保存 `auditor_model` 或 `synthesis_model`，此前不会在执行前逐项验证；本轮将对最终参与固定审核的两个模型都执行当前供应商目录和小说兼容性校验，避免历史配置绕过模型来源约束。
- 后续规格审查补充两项：旧 API 动作请求中的 `default_model_id` 也应作为显式模型入站兼容字段；恢复已有 checkpoint 时必须校验 checkpoint 内真正会被图节点使用的固定审核模型，不能只校验任务创作模型。
