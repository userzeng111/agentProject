# 上下文管理器与缓存压缩规划

## 用户原始诉求

采用 agent team 模式规划并分配一个新的实现任务：为当前小说 Agent 项目实现上下文功能，参考某个开源框架和官方教程实现上下文管理器，同时开启缓存功能，实现上下文管理与上下文压缩；另外在获取模型列表时，也需要同步获得这些模型可用的上下文能力信息。方案由助手自行决定。

## 初始问题拆解

- 需要先确定“上下文功能”参考哪一个开源框架与官方教程，优先选择与现有 `LangChain + LangGraph + FastAPI + Next.js` 架构兼容的路线。
- 需要明确上下文管理器最小职责：
  - 多轮任务上下文装载
  - 文件化持久化与读取策略
  - 缓存命中与失效
  - 压缩/摘要策略
  - 模型上下文能力元数据采集
- 需要评估“模型上下文能力”来源：
  - 网关返回模型元数据
  - 本地静态映射
  - 启动时探测/官方文档映射
- 需要输出可执行的实现方案、模块边界、数据流、页面影响与阶段落地顺序。

## 当前规划结论

### 推荐框架路线

- 短期上下文使用 `LangGraph checkpointer`，负责线程级工作流状态恢复。
- 长期上下文使用 `LangGraph store` 思路，但在当前项目里优先落为 `tasklog/context` 文件化持久化，保证可审计、可回放、可前端查看。
- 上下文压缩采用“消息裁剪 + 结构化摘要 + 分层降载”的组合方案，不直接暴露原始思维链，只保留可展示摘要流。
- 缓存采用多层策略：
  - 模型目录与能力画像缓存
  - 素材摘要缓存
  - 上下文装配结果缓存
  - embedding/cache 能力作为后续阶段扩展
- 模型上下文能力不完全依赖 `/models`，而是采用“网关模型列表 + 本地能力注册表 + 运行时覆盖项”的聚合方式。

### 与当前仓库的兼容性判断

- 当前 `main_graph.py` 已使用 `MemorySaver()`，说明项目已经具备接入 LangGraph memory/checkpointer 机制的基础。
- 当前 `task_store.py` 已承担任务日志与归档输出，适合作为 `context/` 文件化存储的落点。
- 当前 `story_engine.py` 仍以 `reference_text` 整段拼接方式投喂模型，缺少预算控制、压缩、缓存与上下文包封装，后续需要解耦。
- 当前 `/api/models` 只是透传网关模型列表，未包含上下文窗口、缓存能力、输出预算等信息，需要新增能力元数据层。

### 推荐模块边界

- 保持现有主链：`TaskService -> Graph -> StoryEngine`。
- 新增 `app/context/` 目录，建议拆分：
  - `models.py`：上下文快照、压缩记录、预算、模型能力画像
  - `manager.py`：上下文管理器统一入口
  - `assembler.py`：装配任务输入、素材、大纲、章节摘要
  - `compressor.py`：摘要压缩与降载策略
  - `cache_store.py`：L1/L2 缓存封装
- 新增 `app/llm/model_catalog.py`：
  - 聚合 `/models`
  - 补齐模型能力画像
  - 输出前端可消费的模型能力信息

### 推荐数据流

1. `run_task` 启动任务
2. 图执行进入 `prepare_outline_context`
3. `ContextManager` 根据模型能力和预算装配 planning 阶段上下文
4. `StoryEngine.build_story_plan()` 消费 `ContextPacket`
5. 审核通过后进入 `prepare_draft_context`
6. `ContextManager` 基于大纲、参考素材、章节滚动摘要装配 drafting 阶段上下文
7. `StoryEngine.generate_draft()` 消费 `ContextPacket`
8. 每一轮上下文快照、压缩结果、缓存命中结果写入 `tasklog/.../context/`

### 上下文压缩策略

- 第一级：保留最近高价值内容，裁剪低价值历史消息。
- 第二级：把较早历史折叠为结构化摘要，重点保留人物、世界观、剧情线、风格约束。
- 第三级：超限时只保留主线摘要、角色状态、禁忌要求和必要素材命中片段。
- 对上传小说素材，不直接全量拼接，而是拆分为：
  - 原始素材
  - 素材摘要
  - 召回片段

### 缓存策略

- L1：进程内 TTL cache
  - 适合模型列表、能力画像、摘要结果
- L2：文件缓存
  - 适合上下文包、压缩产物、阶段摘要
- 缓存键建议：
  - `task_id + stage + model_id + context_hash + profile_version`

### 模型能力信息规划

- `/api/models` 维持 `{ data: [...] }` 兼容形态。
- 每个模型对象补充：
  - `display_name`
  - `provider`
  - `capabilities.context_window`
  - `capabilities.cache`
  - `capabilities.features`
  - `metadata.source`
  - `metadata.profile_version`
- 前端创建任务页可直接展示：
  - 上下文窗口
  - 是否启用运行时缓存
  - 是否可能触发压缩

## 2026-03-31 调研记录

### 当前仓库实现现状

- 仓库中不存在字面路径 `agent-runtime/web`，当前相关代码实际分布为：
  - 后端运行时：`apps/agent-runtime`
  - 前端消费层：`apps/web`
- `apps/agent-runtime/app/api/routes.py` 当前暴露 `/api/models`，仅直接返回 `task_service.list_models()` 的结果，没有上下文能力、缓存命中信息或压缩状态字段。
- `apps/agent-runtime/app/application/task_service.py` 负责：
  - 任务创建、运行、恢复、归档视图组装
  - 通过 `thread_id=task_id` 调用 LangGraph
  - 将 LangGraph 状态同步回 `TaskLogStore`
  - 生成 dashboard 的 `model_summary`
- `apps/agent-runtime/app/graph/main_graph.py` 已经使用 LangGraph checkpointer，并以 `MemorySaver()` 作为当前内存级检查点存储；`review_outline` 通过 `interrupt()` 暂停，恢复时依赖同一个 `thread_id`。
- `apps/agent-runtime/app/storage/task_store.py` 当前承担任务文件化持久化，核心是 `tasklog/runs|archive/<task_id>/...`，但保存的是任务快照、事件、结果与工件，不保存 LangGraph 检查点，也没有独立上下文快照结构。
- `apps/agent-runtime/app/llm/story_engine.py` 当前上下文拼装方式较轻：
  - 请求上下文主要来自 `normalized_spec`
  - 外部素材被合并为单个 `reference_text`
  - 章节生成时只传已完成章节摘要，不存在独立上下文装配、压缩或预算控制层
- `apps/agent-runtime/app/llm/gateway_client.py` 当前 `/models` 仅透传兼容 OpenAI 的模型列表，默认只能拿到 `id/object/owned_by` 这一类基础字段。
- `apps/web/src/lib/api.ts` 与 `apps/web/src/features/task-create/create-task-client.tsx` 当前仅把模型列表作为下拉选项消费，默认字段模型为 `id`；尚未定义上下文能力字段或展示位。

### 第三方文档核对结论

- LangGraph 官方文档确认：
  - `thread_id` 是检查点线程的主键；复用同一 `thread_id` 会恢复同一线程状态。
  - `interrupt()`/`resume()` 依赖 checkpointer 才能跨调用恢复。
  - 当前项目虽然已具备 HITL 基础形态，但 `MemorySaver()` 只适合进程内短期状态，不适合需要跨重启恢复的正式上下文管理。
- LangGraph 官方文档确认可在 graph compile 时挂载 `cache`，并在节点级声明 `CachePolicy(ttl=...)`；缓存键默认基于节点输入哈希，也支持自定义 `key_func`。
- OpenAI 官方文档显示 `/v1/models` 主要提供模型基础清单，不保证返回上下文窗口、最大输入/输出 token、结构化输出、工具调用等完整能力元数据；因此“模型上下文能力”不能只依赖该接口，必须补一层能力元数据整合。

### 当前判断

- 上下文管理器不应直接塞进 `StoryEngine`，否则会把“上下文装配”“模型能力预算”“压缩策略”“缓存命中策略”混入提示词生成逻辑。
- 更合适的边界是在 `TaskService -> Graph 节点 -> StoryEngine` 之间增加独立上下文层，让 `StoryEngine` 继续只关心“拿到已装配好的 prompt 输入后调用模型”。
- 模型列表接口后续需要升级为“模型基础信息 + 能力元数据 + 默认预算建议”的复合返回，但应保持兼容旧前端仍可只读 `id`。
