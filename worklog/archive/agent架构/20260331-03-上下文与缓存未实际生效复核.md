# 上下文与缓存未实际生效复核

## 用户原始诉求

用户反馈当前程序虽然已经实现了“上下文管理器”和“缓存”相关代码，但实际请求表现看起来仍然是单次独立请求，没有形成类似 `q1/a1/q2/a2/.../qn` 的连续上下文，也没有观察到缓存命中与复用，因此要求复核代码实现是否只是“有结构、无真实生效”。

## 当前状态

已完成根因复核并进入修复实现，当前修复后的代码与验证已完成，尚未收口归档。已验证：

- 上下文是否真的进入模型请求
- 上下文是否只是“任务阶段上下文”，而不是多轮消息历史
- 缓存是否只是进程内写入，但没有跨请求、跨轮次复用
- SSE/工作台展示的上下文状态是否只是快照，不代表真实命中

## 初始复核重点

- `main_graph.py` 中的 `prepare_outline_context` / `prepare_draft_context` 是否只服务于单个任务阶段，而不承载多轮对话消息历史。
- `story_engine.py` 是否仍然按“单次 prompt -> 单次 JSON 返回”的方式调用模型，而不是 `messages` 累积对话。
- `ContextManager` 的 `InMemoryCacheStore` 是否仅限当前进程和相同 cache key 命中，无法支撑用户感知到的“历史上下文”。
- 当前 `TaskService` / `TaskStore` 是否只把上下文快照落盘用于审计和展示，并未把历史 `Q/A` 回灌到下一次请求。

## 本轮只读复核结论

- 当前缓存 key 由 `task_id + stage + instruction + model_profile + references + memory_items` 序列化后做 `sha256` 得到，因此只有“同一任务、同一阶段、同一模型画像、同一参考材料、同一记忆条目、同一指令文本”再次调用 `build_snapshot()` 时才可能命中。
- 缓存实体是 `InMemoryCacheStore` 内部字典，默认 TTL 300 秒，只存在于当前 Python 进程内；`TaskStore` 落盘的是 `context/.../*.json` 快照文件，不是缓存存储本身，也没有在启动时回灌到 `ContextManager`。
- 从正常业务路径看，`build_snapshot()` 仅在 `prepare_outline_context` 和 `prepare_draft_context` 各调用一次；普通用户流程里通常不会对同一 `task_id + stage` 再次构建完全相同的快照，所以实际几乎看不到命中。
- 因为 key 包含 `task_id`，所以天然不能跨任务复用；因为缓存不持久化，所以不能跨重启复用；因为只在图执行阶段读取，而工作台接口仅读取落盘快照，所以“跨请求可见的缓存复用”也基本不存在。
- 因此如果用户的体感是“没有缓存”，从产品体验上基本成立；更准确地说，当前只有一个短生命周期、进程内、阶段快照级别的 memoization，而不是用户可感知的结果缓存或跨任务上下文缓存。

## 当前状态更新

- 已确认缓存实现真实存在，但命中窗口极窄，且主要收益点停留在“避免同进程内重复装配相同上下文快照”。
- 已确认工作台展示的 `context_status.cache_hit` 来自落盘快照字段，不代表当前请求再次访问了运行时缓存。
- 尚未进入修复设计与改码阶段，维持讨论状态。

## 复核结论

### 1. 用户关于“没有 q1/a1/q2/a2/.../qn 多轮上下文”的判断成立

- 当前 `StoryEngine` 的三个 prompt 模板都固定为：
  - 一个 `system`
  - 一个 `human`
- 代码位置：
  - `story_engine.py:32-80`
  - `story_engine.py:105-121`
  - `story_engine.py:176-225`
- `context_packet` 被塞进的只是字符串字段：
  - `context_memory`
  - `reference_excerpt`
- 这不是多轮消息历史，也没有把上一轮模型输出作为下一轮 `assistant` 消息回灌。

### 2. 当前“上下文”本质上是阶段性摘要包，不是会话历史

- `prepare_outline_context` 构造的是：
  - 当前任务说明
  - 上传素材压缩结果
  - planning 阶段为空的 `memory_items`
- `prepare_draft_context` 构造的是：
  - 当前正文任务说明
  - `story_plan` 派生出的世界观 / 人物 / 章节计划摘要
- 代码位置：
  - `main_graph.py:60-75`
  - `main_graph.py:103-118`
  - `main_graph.py:231-257`
  - `main_graph.py:260-273`
- 这说明现在的“上下文”是“任务阶段输入摘要”，不是“对话轮次历史”。

### 3. 用户关于“每次看起来像单独请求”的判断成立

- `TaskService._initial_state(...)` 每次工作流启动只塞入：
  - 当前 `input_payload`
  - 当前 `reference_text`
  - 当前 `source_assets`
- 没有历史 `Q/A messages` 字段。
- 代码位置：
  - `task_service.py:257-274`
- `review` 恢复也只是走 `Command(resume={approved, comment})`，并没有把历史对话消息整理成下一轮 prompt。
- 因此现在是：
  - 任务级单次 planning 请求
  - 审核后单次 drafting 请求
  - 章节内多次生成请求
- 但不是用户感知里的连续多轮会话。

### 4. 用户关于“没有缓存”的体验判断也基本成立

- 当前缓存只有 `InMemoryCacheStore`，是纯进程内 TTL 字典。
- 代码位置：
  - `cache_store.py:15-41`
- 命中条件非常苛刻：
  - `task_id`
  - `stage`
  - `instruction`
  - `model_profile`
  - `references`
  - `memory_items`
  全部完全一致才会命中。
- 代码位置：
  - `manager.py:37-48`
  - `manager.py:77-97`
- 这意味着：
  - 不跨进程
  - 不跨重启
  - 不跨任务
  - 同一任务只要内容有一点变化就不会命中
- 实际工作流里 `planning` 和 `drafting` 基本只各调用一次，天然缺少第二次相同请求，因此用户几乎感知不到缓存收益。

### 5. 当前落盘的是“上下文快照展示”，不是“缓存回灌”

- `TaskService._sync_result(...)` 只是把 `outline_context_snapshot` / `draft_context_snapshot` 写入文件。
- `TaskStore.write_context_snapshot(...)` 只是写 JSON。
- `get_workspace()` 再把这些 JSON 读出来生成 `context_status` 给前端展示。
- 代码位置：
  - `task_service.py:279-353`
  - `task_store.py:303-317`
  - `task_service.py:181-193`
- 这条链路是：
  - 先调用模型
  - 再写快照
  - 再前端展示
- 不是：
  - 从历史上下文仓库读取
  - 参与下一次请求
  - 实现真正的“连续记忆”。

## 已完成修复

### 1. 已实现真实消息链上下文

- `StoryEngine` 现在在章节生成阶段维护连续消息历史。
- 第 2 章开始的请求不再是新的 `system + user` 独立请求，而是：
  - 已有历史消息
  - 当前章节新的 `user` 请求
  - 模型新的 `assistant` 响应
- 已新增测试覆盖：
  - `tests/test_story_engine_context.py`
  - 已验证第二次章节调用包含前一轮 `assistant` 消息。

### 2. 已实现持久化模型响应缓存

- 模型响应缓存已从“无持久化”升级为：
  - 进程内内存缓存
  - 文件持久化缓存
- 响应缓存 key 现在基于：
  - `model`
  - `request_messages`
  的稳定 `sha256`
- 已新增测试覆盖：
  - 相同请求跨 `StoryEngine` 实例命中持久缓存

### 3. 已修正上下文快照缓存过度绑定 `task_id`

- `ContextManager` 缓存 key 已去掉 `task_id`
- 同一规格的不同任务现在可以复用上下文快照缓存
- 命中后会把返回快照里的 `task_id` 修正为当前任务

### 4. 已补充上下文记录落盘

- 每次模型请求完成后，都会把当前阶段的消息链写入：
  - `context/<stage>/<exchange>-history.json`
- `TaskService` 还会追加事件：
  - `context.history.updated`
  - `cache.hit`
- 工作台日志现在可以通过 `json_ref` 追踪具体消息链文件
