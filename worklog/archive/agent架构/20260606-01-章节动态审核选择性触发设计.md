# 章节动态审核选择性触发设计

## 问题标题

章节动态审核选择性触发设计

## 用户原始诉求

章节动态审核这部分选择性触发，先走一次全文验证，这个验证是检查有没有什么严重和致命问题，如果没有直接走后续的动态审核，减少多次动态审核链路，如果有则需要根据全文验证的结果去分配子 Agent 进行针对性动态审核。

## 当前状态

已完成代码实现、本地回归和完整真实链路验证，满足归档与提交条件。

## 需求澄清补充

- 用户明确指出：该方案不能依赖“整本写完再审核”的前提。
- 约束原因：长篇小说不会在中途等待整本完成后再决定章节动态审核，流程必须在长篇场景下成立。
- 当前修正方向：将“先验证再决定是否触发动态审核”理解为批次级、窗口级或累计上下文级验证，而不是整本终局验证。
- 用户进一步要求：章节阶段门禁验证应改为“近几章校验”，默认窗口为 2 章。
- 用户进一步修正：章节阶段门禁验证的正文窗口改为最近 1 章。
- 默认上下文策略：
  - 最近 1 章可传正文全文/正文摘录；
  - 更早章节仍按当前方案传摘要，但摘要窗口最多保留最近 10 章；
  - 保留按需切换为更大正文范围或全文正文参与校验的能力。

## 初始分析方向

- 梳理当前章节审核、全文验证、动态审核、恢复链路和待审核状态的先后关系。
- 评估“章节动态审核必跑”改成“先做批次/窗口级严重问题筛查，再按需触发针对性动态审核”的最小改造边界。
- 识别对 `auto_review_trace`、等待审核状态、恢复入口、前端审核展示和最终结果语义的影响。

## 当前链路结论

- 当前真实主图顺序仍是：`prepare_chapter_pair_context -> draft_chapter_pair -> review_chapter_pair -> accumulate_chapters -> verify_full_story -> review_verification`。
- 也就是说，章节动态审核现在是“每批必跑”，全文验证只在全部章节完成后才会进入。
- 若要支持长篇场景，不能依赖“整本完成后的终局验证”；应改为“当前章节对 + 已完成章节摘要”的批次级严重问题筛查。

## 候选方案

### 方案 A：批次级验证前置，异常才进动态审核（推荐）

- 在 `draft_chapter_pair` 之后，不直接进入 `review_chapter_pair`。
- 先进入一个轻量“批次验证门禁”，输入范围固定为：
  - 当前章节对正文；
  - 已完成章节摘要；
  - 当前大纲与风格约束。
- 该门禁只判断是否存在 `critical/fatal` 级问题，不做全量多 Agent 审核。
- 若没有严重问题：直接 `accumulate_chapters`，继续后续批次生成。
- 若存在严重问题：再进入“针对性动态审核”，根据验证报告里的问题类型分配定向子 Agent，例如结构、人物动机、伏笔、风格，而不是每次都跑完整通用 Agent 套餐。
- 实现上优先复用现有 `verification_review` 骨架，并补一个 `scope=chapter_window` 或等价标记，避免前端和恢复链路大改。

优点：

- 最符合“长篇可持续推进”的要求。
- 请求数下降明显：健康批次只需 1 次轻量验证，不再每批都跑 `Master + Planner + 多个子 Agent + 综合 Agent`。
- 可以保留现有恢复/等待审核主骨架，改动集中在后端图节点和审核载荷。

代价：

- 需要把“全文验证”语义拆成“批次验证门禁”和“终局全文验证”两种 scope。
- `auto_review_trace` 会从“每批都有章节动态审核轮次”变成“只有异常批次才有动态审核轮次”。

### 方案 B：新增中间审核类型与等待状态

- 新增如 `chapter_gate_review`、`targeted_chapter_review` 两个新 review type。
- 工作流语义最清晰：门禁验证就是门禁验证，针对性动态审核就是针对性动态审核。
- 前端审核页、恢复页、`pending_review.type`、`waiting_*` 状态都按新语义扩展。

优点：

- 语义最干净，后续维护最好。
- 历史 trace、恢复目标和页面展示都更准确。

代价：

- 改面最大：后端状态、恢复、前端审核展示、类型定义都要动。
- 不适合作为第一批最小落地。

### 方案 C：本地规则先筛，再决定是否调 LLM 门禁

- 先用规则做本地检查，例如章节为空、章节数错位、标题/正文缺失、明显长度异常、关键字段缺失。
- 规则通过后直接放行；规则失败时才进入 LLM 门禁，再决定是否做动态审核。

优点：

- 最省请求。
- 对明显坏稿能立刻拦截。

代价：

- 只能发现机械问题，发现不了“悬疑推进断裂、人物动机失真、伏笔回收失败”这类内容问题。
- 不足以独立满足你的目标，只适合作为方案 A 的附加优化。

## 当前推荐

- 推荐方案 A。
- 具体理解是：
  - 每批章节生成后先做一次“批次级严重问题筛查”；
  - 筛查范围是“当前章节对 + 已完成章节摘要”；
  - 没有严重问题就直接进入后续批次；
  - 只有严重问题才触发针对性动态子 Agent 审核。
- 这条路最接近你的目标，同时对现有恢复、前端和审核页的破坏最小。

## 最新方案修正

- 章节门禁验证窗口不再固定为“当前章节对正文 + 全部历史摘要”。
- 改为：
  - 默认取最近 1 章正文窗口参与门禁验证；
  - 更早章节只保留摘要，且摘要窗口最多保留最近 10 章；
  - 当前批次正文仍完整参与；
  - 配置上保留扩展到更大窗口或全文正文参与校验的能力。
- 这样做的目的：
  - 保持长篇连续性问题的可见性；
  - 避免每批都把长篇全文正文送入模型；
  - 比“只看当前章节对”更贴近实际写作上下文，同时严格控制 token 成本。

## 已实施内容

- 工作流改造：
  - 在 `draft_chapter_pair` 后新增 `chapter_gate_review` 节点。
  - 自动审核开启时，先做章节批次门禁验证，不再每批直接进入 `review_chapter_pair`。
  - 门禁无严重问题：直接 `accumulate_chapters`。
  - 门禁发现 `critical/fatal`：进入 `review_chapter_pair`，并将其语义收敛为“针对性动态审核”。
  - `revise_chapter_pair` 完成后回到 `chapter_gate_review` 重新筛查，而不是直接回章节动态审核。
- 门禁验证范围：
  - 当前章节对保留正文；
  - 已完成章节默认拆成两段：
    - 最近 1 章保留正文；
    - 更早最近最多 10 章只保留摘要；
  - 最近 1 章不会再重复传摘要。
  - 复用现有 `full-text-verifier` 能力，不新增前端状态。
- 动态审核上下文增强：
  - `ReviewPayload` 新增 `review_scope`、`target_dimensions`。
  - 若门禁报告存在严重问题，`review_chapter_pair` 会把门禁报告和推导出的目标维度带给动态审核桥接层。
  - 动态审核描述从“通用章节审核”改为“根据前置验证发现的严重问题做针对性审核”。
- 保持不变：
  - 人工审核路径仍复用现有 `waiting_chapter_review`。
  - 全书完成后的 `verify_full_story -> review_verification` 终局验证仍保留。
  - 前端审核页和恢复页第一批不新增 `waiting_*` 状态。

## 2026-06-06 只读分析结论（进行中）

- 当前实现仍是“章节批次生成后立即进入 `review_chapter_pair`，全部章节通过后才进入 `verify_full_story -> review_verification`”，不是“先验证再决定章节审核”。
- `waiting_chapter_review`、`waiting_verification_review` 两类等待态都由 LangGraph `interrupt` 经 `TaskServiceCore._sync_result()` 落盘，恢复、审核页、工作台状态均直接依赖 `pending_review.type + task.status/current_stage`。
- 恢复链路对章节审核与全文验证分开建模：章节审核依赖 `pending_review.chapter_pair` 可重建，全文验证依赖 `pending_review.verification_report` 可重建；另外存在“章节审核状态过期时自动校正到全文验证审核”的专门兜底。
- 若改为“先筛严重问题，再按需触发章节动态审核”，最小改动主要落在后端图节点/路由与 `ReviewPayload` 语义，不在前端骨架；前端更多是跟随后端返回的新审核类型或新等待态。
- `auto_review_trace` 当前按“每发生一次自动审核就追加一轮 `__summary__`”统计，前端按轮次分段展示；因此它不强依赖“每批必跑”，但如果跳过章节动态审核，章节审核页会出现 trace 为空或轮次减少的表现。
