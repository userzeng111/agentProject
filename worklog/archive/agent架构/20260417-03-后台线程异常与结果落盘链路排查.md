# 后台线程异常与结果落盘链路排查

- 用户原始诉求：只读检查后台线程/异常路径，聚焦 `TaskService._start_background`、`_run_task_sync`、`_sync_result`、store 写入链，判断是否存在 graph 已完成 interrupt 但后台线程异常、返回结构不兼容、或结果同步未落盘的可能，并给出证据化结论和最小修复建议，不改代码。
- 当前状态：已完成实现，待收口。`TaskService` 已补上终态保护与稳态兜底，相关定点与回归测试已通过，待和其余 active 一起统一归档。
- 讨论范围：
  - 后台线程入口与异常处理。
  - `graph.invoke()` 返回结构与 `TaskService` 取值兼容性。
  - `_sync_result()` 到 store 持久化的调用顺序、吞异常点与漏写风险。
- 讨论结论：
  - 目前代码里确实存在“graph 已经到达 interrupt/END，但后台线程最终仍被标记失败”的窗口。证据链是：`main_graph` 在审核节点直接调用 `interrupt(...)` 并依赖 checkpointer 持久化状态；`TaskService._run_task_sync()` / `_resume_task_sync()` 在 `graph.invoke()` 返回后统一进入 `_sync_result()`；只要 `_sync_result()`、`_sync_supervisor_plan()` 或其后的 `_emit_trace_summary()` 任一点抛异常，外层 `except` 就会执行 `store.set_failed(...)`，随后 `_start_background()` 的线程包装还会再尝试一次 `set_failed(...)`。这意味着图状态可能已经可恢复，但任务快照最终会被覆盖成 `failed`。
  - 当前仓库内，`graph.invoke()` 的返回结构假设与实现、测试是一致的，不存在“已经确认的当前不兼容”。证据是：图中审核节点用 `interrupt({...})` 生成打断；多个图测试都断言 `result["__interrupt__"][0].value[...]`；`_sync_result()` 也按同一结构读取 `result["__interrupt__"][0].value`。同时，正常结束分支并不依赖 `result` 本体，而是依赖 `graph.get_state(...).values`，`tests/test_task_service_supervisor_seed.py` 也明确用空字典 `{}` 调 `_sync_result()` 覆盖了这一路径。
  - 但这条返回结构处理非常脆弱，属于“兼容当前实现，但缺少形态兜底”。如果未来 LangGraph 升级、测试桩、包装层或 mock 把 `__interrupt__` 变成 plain dict / plain payload / 空数组，`_sync_result()` 会在 `result["__interrupt__"][0].value` 这里直接抛异常，随后被外层失败逻辑覆盖成 `failed`。
  - “结果同步未落盘”不是主链常态，但存在两个明确窗口。第一，`_sync_result()` 在任何 `store.set_waiting_*()` / `set_completed()` 调用前抛异常时，graph checkpoint 已写、任务文件还没同步到 `pending_review` / `draft_result`，表现为图里已经 interrupt/结束，但 `task.json` 还停留在 `planning`/`drafting`，随后又被改成 `failed`。第二，`store.append_event()` 会先把事件写入 `events.md` / `trace/current.json`，而完整任务快照与 `result.json` 要等后续 `save()` -> `_write_task_files()` 才写；如果进程在两者之间中断，会出现事件先更新、`state/task.json` 与 `result.json` 尚未同步的短暂不一致。
  - 现有主链在“成功进入 `_sync_result()` 且 `store.set_waiting_*()` / `set_completed()` 执行成功”的情况下，审核快照和结果是会落盘的。`TaskLogStore.save()` 会统一调用 `_write_task_files()`，后者同时写 `task.json`、`state/task.json`、`outline.json`、`result.json`、`result.md`。因此不存在“成功走完同步函数但 store 完全不写盘”的证据。
- 最小修复建议应优先收敛在 `TaskService`，不需要改图：  
  1. 在 `_sync_result()` 内先做一个独立的 `extract_interrupt_payload(result)`，兼容 `Interrupt.value`、plain dict、空列表三种形态，并在缺失时给出明确错误。  
  2. 将 `_sync_result()` 中“状态持久化”和“附加 trace/supervisor 更新”拆开；一旦 `set_waiting_*()` / `set_completed()` 已成功，后续 `_sync_supervisor_plan()` 或 `_emit_trace_summary()` 失败不应再把任务整体改成 `failed`，最多追加告警事件。  
  3. `_start_background()` 的 runner 在二次兜底 `set_failed()` 前，先重新读取任务；若状态已是 `WAITING_*` / `COMPLETED` / `CANCELLED`，则只记录日志，不要覆盖终态。这样可以避免“图已完成 interrupt，但线程尾部异常把终态刷成 failed”。

- 本轮实现计划：
  1. 先在 `tests/test_task_service_supervisor_seed.py` 与相关测试中补失败用例，锁住“outline waiting 已落盘后，后续附加同步失败不反刷 failed”的行为。
  2. 再在 `TaskService` 内拆分“稳定状态写入”和“附加同步/追踪”两个阶段。
  3. 最后补 `_start_background()` 的终态保护，并执行阻塞式回归验证。
