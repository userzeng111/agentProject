# 多 Agent 并行写作隔离与提速验证

## 用户原始诉求

现在已经测试了单章即时展示与验证降级能力，但还没有测试：如果是 8 章短篇小说，同时并行编写 3 本，会不会出现上下文被污染干扰；任务之间是不是彼此独立；多 Agent 并行编写正文能不能提速；多 Agent 共同治理时会不会出现部分 Agent 异常。

- 本轮目标：确认任务隔离边界、并发正文执行模型、治理 Agent 失败传播方式，并完成真实链路暴露问题修复。

## 待验证问题

1. 3 个 8 章短篇任务并行执行时，任务状态、上下文、章节正文、缓存是否隔离。
2. 多 Agent 并行编写正文是否真的并发发起 LLM 请求，还是被当前流程串行化。
3. 多 Agent 共同治理时，单个 Agent 失败、超时或返回异常结构是否会污染其他 Agent 或阻断整体任务。

## 只读排查结论

- 任务运行隔离：`TaskService._config()` 使用 `task_id` 作为 LangGraph `thread_id`，checkpoint 按任务线程隔离。
- 任务文件隔离：任务目录为 `tasklog/runs/<task_id>/`，章节写入锁为 `_chapter_file_locks[task_id]`，跨任务不会共用章节索引锁。
- 任务执行并发：不同 `task_id` 可各自启动后台线程，同一任务通过 `_active_runs` 阻止重复运行。
- 正文章节并发：`StoryEngine.generate_chapter_pair()` 默认只对首批章节对并发；8 章任务仍按批次推进，不是 8 章全并发。
- 共享风险：`StoryEngine.response_cache` 是跨任务全局缓存，key 由完整请求消息、模型、max_tokens、request_options 组成，不包含 `task_id`；正常不同 prompt 不会互相命中，但完全相同请求并发写同一 cache 文件时存在文件级竞态风险。
- 治理失败隔离：旧 `AutoReviewManager` 子 Agent 异常会封装为 `SubAgentOutput.error`，动态编排器并行 future 异常会封装为失败结果。

## 动态 Agent 模板缺陷修复

- 根因：`AgentFactory.render_prompt()` 对整段动态 `user_prompt_template` 调用 `str.format()`，当 Master Agent 生成的模板包含未转义 JSON 示例（如 `{"score": 80}`、`{"total_score": 80}`、`{"issue_location": "第1章"}`）时，Python 会把 JSON 花括号当成格式字段并触发 `KeyError`。
- 修复：`apps/agent-runtime/app/agents/dynamic/factory.py` 改为安全渲染，只替换明确的 `{变量名}` 与 `{{变量名}}` 占位符；普通 JSON 花括号保持原样；缺失变量继续按旧语义替换为空字符串；已转义的 `{{`/`}}` 仍还原为普通花括号。
- 回归测试：`apps/agent-runtime/tests/test_dynamic_review_bridge.py` 新增动态 Agent 模板测试，覆盖 JSON 示例中 `score`、`total_score`、`issue_location` 字段不再触发模板错误，并覆盖 `execute_agent()` 可继续进入 fake LLM JSON 调用。
- RED 验证：修复前运行 `uv run --project apps/agent-runtime pytest apps/agent-runtime/tests/test_dynamic_review_bridge.py -v`，新增 2 条测试失败，错误为 `'"score"'`。

## 审核并发参数讨论

- 真实压测最大在飞请求数为 6，主要来源是 `AUTO_REVIEW_MAX_WORKERS` 未显式设置时默认值为 2；3 个任务并行时，动态审核层理论上形成 `3 个任务 × 每任务最多 2 个审核 worker = 6` 的上限。
- 动态审核不是简单一个 Agent 接一个 Agent：流程是 Master Agent 生成蓝图、Planner Agent 规划 DAG、同一 DAG 层内子 Agent 并行执行、下一层综合 Agent 等待前层结果后再执行。层内并发受 `AUTO_REVIEW_MAX_WORKERS` 限制，层间仍然串行。
- 将 `AUTO_REVIEW_MAX_WORKERS` 设置为 10 可以提高审核层并发上限；但实际收益取决于 Master 生成的同层分析 Agent 数量、上游网关并发容量和限流策略。若每次审核只有 3-5 个同层分析 Agent，10 不会被打满；若 3 个任务同时运行，峰值可能从 6 提升到 12-30 区间。
- 该参数只影响审核子 Agent 并发，不会直接改变正文批次生成逻辑。正文生成仍按章节批次推进，首批章节对可并行，后续批次受上下文连续性约束。
- 动态模板缺陷修复后，之前渲染阶段失败的审核 Agent 会重新进入真实 LLM 调用，请求数可能比本次 160 更多；因此不建议直接把生产默认拉到 10 后不验证，建议按 4、6、10 做阶梯压测，比较 wall time、平均请求耗时、最长请求耗时、失败率和 429/5xx。

## 动态评分字段兼容修复

- 根因：动态子 Agent 有时返回维度化评分字段（如 `atmosphere_score`、`coherence_score`、`style_score`），而 `AgentFactory.execute_agent()` 只识别 `score`、`total_score`、`overall_score`、`weighted_score`、`final_score`、`synthesis_score`，导致真实链路中个别子 Agent 评分被记为 0。
- 修复：`apps/agent-runtime/app/agents/dynamic/factory.py` 新增统一评分提取逻辑；标准评分字段保持最高优先级；若标准字段缺失，则兼容识别安全的 `*_score` 数值字段；排除 `max_score`、`threshold_score` 等容易误判的阈值类字段；同时区分“真实 0 分”和“没有评分字段”。
- 回归测试：`apps/agent-runtime/tests/test_dynamic_review_bridge.py` 新增 `test_execute_agent_accepts_dimension_specific_score_field`，覆盖 `atmosphere_score` 可正确进入 `TaskExecutionResult.score`。
