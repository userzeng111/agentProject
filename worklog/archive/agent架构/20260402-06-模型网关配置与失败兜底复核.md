# 模型网关配置与失败兜底复核

## 用户原始诉求
用户指出：
- `tasklog/archive/task_6b53157b3e/result.md` 对应任务没有调用其提供的模型请求网址和 key
- 后续不允许再出现这种问题
- 如果调用模型请求失败，必须直接提示错误，不能再继续推进任务流

## 当前已知上下文
- 当前需要核对：
  - 运行中的后端进程实际拿到的模型网关环境变量
  - 当前代码是否在模型请求失败时存在 fallback 继续生成

## 当前状态
- 已创建问题记录
- 已完成根因排查，暂未进入代码修改

## 当前排查结论
- 当前运行中的 8001 后端进程没有读到任何模型网关环境变量：
  - `LLM_BASE_URL`
  - `OPENAI_BASE_URL`
  - `LLM_API_KEY`
  - `OPENAI_API_KEY`
  - `LLM_MODEL`
  - `DEFAULT_CHAT_MODEL`
- 因此当前服务不会使用用户提供的 `agenturl` 与 key，而是落回代码默认配置
- 代码默认配置位于 `apps/agent-runtime/app/settings/config.py`
  - `openai_base_url` 默认值为 `https://api.lclaitech.com/v1`
  - `default_chat_model` 默认值为 `gpt-5.4`
- 当前代码确实存在“模型请求失败仍继续推进”的兜底逻辑
  - `apps/agent-runtime/app/llm/story_engine.py` 在大纲/正文/修订/验证各阶段调用网关失败后，会 `except (GatewayClientError, ValueError): pass`
  - 随后直接进入 `_fallback_story_plan(...)` 或其他 fallback 生成逻辑，继续产出结果
  - `_complete_json_with_cache(...)` 本身在 `gateway_client is None` 时也只抛错给上一层，而上一层当前会吞掉异常并继续 fallback

## 当前结论
- 用户指出的问题成立：
  - 当前运行服务没有使用其提供的模型请求网址和 key
  - 当前代码在模型调用失败时不会立即报错终止，而是会 fallback 继续推进

## 本轮新增配置结论
- `apps/agent-runtime/.env` 与 `apps/agent-runtime/.env.example` 目前存在三类问题：
  - 加载路径问题：当前 `Settings` 使用 `env_file=\".env\"`，不是固定指向 `apps/agent-runtime/.env`
  - 键名混乱：`.env` 主要使用 `LLM_*`，`.env.example` 主要使用 `OPENAI_*`
  - 模板污染：`.env.example` 不应携带真实密钥样式内容
- 用户已明确要求先修复这两份环境配置，再继续修复“模型失败必须直接报错终止”

## 建议整改方向
- 配置层
  - 显式要求运行时必须存在用户提供的模型网关 URL 与 API key
  - 若缺失，则服务启动即报错或接口直接返回错误
- 运行层
  - 去掉 `StoryEngine` 中吞掉 `GatewayClientError / ValueError` 后继续 fallback 的逻辑
  - 模型请求失败时直接让任务进入 `failed`，并把错误信息展示到工作台/审核页
- 验收口径
  - 若模型请求失败，任务不得生成任何 fallback 大纲/正文
  - 错误必须在 API/前端可见

## 本次实施（方案 A）
- 配置层
  - 固定 `Settings` 读取 `apps/agent-runtime/.env`
  - 统一环境变量名为：
    - `LLM_BASE_URL`
    - `LLM_API_KEY`
    - `DEFAULT_CHAT_MODEL`
  - `apps/agent-runtime/.env.example` 已改为纯模板，不再保留真实 key 样式内容
  - `apps/agent-runtime/.env` 已整理为单一生效配置，不再保留当前代码未使用的重复项
- 运行层
  - 去掉 `StoryEngine` 中大纲、章节、验证、修复链路的 fallback 继续推进逻辑
  - 当前没有可用网关或网关请求失败时，直接抛出错误，不再自动生成替代内容
