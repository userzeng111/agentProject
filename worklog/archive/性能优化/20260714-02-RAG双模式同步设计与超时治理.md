# RAG 双模式同步设计与超时治理

## 问题标题

将 RAG 索引操作明确拆分为增量同步与全量重建，并解决当前“增量”入口可能触发长时间全量构建而超时的问题。

## 用户原始诉求

用户反馈设置页请求 `POST /api/settings/rag/rebuild` 超时，并要求：

1. RAG 必须同时提供增量同步和全量同步两个功能。
2. 全量同步必须像删除操作一样进行二次确认。
3. 增量同步先完成设计，明确实际的实现与执行方式。

## 当前状态

已完成后端双模式后台作业、设置页双操作与全量二次确认；当前处于已实现、已完成回归验证状态，等待用户决定是否收口。

## 已知事实

- 现有单一 `/api/settings/rag/rebuild` 入口在旧索引缺少 manifest、模型或分块配置不兼容时会自动降级为全量构建。
- 首次全量嵌入大样本小说耗时较长，前端请求会超过默认超时，因此用户看到请求超时。
- 已实现的来源级 manifest 可用于后续的新增、修改、删除来源的局部同步，但当前 UI 和 API 尚未将用户意图明确区分为两种模式。

## 设计目标

- 增量同步永不隐式退化为长时间全量构建；遇到不兼容只返回“需要全量重建”的结构化状态。
- 全量重建必须显式选择，并完成首次提示与最终二次确认。
- 后台任务可查询进度、可在页面离开后继续运行，前端不因 HTTP 长连接超时而误报失败。
- 新旧索引切换必须原子发布，失败保持旧索引可用。

## 设计结论与实现结果

### 1. 明确操作语义

设置页拆成两个独立操作，不再使用单一“重建”按钮：

- **增量同步**：比较来源类型加相对路径构成的稳定 `source_key` 和来源 SHA-256 指纹；只对新增或变更来源分块与嵌入，删除来源只移除对应 FAISS、SQLite 和 manifest 映射；无差异返回 `noop`。
- **全量重建**：对当前所有来源重新分块和嵌入，建立新的完整索引；用于首次构建、旧索引迁移、模型/维度/分块规则变化和索引损坏修复。

增量预检发现无索引、manifest 缺失或版本不兼容、模型/维度/分块规则不兼容、FAISS 与 SQLite 数量不一致时，返回 `full_rebuild_required`，**不得自动执行全量构建**。

### 2. 后台作业与接口

前端不再等待八分钟的 HTTP 请求。先预检，再立即创建后台作业，接口在数百毫秒内返回 `202`，页面轮询作业状态：

```text
POST /api/settings/rag/plans                 # { mode: incremental | full }
POST /api/settings/rag/jobs                  # { plan_id, mode, idempotency_key, confirmation_token? }
GET  /api/settings/rag/jobs/current
GET  /api/settings/rag/jobs/{job_id}
GET  /api/settings/rag                        # 总状态、能力与最近结果
```

- `plans` 返回来源快照、预估新增/变更/删除、预计嵌入/复用文档数与兼容性结论；全量预检返回短时有效、一次性的确认令牌。
- `jobs` 返回 `job_id`、`queued` 状态和轮询间隔。后端只允许一个 RAG 写作业；同一幂等键返回原 job，其它请求返回 `409 sync_in_progress`。
- 作业状态为 `queued → running(扫描 → 对比 → 嵌入 → 校验 → 发布) → succeeded | failed | interrupted`。仅在有真实数量时展示进度百分比，否则展示阶段与不确定进度条。
- 作业记录与进度原子持久化；开发热重载或进程重启时，未完成 job 标记为 `interrupted`，不自动续跑。

### 3. 全量重建二次确认

采用与删除一致的两步交互，而非浏览器原生 `window.confirm`：

1. 用户点击“全量重建”。
2. MUI `ConfirmDialog` 明示来源数量、预计文档数、耗时与“旧索引会在新索引校验成功前继续可用”；用户点击“确认全量重建”才可创建 job。

服务端要求预检生成的 `confirmation_token` 与 `mode=full` 同时提交，防止客户端把增量请求误传为全量。取消或关闭 Dialog 不产生 job。

### 4. 索引实际处理和安全发布

1. 扫描 `exampleIndexData` 和已归档小说来源，按文件原始内容计算 SHA-256；mtime 仅用于展示，不决定正确性。
2. 增量模式读取 manifest 并验证 schema、模型指纹、向量维度、分块规则、ID 规则、FAISS/SQLite/映射计数。
3. 新增来源只嵌入新增 chunks；变更来源先在暂存索引删除其旧 doc IDs，再嵌入新 chunks；删除来源只清理旧 doc IDs；未变来源复用现有向量。
4. 当前实现沿用既有的暂存索引发布流程：在暂存目录写入 FAISS、SQLite 和 manifest，校验向量数、文档数、映射数与维度后，再替换已发布文件；替换异常时恢复备份，失败不会覆盖旧索引。
5. `generations/<generation_id>/` 加 `current.json` 指针切换可进一步消除双文件替换期间的读写窗口，作为后续架构增强项，不在本次接口超时治理范围内。

### 5. 设置页交互

- 顶部展示数据库可用性、索引健康、来源/文档数与最近成功时间。
- “增量同步”为主按钮，描述“仅嵌入新增或变更资料，并删除已移除来源”；创建作业后显示“正在后台同步，可离开页面”。
- “全量重建”为 warning 次级按钮，描述适用场景和耗时；只经确认 Dialog 启动。
- `full_rebuild_required` 以就近 Alert 说明原因，将增量入口禁用或改为“需要全量重建”，但不自动切换。
- 作业失败显示“当前已发布索引未改变”及可执行的重试/全量重建入口；轮询失败只提供“重新获取状态”，不重复 POST。
- 移动端按钮纵向全宽，统计可换行；Dialog 具备键盘焦点、可见焦点环、`aria` 描述和至少 44px 触达目标。

### 6. 必要测试

- 增量：新增、变更、删除、空变更、每一种不兼容原因均验证零 embedding 且返回 `full_rebuild_required`。
- 全量：确认令牌缺失/过期/来源快照过期被拒绝，成功后原子切换 generation。
- 作业：202 快速返回、并发 409、幂等、失败/取消/重启不污染活动索引、进度与结果可查询。
- 前端：增量启动和恢复轮询、全量 Dialog 取消不请求/确认才请求、不兼容引导、375px 无横向滚动、键盘焦点与错误提示。

## 本次实现

- 新增 `POST /api/settings/rag/plans`、`POST /api/settings/rag/jobs`、`GET /api/settings/rag/jobs/current` 与 `GET /api/settings/rag/jobs/{job_id}`；旧同步阻塞接口 `POST /api/settings/rag/rebuild` 返回 `410`。
- 增量预检只比较来源级 SHA-256 清单；缺少或不兼容清单、模型/分块/维度变化、索引计数异常时返回 `full_rebuild_required`，不会隐式进行全量嵌入。
- 后台作业使用单工作线程和文件锁互斥，持久化计划、作业阶段与进度；支持幂等提交，服务重启会将未完成作业标记为中断。
- 设置页将“增量同步”与“全量重建”拆为独立操作；全量重建必须先预检并在 MUI 对话框中二次确认，确认后才会创建后台作业。任务创建失败时保留确认弹窗，便于用户原地重试。
