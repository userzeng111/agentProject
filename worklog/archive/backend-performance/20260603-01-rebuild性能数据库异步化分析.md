## 只读上下文分析记录

### Agent Team 角色拆分
- 角色 A：性能/调用路径分析。关注历史请求耗时、同步端点数量、后台线程与阻塞 I/O。

- 角色 C：API 异步化分析。关注 FastAPI 路由是 `def` 还是 `async def`、是否存在事件循环阻塞风险。
- 角色 D：日志/可观测性与技术漏洞分析。关注请求日志、慢查询日志、异常日志与数据清理漏洞。

### 初步发现
- 当前分支为 `rebuild`。
- `apps/agent-runtime/app/api/routes.py` 中大多数 v1 路由仍是同步 `def`；仅上传、SSE、聊天流为 `async def`。
- `apps/agent-runtime/app/storage/database.py` 使用同步 SQLAlchemy `create_engine` + `Session`；SQLite 已设置 WAL、foreign_keys、busy_timeout=5000，但缺少可配置连接参数、慢查询/SQL 查询耗时日志、异步 `AsyncEngine/AsyncSession` 路径。
- 历史应用日志已存在请求耗时日志，6268 条请求中最慢集中在 `/api/tasks/{task_id}/continue`、`/api/tasks/{task_id}/cancel`、`/api/tasks/{task_id}/resume`、`/api/dashboard`、`/api/tasks/{task_id}/workspace`；其中 `continue` 曾出现长期阻塞，但当前代码已有后台队列入口，仍需验证是否完全覆盖。
- `TaskLogStore` 的保存路径仍大量同步写文件并 fsync；即使 API 改成 `async def`，如果直接调用这些同步方法会阻塞事件循环，需通过服务层异步封装或线程隔离逐步改造。
- `TaskService._delete_db_associations` 使用 SQLAlchemy 2.0 不接受的裸 SQL 字符串，并且删除不存在的 `agent_run` 表；实际验证会抛出 `ArgumentError`，导致关联表清理失败并被 warning 吞掉，属于需要修复的数据清理漏洞。
- 后端已有 `app.observability` 请求日志和模块日志，但没有数据库查询耗时日志、慢查询阈值、DB 参数配置项，也没有统一入口记录 API 服务层操作耗时。

### 第三方文档确认
- FastAPI 文档说明：普通 `def` 路由会放入外部线程池执行，避免阻塞事件循环；`async def` 适合等待异步 I/O，但不能直接调用阻塞 I/O。
- SQLAlchemy 2.0 文档说明：可使用 `create_async_engine` + `async_sessionmaker` 构建异步数据库路径；SQLite aiosqlite 应配合 async engine 使用；可在 Engine/AsyncEngine.sync_engine 上注册 `before_cursor_execute`/`after_cursor_execute` 统计 SQL 耗时，并可用 logging 控制 SQL/连接池日志。
- Anthropic 官方 Python SDK 文档确认：Messages API 为 `/v1/messages`，SDK 默认读取 `ANTHROPIC_API_KEY`，客户端支持 `base_url`；本项目已有 Anthropic Messages payload/stream 适配器，但网关基址与认证头当前走项目自定义 `OpenAICompatibleGatewayClient`。

## A 方案执行设计草案

### 第一批修复范围
1. 修复明确漏洞：`TaskService._delete_db_associations` 改用 SQLAlchemy 2.0 `text()` 或 ORM repository 删除路径，移除不存在的 `agent_run` 表删除语句，保留 `novel_generation_batch`、`novel_project` 等真实表关联清理。
2. 补数据库配置：
   - 新增 SQLite 连接参数配置项：`SQLITE_BUSY_TIMEOUT_MS`、`SQLITE_JOURNAL_MODE`、`SQLITE_FOREIGN_KEYS`、`SQLITE_SYNCHRONOUS`、`DB_SQL_LOG_ENABLED`、`DB_SLOW_QUERY_MS`。
   - 初始化时记录数据库路径、WAL/foreign key/busy timeout 等实际参数。
3. 补 SQL 耗时与慢查询日志：
   - 在 SQLAlchemy engine 上注册 `before_cursor_execute` / `after_cursor_execute`。
   - 普通 SQL 耗时按开关输出 debug/info，超过阈值输出 warning。
   - 日志中禁止输出敏感参数完整值，仅输出语句摘要、耗时、行数或连接信息。
4. API 第一阶段异步化：
   - 高频慢点和核心路由改 `async def`。

5. 模型/API 切换：
   - 设置项兼容 `ANTHROPIC_BASE_URL`、`ANTHROPIC_AUTH_TOKEN`，映射到现有网关配置。

## URL 自动拼接设计
- 新增 URL 规范化函数，原则：
  - 用户给根域名：`https://token-plan-cn.xiaomimimo.com`
    - OpenAI 协议请求基址规范化为 `https://token-plan-cn.xiaomimimo.com/v1`
    - Anthropic 协议请求基址规范化为 `https://token-plan-cn.xiaomimimo.com/v1`
  - 用户已经给 `/v1`：保持不变。
  - 用户给特殊前缀如 `/anthropic`：默认不强行改写；除非配置为 Anthropic 且新增显式 path 前缀覆盖。
- 推荐实现位置：
  - 不改 `OpenAIAdapter` / `AnthropicAdapter` 的 endpoint 语义；
  - 在 gateway client 中根据当前 adapter/protocol 解析出实际请求 URL 和实际请求 headers。
- 协议请求形态：
  - OpenAI：`{normalized_base}/chat/completions`、`{normalized_base}/models`，header 用 `Authorization: Bearer ...`。
  - Anthropic：`{normalized_base}/messages`，header 用 `Authorization: Bearer ...` + `x-api-key` + `anthropic-version`；兼容代理是否要求 Bearer。
- 配置兼容：
  - `LLM_BASE_URL` 作为统一根地址或完整协议基址；
  - `ANTHROPIC_BASE_URL` 只在默认协议为 Anthropic 或模型级协议为 Anthropic 时作为更高优先级基址；
  - `LLM_API_KEY` 与 `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_API_KEY` 都可作为密钥来源，但敏感值不进入提交。

## 2026-06-04 Agent Team 只读复核结论

### 性能与阻塞路径
- `/api/models`、`/api/dashboard`、`/api/tasks/{task_id}/workspace`、`/api/tasks/{task_id}/review` 等读接口可能在模型目录缓存失效时同步触发远端 `/models` 请求；现有日志中 `/api/models` 曾出现约 24.6 秒耗时，`dashboard/workspace` 也有秒级请求。
- `GET /api/tasks/{task_id}` 当前不是纯读路径，会调用 `recover_task()`，可能写任务状态、事件、Supervisor 与数据库；这与“API 请求切纯异步路径”和读接口性能目标冲突。
- `TaskLogStore.save()/append_event()` 存在写放大：一次状态变化可能写任务快照、events、trace、index、DB 索引，并且每个文件写入都 `fsync`。
- `continue/resume` 虽已后台化，但入队前仍有同步 DB、文件写、Supervisor 同步与模型校验，历史日志存在秒级请求。
- 动态编排 API 使用默认 `asyncio.to_thread` 包长任务，内部再开线程池跑 LLM；并发时可能占满默认 executor。

### 数据库与 SQL 日志
- 业务 SQLite 初始化固定为 `tasklog_root/data.db`，当前只有 `journal_mode=WAL`、`foreign_keys=ON`、`busy_timeout=5000`，缺少独立 DB 路径、连接超时、`synchronous`、SQL 日志开关、慢查询阈值等配置。
- 当前无 `before_cursor_execute/after_cursor_execute` SQLAlchemy 事件，无法输出 SQL 查询耗时和慢查询日志。
- `TaskService._delete_db_associations()` 存在明确漏洞：
  - SQLAlchemy 2.x 下直接 `session.execute("DELETE ...")` 可能失败，应使用 `text()` 或 ORM/Core delete。
  - 删除不存在的 `agent_run` 表。
  - 遗漏 `novel_outline_chapter` 与 `novel_chapter_plan_batch`。
  - 异常被 warning 吞掉，删除接口可能对外返回成功但 DB 关联残留。
- RAG 元数据库和 LangGraph checkpoint 是独立 sqlite3 连接，不会继承业务库 PRAGMA 配置，需要单独处理。

### API 异步化
- FastAPI 官方行为：普通 `def` 路由会在线程池执行；直接改成 `async def` 后若继续调用同步文件 I/O、同步 SQLite、同步 HTTP，会阻塞事件循环。
- 第一阶段应改为 `async def + run_in_threadpool` 隔离同步服务调用；`upload_asset` 和 SSE 中已有 `async def` 但内部仍直接调用同步服务，也要补线程隔离。
- 第二阶段再逐步引入 SQLAlchemy `create_async_engine`、`async_sessionmaker`、`AsyncSession`；文件 I/O 仍需独立线程池或异步文件方案，不能只靠 AsyncSession。

### 日志与技术漏洞
- “后端没写 log”不准确：项目已有请求日志、文件日志、LLM 耗时日志和部分业务异常日志；真实缺口是异常栈被自定义 formatter 吃掉、缺 DB SQL/慢查询日志、缺服务层分段耗时日志。
- `_StructuredFormatter.format()` 未追加 traceback，`logger.exception()` 只能看到单行错误，排障信息不足。
- 存在安全风险：
  - 删除、上传、聊天、RAG 重建、协议设置等接口无鉴权；若通过 tunnel 暴露，风险高。
  - SPA fallback 拼路径时缺少 `resolve()` + `relative_to()` 约束，存在路径穿越风险。
  - JSON 解析失败时完整 `raw_response` 和 `request_messages` 会落盘；正常 conversation history 也会落盘，需增加开关、大小限制或脱敏。
  - 上传接口 `await file.read()` 一次性读入内存，缺少大小限制。

  - 哪个 HTTP API 慢：可用 `request method/path/status/duration_ms/request_id` 定位。
  - 哪条业务 SQL 慢：开启 `DB_SQL_LOG_ENABLED` 或调低 `DB_SLOW_QUERY_MS` 后可看到 SQL 摘要、参数数量、行数、耗时。
  - 是否慢在模型网关：LLM complete/stream 有模型、消息数和整体耗时，失败/重试有日志。
  - 动态 agent / 自动审核的宏观耗时：响应或任务 trace 中有总耗时、agent 数量、单 agent `duration_ms`。
  - 任务卡在哪个宏观阶段：任务事件与 trace 能显示 planning、drafting、review、chapter.saved、parse_failed 等阶段。
- 仍只能粗定位：
  - `TaskService` 内部没有阶段 span，慢请求只能进一步人工查代码路径，不能直接区分 `store.save`、DB、模型目录刷新、Supervisor 同步、文件 I/O 哪一步慢。
  - SQL 慢查询缺少 repository 操作名，虽然能按 `request_id` 关联 HTTP，但不能直接知道业务方法名。
  - LLM 流式只看整体耗时，缺少首 token、chunk 数、输出 token、finish_reason 汇总、attempt 分段耗时。
  - SSE 长连接会把连接持续时间记为请求耗时，不能和普通 API 慢请求混在一起判断。

  - 后台线程未统一设置 `task_id` 日志上下文，后台 LLM/DB/文件 I/O 日志容易与触发请求断链。
  - 文件写入、flush/fsync、归档复制、context snapshot、response cache 落盘没有慢 I/O 日志。
  - SQLite commit、事务总耗时、锁等待、busy timeout 等待来源没有单独日志。
  - RAG 查询/重建内部缺少 `load_faiss/open_sqlite/embed/search/sqlite_write/faiss_save` 分段耗时。
  - checkpoint 读写只在异常时可见，没有正常路径耗时。
- 结论：
  - 当前日志已经足够“发现性能问题并定位到请求层、SQL 层、LLM 总调用层、agent 宏观阶段”。
  - 当前日志还不足以“精准定位复杂性能根因”，尤其是后台任务、服务层分段、文件 I/O、SQLite 事务等待、RAG/checkpoint 和流式 LLM 细分耗时。
  - 建议第二批补充结构化性能 span：`background_task_start/end`、`task_service_operation`、`task_store_io`、`db_operation/commit_ms`、`llm_stream_metrics`、`rag_operation`、`checkpoint_operation`。
