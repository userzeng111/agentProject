## 2026-06-04 性能结论
- 主要耗时是 LLM 流式调用：
  - 干净样本 4 次 LLM 调用总计约 `428.7s`。
  - 首 token 延迟为 `1.86s` 到 `5.61s`，不是主瓶颈。
  - 主耗时来自长时间流式输出和大量 reasoning chunk。
- 当前流程对 1 章短篇实际触发 4 次 LLM：
  - 大纲生成。
  - 正文生成。
  - 重复正文生成。
  - 全文验证。
  - 期望的最小路径应更接近 3 次 LLM；重复正文生成属于可疑额外路径。
- `model.thinking` 事件数量非常高：
  - 干净样本 `2362` 条。
  - 每条 thinking chunk 都会触发 TaskStore 事件落盘和任务快照保存，导致 `task_store_save` 超过 `4700` 次、`task_store_write_file` 超过 `61000` 次。
  - 这些存储 span 是嵌套统计，不能直接与 LLM 总耗时相加；但它们在同步流式回调中执行，会实质拖慢流处理。
- 数据库本身不是主要瓶颈：
  - 单次 `db_session_total` 平均约 `1.89ms`，commit 平均约 `0.69ms`。
  - 聚合 DB 时间约 `9s`，问题主要是调用次数过多，而不是单条 SQL 慢。
- RAG 不是本轮瓶颈：
  - `rag_search_backend` 只有 2 次，合计约 `207ms`。
- API 入队请求很快：
  - `run`、`resume`、`continue` 请求本身都在数百毫秒内返回。
  - 真正耗时发生在后台线程。

## 2026-06-04 Agent Team 整体优化分析结论
- 状态机/重复正文分析：
  - 章节审核恢复 seed 已包含 `current_chapter_pair`，缺 checkpoint 时应把它作为 `draft_chapter_pair` 的既有输出态回填，而不是重新执行正文生成。
  - 章节审核通过后服务层曾直接写入 `waiting_verification_review`，但 LangGraph checkpoint 仍可能停在章节审核/章节生成附近，导致 TaskStore 状态与图状态错位。
  - 修复方向：`chapter_pair_review` 缺 checkpoint 恢复时 seed 到 `draft_chapter_pair` 输出态，由后续 `review_chapter_pair` 消费 `Command(resume=...)` 后进入 `accumulate_chapters`；刚 seed 后不能再二次校准到 `review_chapter_pair` 后面。
- 流式事件写放大分析：
  - 每个 `reasoning_content` chunk 在 `BaseAgent._call_llm_stream_with_metadata()` 中同步触发 `progress_callback`。
  - `_build_progress_callback()` 对 `model.thinking` 没有特殊处理，直接 `mark_stage()`，进而 `append_event()`、`save()`、写 `events.md`、`events.tail.json`、`trace/current.json`、`task.json` 等文件。
  - 每个 progress event 还会尝试 `_sync_supervisor_plan()`，在有 supervisor plan 时可能再触发一次 `save()`。
  - 修复方向：`model.thinking` 降级为高频遥测事件，只广播或按窗口聚合，不再逐 chunk 改任务状态和全量落盘。
- 全文验证耗时分析：
  - `verify_full_story()` 一次性拼接所有章节正文，并使用宽泛一致性验证 prompt。
  - 验证阶段未传独立 `max_tokens`，当前配置会复用全局 `generation.max_tokens=10000`。
  - 未发现阶段化 reasoning 控制；对于支持的 OpenAI Chat Completions 参数，官方文档中存在 `max_completion_tokens`、`reasoning_effort`、`response_format`，但当前默认模型是 `mimo-v2.5-pro`，不能在未做兼容性测试前直接硬塞 OpenAI 专属参数。
  - 修复方向：为验证阶段设置独立输出预算、收紧 prompt、可选配置更快的验证模型；中长期改成摘要/事实表验证加必要片段复核。

## 2026-06-04 推荐优化方案
- P0：消除额外 LLM 调用和读接口副作用。
  - `GET /api/tasks/{task_id}` 改为纯读，不再调用 `recover_task()`；恢复只走显式 `POST /api/tasks/{task_id}/recover`。
  - 修复章节审核恢复入口：`chapter_pair_review` 缺 checkpoint seed 使用 `draft_chapter_pair` 输出态，并保留 `current_chapter_pair`、`completed_chapters`、`batch_index`、`total_chapters` 等状态；随后跳过二次审核节点校准。
  - 避免在未真实执行 `verify_full_story()` 前直接构造“全文验证完成”的 `verification_review`；章节最终通过后应通过统一图恢复进入 `accumulate_chapters -> verify_full_story -> review_verification`，或由服务层显式执行验证并同步 checkpoint。
- P1：降低流式持久化放大。
  - `model.thinking` 不再调用 `mark_stage()` 和 `_sync_supervisor_plan()`。

- P1：降低全文验证单次耗时。
  - 增加验证阶段独立配置，例如 `verification_max_tokens=1200~2000`，不要复用全局 10000。
  - 收紧验证 prompt：限制最多问题数、单条描述/建议字数、summary 字数，只报告影响主线理解的问题，不逐章复述。
  - 增加 `verification_model_id` 或复用审核模型配置，让验证可使用更快的审核模型；供应商参数如 `reasoning_effort/max_completion_tokens/response_format` 需要先做模型兼容性探测。
- P2：结构性存储优化。
  - `task.json` 不再保存完整事件数组，完整事件改 append-only `events.jsonl`。
  - `events.md` 改为完成/归档时生成或按需生成，避免每个事件重写全文。
  - TaskStore 写入改为 per-task debounce/批量 flush，任务失败、取消、等待审核、完成等稳定边界强制 flush。

## 2026-06-04 方案 A 实施校正
- 后续本地 LangGraph 最小实验校正了章节审核恢复入口判断：
  - `update_state(..., as_node="draft_chapter_pair")` 表示把 `current_chapter_pair` 作为正文生成节点的既有输出回填，随后 `Command(resume=...)` 会进入 `review_chapter_pair` 并消费 interrupt。
  - `update_state(..., as_node="review_chapter_pair")` 会把 checkpoint 推过审核节点，可能跳过 interrupt，不适合作为缺 checkpoint 的 seed 入口。
- 因此最终实现不是把缺 checkpoint seed 改到 `review_chapter_pair`，而是保持 seed 到 `draft_chapter_pair`，并在 `_resume_task_sync()` 中检测到刚刚 seed 后跳过后续二次 `as_node=review_chapter_pair` 校准。

## 2026-06-04 失败成因与修改设计讨论
- 用户追问：为什么正文回传字符串会影响主体，以及应该如何调整修改。
- 成因说明：
  - 网关 HTTP 响应外层 JSON 没有坏；适配器已经成功拿到了 `choices[].delta.content` 文本。
  - 失败发生在业务内层：系统要求模型把章节正文作为 `content(string)` 嵌入一个模型生成的 JSON 文本里，随后后端对这个文本执行 `json.loads()`。
  - JSON 字符串没有“正文隔离区”，正文里的英文裸双引号会被解析器当作 `content` 字段结束符，因此正文文本会破坏业务 JSON 边界。
- 修改设计倾向：
  - 必修一：修复章节数参数传递，`_initial_state()` 必须把 `target_chapter_count`、`chapter_count_min`、`chapter_count_max` 放入 `input_payload`，避免 1 章任务被标准化成 `7 到 9 章`。
  - 必修二：修复章节计划重复追加，批次审核通过时应按章节号合并/覆盖已存在计划，不能把总纲已有的 1-7 章再追加成 14 条。
  - 推荐结构性修复：章节生成不再把长正文嵌在单个 JSON 字符串里，改为“元数据 JSON + 正文原文分区”，例如 `<chapter_meta>{...}</chapter_meta>` 与 `<chapter_content>...</chapter_content>`；后端只解析短元数据 JSON，正文作为原文提取。
  - 兼容兜底：保留旧 JSON 响应解析路径；若旧路径失败且是章节生成，再尝试章节专用分区解析或有限修复，避免影响大纲、审核、验证等其它 JSON 响应。
  - 诊断补充：repair 失败时也保存 `*-repair-raw-response.json`，并在事件里区分首次失败与修复失败。
- 测试点：
  - `_initial_state()` 保留章节数输入，`build_normalized_spec()` 不回落到短篇默认 8。
  - 总纲已携带完整 `chapter_plan` 时，章节批次审核通过后章节计划长度仍等于规划章节数，章节号唯一。
  - 章节正文包含英文双引号、反斜杠、换行、Markdown 代码块时仍能生成 `ChapterDraft`。
  - repair 失败会保存二次诊断，方便定位真实失败响应。
- 方案边界校正：
  - “元数据 JSON + 正文原文分区”可以消除正文英文双引号破坏 `content(string)` 的问题，因为正文不再参与 `json.loads()`。
  - 但简单 XML/标签分区仍可能遇到分隔符碰撞，例如正文中意外出现 `</chapter_content>`。
  - 更稳妥的落地方案应使用明确不可用于正文的随机边界 token，并让后端只解析首段短 JSON；正文提取失败时进入一次协议修复或重试。
