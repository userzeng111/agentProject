# 后端链路耗时与最长 LLM 步骤观测设计

## 问题标题
后端链路耗时与最长 LLM 步骤观测设计

## 用户原始诉求
使用 agent team 模式并行分配任务，先头脑风暴并设计如下功能：在网关位置打日志，或者直接抓包，与前端日志做比对，观察整体后端链路耗时；当前每个步骤都要请求大模型，需要观察哪一步耗时最长。

## 当前状态
讨论中。已进入只读分析与方案设计阶段，尚未开始业务代码修改。

## 已知背景
- 历史性能分析已表明当前最小创作链路通常是大纲、正文、全文验证三类 LLM 调用。
- 仓库已具备部分后端性能观测与任务级 `llm_report` 能力，但尚未形成“网关请求 -> 后端阶段 -> 前端展示”统一对账视图。
- 本轮目标优先明确观测方案、日志对齐字段、实现落点与验证路径，再等待用户确认是否进入开发。

## 本轮关注点
- 选择“网关打日志”还是“抓包采样”作为主方案。
- 明确前端日志与后端日志的统一关联键。
- 明确如何统计每一步 LLM 请求耗时、首 token、总耗时与步骤归属。
- 识别当前链路中耗时最长的节点，并确定后续验证办法。

## 2026-06-08 只读调研结论

### 后端现状
- API 总耗时已由 `apps/agent-runtime/app/observability/middleware.py` 中的 `TracingMiddleware` 记录，字段包含 `request_id`、`method`、`path`、`status`、`duration_ms`。
- 后台线程会在 `apps/agent-runtime/app/application/task_service/core.py` 中继承 `request_id` 并注入 `task_id`，因此任务线程日志天然可以按 `request_id + task_id` 追踪。
- LLM 网关层已在 `apps/agent-runtime/app/llm/gateway_client.py` 记录：
  - `llm_stream_sync_first_token`
  - `llm_stream_sync_metrics`
  - `llm_stream_first_token`
  - `llm_stream_metrics`
  - `llm_complete`
- 这些日志已经包含 `model`、`duration_ms`、`first_token_ms`、`chunk_count`、`finish_reason`、`content_chars`、`reasoning_chars`、`attempt`，但缺少明确的业务步骤归属字段。
- `stage` 与 `exchange_label` 当前在 `apps/agent-runtime/app/llm/story_engine.py` 中最清楚，例如：
  - `planning / outline`
  - `drafting / chapter-01`
  - `verification / full-story-verification`
- 当前 `llm_report` 只聚合 token 与 exchange 次数，尚未纳入 `first_token_ms`、`duration_ms`、重试次数，前端无法直接拿它做完整耗时对账。

### 前端现状
- 前端统一 JSON API 入口在 `apps/web/src/lib/api.ts` 的 `request()`，目前只有失败重试和错误输出，没有统一的请求开始/结束耗时日志。
- 前端没有把后端 `X-Request-ID` 读出来，也没有主动生成统一 `client_request_id`。
- `continue_request_id` 仅在“继续创作”动作中存在，位于 `apps/web/src/features/task-run/task-run-client.tsx`，适合作为首个端到端样本的补充关联键。
- `fetchTextRef()`、`fetchJsonRef()`、`streamChat()` 和 `EventSource` 不走统一 `request()`，如果后续做前端侧对账，这几条链路也要单独补齐。

### 抓包可行性结论
- 主方案不建议从抓包开始。
- 原因：
  - 当前仓库的 LLM 出站调用高度集中在 `apps/agent-runtime/app/llm/gateway_client.py`，应用内日志已经能拿到最关键的性能字段。
  - `httpx.Client/AsyncClient` 使用 `trust_env=False`，系统级透明代理不可直接接管。
  - HTTPS 被动抓包只能得到网络层粗粒度指标，拿不到步骤名、模型、首 token 语义。
- 若需要代理补充验证，最低侵入方案是把 `LLM_BASE_URL` / `ANTHROPIC_BASE_URL` 指向本地反向代理，但这只能作为辅助交叉验证。

### 当前最长耗时判断
- 当前最需要优先盯住的步骤仍然是 `verification / full-story-verification`。
- 依据：
  - 代码形态上该步骤会消费完整已生成内容，且可能触发截断重试与 repair。
  - 历史真实样本中，全文验证多次是单次最长调用。
  - 最新 1 章真实样本中，验证约 `61.084s`，仍高于大纲与正文。
- 边界说明：
  - 某些样本中正文生成也可能更长，因此最终应以任务级明细统计为准，而不是写死判断。

## 当前推荐方向
- 主方案：应用内日志增强。
  - 后端以 `gateway_client` 为主观测点，补齐 `stage`、`exchange_label`、`step_name` 等业务归属字段。
  - 前端以 `apps/web/src/lib/api.ts` 为主入口，补齐结构化请求日志，并读取/透传 `X-Request-ID`。
  - 任务页优先用“继续创作”作为首个对账样本，结合已有 `continue_request_id` 做端到端串联。
- 备选方案：本地反向代理辅助采样。
  - 只采 HTTP 元数据，不采正文与完整 prompt。
  - 用于交叉验证首包时间、总时长和上游状态码，不作为主事实源。

## 建议的统一关联键
- 核心关联键：`request_id + task_id`
- 业务步骤键：`stage + exchange_label`
- 样本动作键：`continue_request_id`（首轮优先）

## 2026-06-10 verification repair 根因
- 当前已确认：
  - repair 的直接触发点不是“业务层主动选择修复”，而是 `full-story-verification` 主调用在 `finish_reason=length` 时返回了未闭合 JSON，解析失败后进入 repair。
  - 这次更像 `verification` 预算问题 + 截断处理策略问题，不像 prompt 体积问题，也不主要像纯随机波动。
- 关键证据：
  - 主调用 `completion_tokens` 打满当前 `verification` 预算上限。
  - 主调用 `content_chars` 很少，而 `reasoning_chars` 很高，说明大量预算消耗在 reasoning，导致 JSON 主体被截断。
  - 当前代码只在“截断且正文为空”时走更高预算 retry；本次正文非空，因此直接走 parse_failed -> repair。
- 当前建议：
  - 先继续复跑 1 到 2 个同配置 `3章` 样本，看是否稳定复现。
  - 若复现，再优先改 `verification` 的 `non-empty + finish_reason=length` 截断处理和预算策略，而不是先怀疑 prompt 体积。

## 2026-06-10 慢点根因解释
- 当前“慢”的主因不是数据库、文件落盘或前后端通信，而是 LLM 调用本身太重。
- 证据：
  - `first_token_ms` 虽然不低，但量级通常在 `0.5s ~ 5.5s`，不是总耗时大头。
  - 真正的大头在 `duration_ms`，说明主要时间消耗在模型持续生成和 reasoning。
- `verification` 之所以慢：
  - 验证 prompt 需要对已完成内容做一致性审查，天然会诱发较长 reasoning。
  - 输出结构虽然是 JSON，但在旧版本里问题条数、字段长度和总结长度都偏宽，导致模型容易“认真展开”。
- `drafting` 之所以慢：
  - 章节生成本身是长文本输出，输出 token 量天然大。
  - prompt 中同时携带章节目标、风格约束、章节规划、上一章全文、已完成章节摘要、上下文记忆、参考摘要，模型决策空间很大，容易进入长 reasoning。
  - 章节数增加后，这类长文本调用按章线性叠加，所以多章节样本中 `drafting` 会压过 `verification`。
- `planning` 也慢，但不是当前首要问题：
  - 大纲规划仍是一次长结构化输出，会消耗较长生成时间。
  - 但随着章节数增加，它不会像 `drafting` 那样按章放大。
- 因此根因不是“系统坏了”，而是：
  - `verification` 的检查任务过重；
  - `drafting` 的生成任务过重；
  - 两者都由 `mimo-v2.5-pro` 这类会输出较长 reasoning 的模型承担，放大了等待时间。
