### 慢点位置

1. 请求数已不是短流程的唯一主因。
   - 1 章短流程已经压到 3 次 LLM：大纲、正文、全文验证。
   - 仍需 155 秒，说明瓶颈从“请求次数过多”转为“单次请求输出慢 + reasoning token 过多”。

2. 大纲和验证的 reasoning token 占比过高。
   - 样本中大纲 `completion_tokens=1828`，其中 `reasoning_tokens=1513`。
   - 正文 `completion_tokens=1525`，其中 `reasoning_tokens=479`。
   - 验证 `completion_tokens=2532`，其中 `reasoning_tokens=2153`。
   - 验证 prompt 已要求不要输出分析过程，但模型仍在内部推理，说明需要模型参数/模型分流处理，单靠 prompt 不够。

3. 全文验证是短流程最大单点。
   - 1 章场景下验证耗时仍约 61 秒。
   - `verification_max_tokens` 默认 `4096`，短篇验证预算偏宽。
   - 验证返回结构化质量报告，输出正文不多，但 reasoning 多。

4. 任务生成链路没有真正的正文流式预览。
   - `BaseAgent._call_llm_stream_with_metadata()` 对 `reasoning_content` 发送 `model.thinking`，但对 `content` 只累积为 `full_content`，没有广播正文 chunk。
   - `TaskStore.broadcast_event()` 是瞬时广播，不落盘，适合实时 SSE。
   - 任务页 `EventSource` 收到 `snapshot/task.event/task.done` 后只是触发 `refreshWorkspace()`，没有消费 SSE payload 追加本地状态。
   - 因此即使后端广播了 `model.thinking`，前端也可能因为刷新的是 workspace 持久事件而看不到真正逐 chunk 变化。
   - 聊天页已有逐 chunk SSE 消费范式，可作为任务页实现参考。

5. TaskStore/DB/RAG 不是当前短流程主瓶颈。
   - 之前写放大问题已处理，`model.thinking` 不再写入任务文件。
   - parse 时间约 `0.03ms`。
   - DB/TaskStore 相对 LLM 调用耗时很小。
   - RAG rebuild 有独立重建耗时问题，但不是本次 1 章生成主瓶颈。

6. 大项目下仍会被请求数放大。
   - 正文基础请求约等于章节数 `N`。
   - 自动审核开启时，大纲/章节/验证审核会额外产生多个 Agent 请求。
   - 驳回修订会产生“审核 LLM + 修订 LLM + 再审核 LLM”循环。
   - 全文验证/修复会随章节数变大而更重。

### opencode/Crush 对照结论

- `opencode-ai/opencode` 当前 GitHub README 明确说明项目已归档，并迁移到 `charmbracelet/crush`。
- Crush 的快主要来自代码任务形态：
  - 使用 `ls/grep/view/diagnostics/lsp/sourcegraph/edit/multiedit/agent` 等工具检索局部证据。
  - 使用 `.crushignore`、项目初始化上下文文件、session context、LSP/MCP 维持项目上下文。
  - 支持 workspace SSE，把 message、tool call、reasoning、finish 等消息 part 实时送到客户端。
  - 支持 large/small model、子 Agent、provider options、reasoning/thinking 参数。
- 它能在大项目中“短请求成功输出”的核心不是把全项目塞进一次 LLM，而是：
  - 先用工具查局部上下文；
  - 模型输出小 patch、工具调用或短解释；
  - 对话上下文接近上限时自动摘要/压缩；
  - UI 直接消费实时消息事件。
- 小说任务不能完全照搬，因为小说正文是目标产物，正文 token 不能像代码 patch 那样省掉。
- 可迁移的是“局部检索、分层上下文、模型分流、流式事件消费、推理预算控制”；不可迁移的是“用小 patch 替代主体输出”。

### 更快输出的可行方案推测

方案 A：用户感知最快，做任务正文流式预览。

- 后端在 `_call_llm_stream_with_metadata()` 中对 `chunk.content` 增加瞬时事件，例如 `model.content.delta` 或 `chapter.content.delta`。
- 任务页 EventSource 不只刷新 workspace，而是解析 `task.event` payload，直接追加到本地 `liveDrafts/liveThinking` 状态。
- 章节输出采用边界解析：正文位于 `chapter_content_boundary` 后、`chapter_end_boundary` 前时展示为“草稿预览”，最终 `chapter.saved` 后替换为持久章节。
- 预期：总耗时不一定减少，但首屏可见输出可从几十秒后变成首 token 后立即出现，用户感知会明显改善。

方案 B：降低总耗时，优先压验证和 reasoning。

- 短篇/低章节数将 `verification_max_tokens` 动态降到 `800~1600`。
- 验证模型分流到更快、更少 reasoning 的模型，正文仍使用强创作模型。
- 对支持的 provider/model 增加 `reasoning_effort=low`、`thinking=false`、`enable_thinking=false`、`extra_body` 等可配置项。
- 短篇可采用规则验证优先：章节数少、无复杂设定时先做本地结构校验，LLM 验证降级为可选。
- 预期：短篇可能减少 `30~70s`；长篇随验证输入规模增长，收益更明显。

方案 C：大项目吞吐优化，减少请求放大。

- 保留章节并行，但把并行策略从“首批可并行”扩展为“依赖允许的窗口并行”，例如每批 2 章同时生成，后续依赖上一批摘要。
- 自动审核按风险开关：低风险阶段走轻量规则/小模型，高风险再触发多 Agent。
- 审核输出改为结构化短报告，严格限制 `issues` 数量和 reasoning 字段长度。
- 章节修复继续使用 patch，不返回完整全书或完整章节数组。

方案 D：观测闭环。

- 在 workspace 增加派生 `llm_report`，从 `model.usage/context.history.updated/cache.hit` 聚合请求数、token、cache、阶段耗时。
- 增加节点级 timeline：LangGraph 节点进入/退出、LLM 首 token、完成、repair/retry。
- 前端展示当前阶段的“首 token、输出中、累计字符、预计剩余”，帮助判断是网关慢、reasoning 慢还是前端没显示。

### 推荐优先级

1. 先做方案 A：任务正文/思考的真实 SSE 增量消费，解决“看起来没输出”的问题。
2. 再做方案 B：短篇验证降预算 + 快速验证模型 + reasoning 参数控制，解决“总耗时太长”的问题。
3. 再做方案 D：workspace `llm_report` 和节点 timeline，避免后续靠人工翻日志定位。
4. 最后做方案 C：章节窗口并行和审核风险分流，主要服务更大项目。

当前推荐的第一批实施范围：

- 后端：新增 `model.content.delta`/`chapter.content.delta` 瞬时事件，不落盘。
- 前端：任务页直接消费 SSE payload，维护 live preview，不再只依赖 `refreshWorkspace()`。
- 配置：增加按阶段的 max tokens/reasoning 参数，至少先给 verification 单独配置。
- 测试：覆盖瞬时事件不落盘、SSE payload 可被前端 reducer 合并、验证 max tokens 动态降低。

## 方案讨论补充：不影响正文输出的多次输出方案

用户进一步约束：

- 希望给出处理方案。
- 不能影响当前最终正文输出质量与结果结构。
- 可以支持多次输出/增量输出。

推荐设计方向：

- 将“多次输出”设计为旁路实时预览通道，不替换现有最终正文生成链路。
- 现有正文仍由 `_complete_stream_json_with_cache()` 完整收集、解析、缓存、生成 `chapter.saved` 和最终工件。
- 新增的实时输出只做 transient SSE，不落盘、不参与 JSON 解析、不写入 `conversation_history`，因此不会改变模型上下文和最终正文。
- 前端维护独立的 `liveDrafts` 状态，展示“生成中草稿预览”；当 `chapter.saved` 到达后，用正式章节内容覆盖预览。

可选方案：

1. 最保守方案：只广播原始 `chunk.content` 到前端预览，不改变后端解析流程。
2. 章节感知方案：在前端根据章节边界识别正文段，实时展示章节正文预览。
3. 分阶段方案：先广播大纲/验证/正文的统一 `model.content.delta`，后续再优化为章节专用 `chapter.content.delta`。

当前推荐：

- 先采用方案 1 + 轻量章节聚合。
- 后端只加瞬时 SSE delta。
- 前端只新增本地 live preview reducer。
- 最终正文仍以 `chapter.saved`/`result.json`/章节文件为准。

## 单章场景提效判断

针对当前 1 章任务：

- 该方案对“总完成时间”提升有限，因为大纲、正文、全文验证仍需要完整执行。
- 该方案对“首个可见正文时间”有明显提升，只要模型开始输出正文内容，前端即可展示草稿预览。
- 如果模型先输出大量 reasoning，再输出正文，仅广播 `content` 时首个正文仍会被 reasoning 阶段拖延；可同时展示 `model.thinking` 作为状态反馈，但正文预览仍以 `content` 为准。
- 单章没有章节并行空间，所以并行优化收益接近 0。
- 单章最大实际提速点不是流式预览，而是降低/后台化全文验证，以及控制 reasoning。

单章推荐组合：

1. 正文旁路流式预览：提升用户感知速度，不改变最终正文。
2. `chapter.saved` 后立即允许查看/审核章节：把“可阅读时间”提前到全文验证之前。
3. 短篇验证降级：1 章场景将验证预算降到 `800~1600`，或将验证后台化/可选化。
4. 按阶段关闭或降低 reasoning：特别是大纲和验证阶段。

预期效果：

- 若只做流式预览：总耗时基本不变，但用户能更早看到正文。
- 若增加“章节完成即展示”：用户可在大约大纲 + 正文完成后阅读，不必等全文验证。
- 若同时降低验证与 reasoning：才会实质减少总耗时。

## 单章提效幅度预估

基于样本 `task_76327d8c7b`：

- 当前总耗时约 `155s`。
- 章节完成时间约 `94s`。
- 全文验证约 `61s`。

分项预估：

- 仅“章节完成先展示”：可阅读时间从约 `155s` 提前到约 `94s`，用户等待正文时间减少约 `61s`，感知提升约 `39%`；总完成时间基本不变。
- 验证降级：若 1 章验证从约 `61s` 降到 `15~30s`，总完成时间约为 `109~124s`，总耗时减少约 `20%~30%`。
- reasoning 控制：如果大纲/验证 reasoning 明显下降，大纲可能从约 `47s` 降到 `28~38s`，验证可能进一步稳定在 `12~25s`，正文变化较小；组合后总耗时可能落在 `85~110s`，总耗时减少约 `29%~45%`。

保守预期：

- 不牺牲正文质量的前提下，推荐目标是单章从 `155s` 降到 `95~115s`。
- 用户可阅读正文时间从 `155s` 提前到 `70~95s`。
- 低于 `80s` 需要更激进的模型分流/跳过验证，质量风险更高。

## 更激进方案补充

如果目标继续压低到 `80s` 以下，必须减少前台阻塞 LLM 调用或改变请求形态：

1. 单章快速路径：把“大纲 + 单章正文”合并为一次 LLM 调用。
   - 当前前台至少大纲约 `47s` + 正文约 `46s`。
   - 合并后前台理论上接近一次正文级调用，约 `45~70s`。
   - 风险：大纲独立审核能力变弱，需要仅对单章/短篇启用，并保留原流程。

2. 验证后台化：正文完成即进入 `draft_ready`，全文验证异步继续。
   - 用户可读时间可从 `155s` 降到正文完成时。
   - 不改变正文，只改变“完成/可读/验证中”的状态语义。

3. 模型分流：大纲和验证用快模型，正文继续用质量模型。
   - 目标是大纲 `47s -> 10~20s`，验证 `61s -> 8~20s`。
   - 正文质量不受影响，但大纲质量可能轻微下降；可用规则兜底。

4. 单章跳过 LLM 全文验证：只做本地结构校验，LLM 验证改为用户点击或后台任务。
   - 总耗时可能接近 `大纲 + 正文`，约 `70~95s`。
   - 质量门变弱，但 1 章场景风险可控。

5. 分段并行生成单章：先生成小纲，再并行生成开端/中段/结尾，最后合并。
   - 理论可降低正文墙钟。
   - 风险最大，容易影响语气连续性和最终正文质量，不建议作为首选。

更激进推荐路线：

- 第一档：快速路径可选开关 + 验证后台化，目标 `60~90s` 可读。
- 第二档：大纲/验证快模型 + reasoning 关闭，目标 `70~100s` 完成。
- 第三档：单章一体化调用 + 后台验证，目标 `45~75s` 可读，但需要保留原流程作为高质量模式。
