# LLM 请求次数与 Agent 生成速度分析

## 用户原始诉求

对于现在的 LLM 请求次数导致 agent 生成速度太慢的原因，需要多维度进行 review 和动态分析；分析 opencode 在面对更大项目、更长文本时为什么能够达到短请求并成功输出，而当前 agent 流出现慢的问题；分析耗时并给出更成功的优化方案与解决方案推测。

## 当前状态

实现中。用户已选择方案 B：进入实现，优先做 P0+P1 组合优化。

## 初始分析方向

- 复核当前 LangGraph/Agent 流中 LLM 调用次数、串并行关系、审核/重写循环与上下文压缩链路。
- 对比 opencode 类编码 Agent 的短请求策略：工具检索、增量上下文、补丁式输出、会话压缩与任务切分。
- 结合本项目任务耗时记录、日志与实现路径，估算主要耗时来源并提出可执行优化方案。

## 只读分析结论

### 当前主链路

- 主图在 `apps/agent-runtime/app/graph/main_graph.py` 中串行推进：`normalize_request -> prepare_outline_context -> plan_story -> review_outline -> prepare_chapter_pair_context -> draft_chapter_pair -> review_chapter_pair -> accumulate_chapters -> verify_full_story -> review_verification -> assemble_result`。
- 真正的创作 LLM 请求集中在 `apps/agent-runtime/app/llm/story_engine.py`：
  - `build_story_plan()`：大纲 1 次。
  - `build_chapter_plan_batch()`：仅当总纲缺少完整章节计划时额外调用。
  - `generate_chapter_pair()`：每章 1 次正文生成。
  - `revise_chapter_pair()`：每轮章节驳回 1 次。
  - `verify_full_story()`：全文验证 1 次，请求包含已完成全文。
  - `fix_verified_issues()`：验证驳回后 1 次，可能要求返回全部章节。
- 上下文/RAG 节点本身不调用 LLM，但会增大 prompt。`ContextManager` 当前是截断压缩和缓存，不是 LLM 摘要压缩。

### 请求次数模型

- 不开自动审核、无重试时，最小请求数约为：`1 大纲 + N 章节 + 1 全文验证 = N + 2`。
- 1 章短篇的最小链路就是 3 次 LLM，已被最新真实样本验证。
- 旧自动审核模式会放大：
  - 大纲审核：3 个子 Agent 并行 + 1 个综合 Agent，约 4 次。
  - 章节审核：每个章节批次约 4 次，批次数约 `ceil(N / 2)`。
  - 验证审核：2 个子 Agent + 1 个综合 Agent，约 3 次。
  - 估算：`N + 2 + 4 + 4 * ceil(N / 2) + 3`。
- 动态审核模式更重：每个审核点会增加 `Master + Planner + 多个执行 Agent + 综合 Agent`，常见约 6 到 9 次 LLM。7 章任务可能从最小约 9 次放大到 40 次以上。
- 解析失败、输出截断、网络 5xx、流式失败 fallback、JSON repair 都会额外增加请求次数。

### 真实耗时证据

- `worklog/archive/backend-performance/20260604-01-全流程Agent创作耗时测试.md` 记录了三轮关键样本：
  - 修复前干净样本 `task_3cd9e991b3`：墙钟 `443.945s`，LLM 总耗时 `428.727s`，占 `96.6%`。4 次 LLM 中有重复正文和全文验证长耗时。
  - 中间修复后 `task_6a89271555`：墙钟 `304.794s`，LLM 约 `216.75s`。剩余问题是全文验证首次被截断并触发 repair。
  - 最新真实样本 `task_cbef466e90`：墙钟 `195.087s`，3 次 LLM 总约 `186.43s`：大纲 `54.6s`、正文 `90.4s`、全文验证 `41.4s`。
- 最新样本中 DB 约 `90ms`、TaskStore 约 `1.61s`，已经不是主瓶颈。
- 结论：请求次数已经被压到最小后，仍然慢，说明单次请求输出长度、reasoning、模型速度和全文验证 prompt 也是主因。

### opencode/Crush 对比

- 原 `opencode-ai/opencode` 仓库已归档，README 指向 `charmbracelet/crush` 继续维护；本次同时参考了 opencode 文档和 Crush 源码。
- opencode/Crush 能在大项目中保持短请求，关键不是“读入更多全文”，而是：
  - 代码项目以工具检索为主，`grep/glob/view` 只返回局部证据；Crush 的 `grep` 默认最多 100 条结果，单行宽度也截断，`view` 默认 200 行且最大 200KB。
  - 输出通常是补丁、命令结果或短回答，不需要像小说正文一样生成数千字内容。
  - 会话接近上下文窗口时自动 summarization；Crush 根据 session token 与模型 context window 计算阈值，触发 `Summarize()` 写入 summary message。
  - 工具和消息流有工程限流；Crush 的 message service 使用 33ms debounce 合并流式更新，避免每个 chunk 都同步落库。
  - 允许 subagent/task tool 和并行工具调用，把探索任务局部化；子 Agent 不必继承主会话全部上下文。
  - 支持 `.gitignore` / `.crushignore`、项目初始化上下文文件、LSP、MCP，减少无关上下文进入请求。
- 当前小说 Agent 流与之不同：
  - 业务目标就是长文本生成，正文 tokens 无法像代码 diff 一样省掉。
  - 每个章节请求携带大纲、风格、参考、已完成摘要、上一章全文，最终响应又是长正文。
  - 全文验证直接消费整部作品，章节越多 prompt 越大。
  - 自动审核把一个审核点拆成多个 LLM，而不是一个轻量判定。

## 优化方案推测

### P0：先把请求数继续锁死在可解释范围

- 关闭或限制动态审核作为默认路径。动态 Agent 审核适合深度评审，不适合默认创作提速。
- 新增轻量自动审核模式：每个审核点最多 1 次 LLM，优先用规则检查字数、章节数、JSON 完整性、章节号连续性；只有失败或高风险时升级多 Agent。
- 为每个任务输出聚合报告：节点、exchange_label、model、prompt_tokens、completion_tokens、reasoning、cache 命中、首 token、总耗时、repair/retry 次数。
- 将 `generate_chapter_pair()` 的并行触发条件与批次大小对齐。目前默认批次 2，但并行最小批量默认 3，正常基本不会触发。

### P1：降低单次请求时长

- 章节正文继续每章 1 次，但提供“快速草稿模式”：降低 reasoning、收紧 max_tokens、要求少量元数据 + 正文边界，不让模型输出大段分析。
- 全文验证改成分层验证：
  - 章节生成后做增量校验，只检查当前章节与前文摘要。
  - 最终全文验证只读结构摘要、问题索引和必要片段，默认不把全文一次性塞进 prompt。
  - 只有用户选择“严格全文审校”时才执行完整全文验证。
- `fix_verified_issues()` 避免默认返回全部章节；改为返回补丁式章节修复计划或指定章节内容，未改章节复用原文。
- Prompt cache 继续做稳定前缀：system、风格约束、世界观、大纲尽量固定顺序放前面；动态尾部只放章节号、上一章摘要、当前目标。

### P2：向 opencode 式架构靠拢

- 引入“上下文句柄 + 按需取材”的内部工具层：LLM 不直接接收全部参考/全文，而是接收可查询的章节摘要、设定表、角色表、时间线和片段检索工具。
- 将写作状态结构化：`story_bible`、`chapter_summary_index`、`continuity_facts`、`open_threads`、`style_constraints`。每章请求只带当前章节需要的结构摘要。
- 审核改为 sidecar：先用规则和结构化事实快速判定，通过则不消耗审核 LLM；失败时只把相关片段派发给审核 Agent。
- 子 Agent 必须有明确上下文边界，禁止每个子 Agent 都接收完整正文。

## 当前建议

推荐先执行 P0 + P1 的组合：默认轻量审核、章节并行阈值与批次对齐、全文验证分层化、修复改补丁式返回，并补一份任务级 LLM 聚合报告。这样不破坏小说生成语义，且最可能把 1 章短流程从约 195 秒压到 100 秒以内；多章任务则主要靠章节批次并行和轻量审核降低墙钟。

高风险方案是直接复刻 opencode 的通用工具 Agent 架构。它适合代码修改，但对小说正文生成不能消除输出 tokens，只能减少上下文和审核成本，因此不应作为第一阶段。

## 2026-06-05 结果原因复盘

- 当前真实样本已经排除了“请求次数过多”这个单一原因：自动审核与动态审核关闭后，任务仍只产生最小链路 3 次 LLM，但墙钟仍为 `155.045s`。
- 根因一：单次模型调用慢。大纲 `47.460s`、正文 `46.111s`、全文验证 `61.084s`，三次 LLM 几乎覆盖全部墙钟，DB、TaskStore 和审核推进不是主要耗时。
- 根因二：输出 token 与 reasoning 过重。本次 token 合计 `8010`，其中 output `5885`，占比约 `73.5%`；说明慢更多来自模型生成/思考，而不是输入 prompt 太长。
- 根因三：verification 仍是短篇链路中的最大单点。本次 verification prompt 只有约 `1804` 字符，但输出 `2532` tokens、耗时 `61.084s`，说明验证 prompt 已经变短，但验证模型仍倾向长思考/长输出。
- 根因四：1 章样本无法体现章节并行收益。章节并行阈值已修正为 2，但真实样本只有 1 章，所以不会触发并行；并行收益需要 2 章或 3 章样本观察。
- 根因五：opencode/Crush 的短请求优势来自“检索局部证据 + 输出补丁”，而小说任务的核心成本是“生成正文 + 审核文本”，输出本身不可像代码 diff 一样压缩到几十行。
- 结论：本项目慢已经从“请求次数爆炸”切换为“最小请求链路下单次 LLM 太重”。后续优化必须减少验证/审核输出预算、降低 reasoning、按规则跳过低风险审核，或改成结构化增量校验，不能只继续削 prompt。
