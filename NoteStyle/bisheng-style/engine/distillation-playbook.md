# 蒸馏操作手册

## 标准化流程

### 第1步：前置条件检查

- 确认原始文本（小说正文）已就位，格式为纯文本或Markdown。
- 确认章回结构已明确：总章数、章节编号方式、章节长度分布。
- 确认目标作者身份和作品范围，避免跨作者混淆。
- **不通过处理**：缺少原文则暂停，要求用户提供或指定文本来源；章回结构不明则手动标记后继续。

### 第2步：创建目录

- 从 `engine/instance-template/` 复制完整模板到 `instances/<作者标识>-<作品标识>/`。
- 确认目录结构包含：`manifest.yaml`、`rules/`（含所有rules文件）、`distillation/`（蒸馏分析存放目录）。
- **不通过处理**：模板缺失则回退到手动创建，并记录缺失项。

### 第3步：信息采集（Phase 1）

- 按照11个维度逐一采集原始数据：
  1. 叙事技术
  2. 语言风格
  3. 人物模板
  4. 情节结构
  5. 情感模式
  6. 世界观构建
  7. 信息编码
  8. 对话声学
  9. 动作编码
  10. 修辞签名
  11. 母题变奏
- 抽样不少于30段代表性文本片段，覆盖开篇、中段、高潮、结尾各区域。
- 每个维度至少引用3段原文作为证据。
- **不通过处理**：抽样不足则补充采集；维度缺失则标记为"待补充"并继续。

### 第4步：采集Review检查点（Phase 1.5）

- 检查11个维度的采集完整性：
  - 每个维度是否至少有3条原文证据？
  - 证据分布是否均匀（非集中于同一章节）？
  - 是否存在维度间交叉引用的遗漏？
- 输出《采集Review报告》，列出缺失项和补充建议。
- **不通过处理**：返回第3步补充采集，直到所有维度达标。

### 第5步：写作DNA提炼（Phase 2）

- 对Phase 1采集的原始数据进行提炼，生成12个蒸馏分析文件：
  1. `01-narrative-technique.md` -- 叙事技术提炼
  2. `02-language-style.md` -- 语言风格提炼
  3. `03-character-template.md` -- 人物模板提炼
  4. `04-plot-structure.md` -- 情节结构提炼
  5. `05-emotion-pattern.md` -- 情感模式提炼
  6. `06-worldbuilding.md` -- 世界观构建提炼
  7. `07-info-encoding.md` -- 信息编码提炼
  8. `08-dialogue-acoustics.md` -- 对话声学提炼
  9. `09-action-encoding.md` -- 动作编码提炼
  10. `10-rhetoric-signature.md` -- 修辞签名提炼
  11. `11-motif-variation.md` -- 母题变奏提炼
  12. `12-length-baseline.md` -- 篇幅基线提炼
- 每个文件需包含：核心发现、原文证据、规则化表述、可执行检查项。
- **不通过处理**：提炼不充分则返回补充分析；文件缺失则标记并继续。

### 第6步：编译为实例

- 按照 `engine/compilation-map.md` 的映射关系，将12个蒸馏分析文件编译为实例rules文件。
- 编译顺序：
  1. 先写入通用性规则到各 `rules/*.md` 文件。
  2. 再将具体数值参数写入 `rules/constraints.md`。
  3. 最后更新 `manifest.yaml` 中的元数据。
- 编译时确保每条规则都有溯源标注（标注来源蒸馏文件编号）。
- **不通过处理**：映射关系不明确则参考原文重新定位；编译产物与蒸馏数据不一致则回退修正。

### 第7步：质量验证（Phase 4）

- 执行八道门质量检查：
  1. **Schema完整性**：所有rules文件是否按模板结构填写？
  2. **证据链**：每条规则是否有蒸馏产物的证据支撑？
  3. **Guardrail可执行性**：约束条款是否可被直接执行（无需二次解读）？
  4. **manifest完整性**：manifest.yaml所有必填字段是否已填写？
  5. **fidelity_score**：保真度评分是否达到阈值（>=75）？
  6. **编译映射覆盖**：所有蒸馏产物是否已被映射到实例产物？
  7. **负例拦截**：是否能拦截与该作者风格不符的生成内容？
  8. **跨文件一致性**：各rules文件之间是否存在矛盾？
- **不通过处理**：根据失败类型查阅 `engine/quality-loop-protocol.md` 中的自动回修映射进行修复。

## 回退路径

| 步骤 | 不通过条件 | 回退目标 | 修复动作 |
|------|-----------|---------|---------|
| 第1步 | 原文缺失 | 暂停流程 | 要求用户提供原文 |
| 第2步 | 模板缺失 | 手动创建 | 按标准结构补建 |
| 第3步 | 采样不足 | 返回第3步 | 补充采集至30+段 |
| 第4步 | 维度缺失 | 返回第3步 | 针对缺失维度补充 |
| 第5步 | 提炼不充分 | 返回第5步 | 补充分析并重写 |
| 第6步 | 编译不一致 | 返回第6步 | 重新映射并修正 |
| 第7步 | 质量不达标 | 根据失败类型 | 查阅回修映射修复 |

## 注册流程

实例的生命周期状态通过 `manifest.yaml` 中的 `status` 字段管理：

1. **draft**：蒸馏进行中或编译未完成时的初始状态。
2. **active**：通过质量验证（第7步八道门全部通过）后，由人工确认激活。激活后可用于生产创作。
3. **deprecated**：作者风格发生显著变化、蒸馏数据过期、或被新版本实例替代时，标记为废弃。废弃实例保留但不再用于创作引导。

状态流转规则：
- draft → active：必须通过第7步质量验证 + 人工确认。
- active → deprecated：人工确认后标记，同时记录替代实例的指向。
- 禁止从 deprecated 回退到 active，如需恢复应创建新实例。
