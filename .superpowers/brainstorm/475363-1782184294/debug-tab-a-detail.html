首批信息密度选择

A

轻量诊断页

只做诊断结论、实时连接、LLM 摘要、Agent Trace 摘要、最近事件。实现快，字段基本来自 `WorkspaceResponse`。

B

推荐：均衡诊断页

轻量页基础上增加上下文/RAG、状态对账、证据链接。仍以只读为主，少量新增前端派生逻辑。

C

完整诊断页

加入事件过滤、LLM exchange 列表、RAG 命中详情、原始 JSON 浏览。信息最全，但首批实现和性能风险更高。

我建议首批采用 B

原因：A 太轻，无法覆盖你历史上反复遇到的“状态错位、SSE 误判、LLM 卡住、RAG 是否参与”问题；C 又会逼近完整日志浏览器。B 能形成真正可用的排障页，同时不要求后端先新增复杂接口。
